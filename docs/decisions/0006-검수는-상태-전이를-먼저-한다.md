# 0006. 검수는 상태 전이를 먼저 하고 검수 기록은 그 뒤에 만든다

- 날짜 / 관련 기능: 2026-10-22 / F13 (Task 7)
- 상황:
  - Task 6에서 이력 INSERT가 단말기 UPDATE보다 먼저 나가 데드락이 났다(troubleshooting/0004). 자식 행 INSERT의 FK 검사가 부모 `terminal` 행에 공유 락(S)을 잡고, 뒤이은 UPDATE가 배타 락(X)을 기다린다. 동시에 여러 트랜잭션이 S를 쥐면 아무도 X로 올리지 못한다.
  - 그래서 `TransitionService`는 상태 변경 직후 `flush()`로 UPDATE를 먼저 보낸다.
  - 검수(`InspectionService.inspect`)는 바깥 트랜잭션 하나에서 `Inspection`·`InspectionResult`를 만들고 `transition(cmd, tx)`를 부른다. 계획 코드는 검수 기록을 먼저 `tx.create`하고 전이를 불렀다. 그러면 전이 안의 `flush()`가 같은 작업 단위에 쌓인 검수 INSERT까지 함께 보내고, MikroORM은 flush 한 번 안에서 INSERT를 UPDATE보다 먼저 보낸다. Task 6과 같은 S→X 순서가 다시 생긴다.
- 선택지:
  1. 전이를 먼저 부르고, 검수 기록은 그 뒤에 만든다(커밋 때 flush).
     - 장점: 코드 순서만 바꾸면 된다. 전이 서비스의 "UPDATE 먼저" 규칙과 같은 방향이다. 전이가 거절되면(422·409) 검수 기록은 만들어지지도 않는다.
     - 단점: 호출하는 쪽이 순서를 알아야 한다. 나중에 다른 기능이 같은 실수를 할 수 있다.
  2. 검수 기록을 만들기 전에 `tx.lock(terminal, LockMode.PESSIMISTIC_WRITE)`(`SELECT ... FOR UPDATE`)로 단말기 행에 X 락을 먼저 잡는다.
     - 장점: 이후 INSERT 순서와 상관없이 안전하다.
     - 단점: 낙관적 락으로 정한 decisions/0004와 섞인다. 동시 요청이 줄 서서 기다리고, 뒤에 들어온 요청은 409 대신 기다렸다가 규칙 위반 422로 끝나는 등 응답 의미가 바뀐다. 쿼리가 하나 늘어난다.
  3. 계획 순서 그대로 둔다.
     - 장점: 계획 코드와 같다.
     - 단점: 같은 단말기 동시 검수에서 데드락이 500으로 나간다. 실험으로 확인했다(experiments/0002: 3회 모두 `{"201":1,"500":9}`).
- 결정: 1. 이유: 원인이 쿼리 순서이므로 순서를 바로잡는 것이 가장 작은 변경이다. 이미 정한 낙관적 락 방식(decisions/0004)을 그대로 쓰고, 응답도 전이 API와 같은 409 `VERSION_CONFLICT`가 된다. 수정 후 실험 3회 모두 `{"201":1,"409 VERSION_CONFLICT":9}`, 새 데드락 없음.
- 결과·대가:
  - `inspection.service.ts`에 순서 이유를 주석으로 남겼다. 전이와 자식 기록을 한 트랜잭션에서 쓰는 기능(앞으로 출고·회수 등)은 같은 규칙을 따라야 한다: 전이 먼저, 단말기를 참조하는 INSERT는 나중.
  - 규칙이 코드 구조로 강제되지 않고 주석과 기록으로만 지켜진다.
- 다시 볼 조건: 전이와 함께 자식 기록을 쓰는 기능이 두세 개 더 생기면, 전이 서비스가 "전이 후 실행할 콜백"을 받거나 2(비관적 락)로 구조에서 막는 방식을 검토한다. 다른 경로에서 데드락이 다시 보이면 필터에 1213 매핑이나 재시도도 함께 검토한다.
