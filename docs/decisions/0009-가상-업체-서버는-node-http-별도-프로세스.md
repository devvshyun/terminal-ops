# 0009. 가상 업체 서버는 node:http 별도 프로세스로 만든다

- 날짜 / 관련 기능: 2026-10-22 / F12
- 상황: 택배사 2곳과 메신저 1곳을 흉내 내야 한다. 실제 업체 API는 쓰지 않는다(CLAUDE.md). 골칫거리(중복·429·지연·5xx·순서 섞기)를 설정으로 켜고 끄고, 몇 번 불렸는지 세야 한다.
- 선택지:
  1. API 테스트 안에서 `fetch`를 가로채는 목(mock) — 빠르지만 HTTP·타임아웃·직렬화를 건너뛰고, 워커 프로세스 2개 실험에서 공유할 수 없다.
  2. Nest로 서버를 하나 더 — 익숙하지만 의존성이 무겁고, 가짜 서버에 DI가 필요 없다.
  3. `node:http` + TypeScript 별도 프로세스, 메모리 상태, 관리 API — 의존성은 fast-xml-parser 하나. API 서버·워커·실험이 같은 서버를 진짜 HTTP로 쓴다.
- 결정: 3. 난수는 시드로 재현한다(mulberry32). 확률이 0인 설정은 난수를 쓰지 않아 다른 설정의 난수 순서를 흔들지 않는다.
- 결과·대가: 상태가 메모리에만 있어 재시작하면 사라진다(운송장 번호는 시작 시각을 앞에 붙여 겹치지 않게 했다). 동시 요청 순서에 따라 난수가 어느 요청에 쓰일지는 달라진다(순서가 정해진 단일 요청 테스트에서만 완전히 재현된다).
- 다시 볼 조건: 업체가 늘어 라우팅이 복잡해지면 작은 라우터를 도입한다.
- 갱신(2026-10-23 Day 3): 세움전자(공장)를 같은 서버에 더했다. 납품 명세는 발주 때 정해 두고(조회마다 같다), 다른 발주 시리얼이 섞이는 자리는 시드 난수로 재현한다.
- 갱신(2026-10-23 Day 4): 단말기 시뮬레이터 `apps/device-sim`도 같은 방식(node:http 별도 프로세스, 메모리 상태, 관리 API, 시드 난수)으로 만들었다. 의존성은 개발용(typescript·vitest·@types/node)뿐. 다른 점: ① 우리 API를 **부르는** 쪽이라 keep-alive 에이전트 하나로 소켓 수를 concurrency로 묶는다(5,000대가 요청마다 연결을 열면 Windows 임시 포트가 TIME_WAIT로 바닥날 수 있다) ② 앞 주기가 안 끝났으면 그 주기는 건너뛰고 skippedTicks로 센다(밀린 하트비트를 몰아 보내 부하를 부풀리지 않는다) ③ 오프라인 단말기는 시드로 섞어 고른다(같은 시드면 같은 단말기). 테스트에서는 실제 프로세스가 필요한 곳(연동 확인·실험)만 `test/helpers/device-sim.ts`로 띄우고 PID로 끈다(Task 8). 포트는 개발 4020, 테스트 4021.
- 갱신(2026-10-23 Day 4 리뷰 반영, 실험 0008 신뢰성): device-sim 부하 모델과 통계의 한계를 적는다. **실험 0008에도 이 내용을 그대로 적어야 한다.**
  - **부하 모델**: 한 주기가 시작되면 온라인 단말기의 하트비트를 한꺼번에 만들어 `concurrency`까지 동시에 보낸다(burst). 실제 단말기는 각자 다른 시각에 보내 부하가 퍼지지만, 여기서는 주기 시작에 몰린다. 닫힌 루프(closed-loop)라 응답이 늦어지면 동시 요청 수는 그대로이고 보내는 속도만 줄어든다(개방 루프처럼 대기열이 쌓이지 않는다). 그래서 서버가 느려지면 요청률이 스스로 낮아져 "견딘 것처럼" 보일 수 있다. 다 못 보낸 주기는 건너뛰고 `skippedTicks`로 센다.
  - **응답 시간은 보낸 시각부터**: 클라이언트가 요청을 만든 시각에서 본문을 다 받은(또는 실패한) 시각까지다. 소켓을 기다린 시간(`maxSockets` 대기)과 연결을 새로 맺은 시간이 포함된다. 서버 처리 시간만이 아니다.
  - **keep-alive와 서버 `keepAliveTimeout`**: Node http 서버의 기본 keepAliveTimeout은 5초다. 주기가 5초보다 길면(기본 30초) 서버가 유휴 연결을 끊어 둬서 **각 주기의 첫 묶음들은 연결을 다시 맺거나(드물게) 끊긴 소켓을 만나 실패할 수 있다**. 그래서 주기 첫 묶음의 응답 시간이 나머지보다 길게 나올 수 있다.
  - **실패도 센다**: 응답 시간 분포에 실패(시간 초과·연결 오류·non-2xx·`results` 없는 2xx)를 함께 기록한다(`latency` 전체, `latencyOk`·`latencyFailed`). 성공만 재면 가장 느린 요청이 빠져 p95가 낮게 나온다. 오류는 `httpErrors`·`timeouts`·`networkErrors`·`badResponses`로 나누고 `errors`는 그 합이다.
  - **히스토그램**: 표본을 쌓지 않고 로그 간격 구간(이웃 구간 비율 1.01, 0.001ms~1e7ms, 범위 밖은 양 끝 구간)에 센다. 메모리는 구간 수로 고정, `/stats`는 구간 수만큼만 돈다. 백분위는 구간 윗경계라 실제보다 최대 1% 크게 나올 수 있다(`approx: true`). `count`·`max`는 정확하다. 버리는 값이 없어 `dropped`는 두지 않았다. 선택지였던 reservoir sampling은 꼬리(p99 이상)가 표본 크기에 따라 흔들려 버렸다.
  - **stop**: 주기 도중이면 새 묶음을 보내지 않고, 이미 보낸 요청의 응답(또는 `requestTimeoutMs`)만 기다린다. 이전에는 주기 전체가 끝나길 기다렸다. 그래서 멈춘 주기는 일부 단말기만 보낸 것이다(`ticks`는 세지만 `heartbeatsSent < 대수`일 수 있음).
  - **설정 검증·직렬화**: 키마다 형식·범위(`CONFIG_RULES`), 알 수 없는 키는 400. `count`·시리얼 목록 상한 20,000, `batchSize` 상한 500(API 한도). 새 설정 키를 더하면 `CONFIG_RULES`에도 한 줄 더해야 받는다. config·start·stop·reset 관리 요청은 promise 줄로 하나씩 처리하고, 현재 설정과의 합치기도 줄 안에서 한다. 적용이 중간에 실패하면 이전 설정을 두고 돌던 중이었으면 다시 돌린다.
