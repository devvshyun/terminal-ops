# 0019. 일괄 처리는 행별 결과와 한 트랜잭션

- 날짜 / 관련 기능: 2026-10-23 / F1, F6
- 상황: 박스 스캔(수백 대)과 엑셀(수천 행)은 일부 행만 문제가 있는 것이 보통이다. 행마다 조회하면 N+1, 행마다 트랜잭션이면 이력·Outbox가 행마다 커밋된다. 설계안 Day 3 학습 주제(대량 flush, N+1).
- 선택지(부분 실패):
  1. 전부 아니면 전무: 한 행이라도 틀리면 400. 운영자가 박스 하나를 다시 찍어야 하고, 어떤 행이 문제인지 따로 알려야 한다.
  2. **행별 결과, 유효한 행만 반영**: 결과 코드(CREATED, INVALID_FORMAT, DUPLICATE_IN_REQUEST, UNKNOWN_MODEL, ALREADY_EXISTS, Task 5부터 NOT_IN_DELIVERY_NOTE, NOT_FOUND, INVALID_STATE, RETURNED)를 입력 순서대로 준다. 이미 있는 시리얼을 다시 찍어도 ALREADY_EXISTS로 끝나 재처리가 안전하다.
  3. 행마다 별도 트랜잭션: 부분 반영은 같지만 커밋이 N번이고, 중간에 죽으면 어디까지 했는지 알기 어렵다.
- 결정: 2, 유효한 행 전체는 **한 트랜잭션**. 조회는 행 수와 상관없이 2번(모델, 기존 시리얼). INSERT는 시리얼 순서로 만든다 — 같은 시리얼을 넣는 트랜잭션들이 unique 키를 같은 순서로 잡아 엇갈려 기다리지 않게.
- 동시성: 조회와 INSERT 사이에 다른 요청이 같은 시리얼을 넣으면 unique 위반 → 트랜잭션 전체를 다시 한다(그때는 ALREADY_EXISTS). 처음엔 1회 재시도였고 리뷰 반영에서 데드락 포함 3번으로 바꿨다(아래 "INSERT 순서와 재시도"). Step 5에서 재시도(`attempts = 2`)를 `1`로 바꾸자 겹친 동시 등록 테스트가 3회 모두 `UniqueConstraintViolationException: Duplicate entry 'CO-0021' for key 'terminal.terminal_serial_no_unique'`로 실패했고, 되돌리니 통과했다.
- 낙관적 락 충돌(Task 5 RETURN_IN에서 생긴다): 행별로 다시 하지 않고 **박스 전체 409**(VERSION_CONFLICT). 저장된 결과가 없으니 같은 scanId로 다시 보내면 새로 처리된다. 행별로 하려면 충돌 행을 빼고 다시 flush해야 하는데 MikroORM은 실패한 flush 뒤 Unit of Work를 믿기 어렵다.
- 결과·대가: 한 요청의 행 수에 상한이 필요하다(스캔 500, 엑셀 5000). 트랜잭션이 커지면 락 시간이 길어진다 → 실험 0006에서 잰다.
- 숫자(Step 4, 3회 같음): 10행 요청은 전체 쿼리 8개·select 3개, 200행 요청도 전체 8개·select 3개. 겹친 동시 등록(A 40행, B 40행, 20행 겹침)은 3회 모두 A 생성 40, B 생성 20.
- 쿼리 수가 늘어나는 곳: 조회는 행 수와 상관없이 늘 2번(모델, 기존 시리얼). INSERT와 INSERT 뒤 version 다시 읽기(`select id, version`)는 batchSize 300 단위라 ⌈N/300⌉번이다. 200행의 8개는 begin, 조회 2, 단말기 INSERT 1, version select 1, 이력 INSERT 1, Outbox INSERT 1, commit이다. 5000행이면 계산상 테이블마다 INSERT 17번(단말기는 version select도 17번)이다. 5000행 숫자는 잰 값이 아니라 계산이다. 한 트랜잭션이 커지면 커밋까지 락을 쥐는 시간도 길어진다 → 실험 0006에서 잰다.
- 중복 행 정책: 같은 요청에 같은 시리얼이 두 번 나오면 **첫 행이 결정한다**. 두 번째부터는 DUPLICATE_IN_REQUEST이고, 첫 행이 뒤에서 UNKNOWN_MODEL·ALREADY_EXISTS가 되어도 바뀌지 않는다(뒤 행에 맞는 모델 코드가 있어도 만들지 않는다). 형식이 틀린 행(INVALID_FORMAT)은 중복 판단에 넣지 않는다. 운영자는 결과를 보고 그 시리얼만 다시 보내면 된다. 뒤 행에 자리를 넘기는 방식은 결과가 행 순서에 따라 달라져 설명하기 어려워 버렸다.
- 입력 정규화: 엔진 입구(`normalizeRows`)에서 `serialNo`·`modelCode`를 `String(x ?? '').trim()`으로 맞춘다. 엑셀·JSON에서 숫자 `12345678`과 문자열 `'12345678'`이 섞여 오면 둘째가 DUPLICATE_IN_REQUEST다. 빈 시리얼은 INVALID_FORMAT, 빈 모델 코드는 조회 없이 UNKNOWN_MODEL. 고치기 전에는 숫자 시리얼이 오면 `ValidationError: Trying to set Terminal.serialNo of type 'string' to 12345678 of type 'number'`로 요청 전체가 실패했다(리뷰는 unique 위반을 예상했는데, 실제로는 그 전에 MikroORM 타입 검사에서 멈췄다).

## INSERT 순서와 재시도 (Task 4 리뷰 반영, 2026-10-23)

- INSERT 정렬이 필요한가: 정렬(시리얼 오름차순으로 엔티티를 만든다)을 잠깐 빼고, 겹친 두 요청을 반대 순서(A 오름차순, B 내림차순)로 동시에 보냈다.

  | 크기 | 정렬 있음 | 정렬 없음 |
  |---|---|---|
  | 40행씩, 20행 겹침, 3회 | 3회 통과. 진 쪽은 `Duplicate entry 'RV-0021'` 1번 → 재시도 | 3회 통과, 데드락 없음. 진 쪽은 B의 첫 행 `Duplicate entry 'RV-0040'` → 재시도 |
  | 2000행씩, 1000행 겹침(임시 테스트, 3번 × 3회) | 9번 통과, 데드락 없음 | 9번 모두 한쪽이 `DeadlockException`(1213) |

  40행에서는 데드락이 재현되지 않았다. INSERT 한 문장이 짧아 두 트랜잭션의 INSERT 구간이 거의 겹치지 않기 때문으로 보인다(추정, 시간은 재지 않음). 2000행은 INSERT 문이 7개로 나뉘어 겹칠 시간이 생기고, InnoDB 상태에서 두 트랜잭션이 unique 인덱스 키를 하나씩 X로 쥐고 상대 키의 S를 기다린 것을 확인했다 → troubleshooting/0011. 엑셀 상한(5000행)이 이 크기보다 크므로 정렬은 그대로 둔다. 40행 반대 순서 테스트는 남겼지만 정렬이 없어도 통과하므로 정렬의 회귀 테스트는 아니다.
- 재시도: unique 위반과 데드락(`DeadlockException`)을 다시 한다. 최대 3번, 시도 사이 20~80ms 무작위 대기. 시도마다 새 fork, 새 트랜잭션.
  - 겹친 세 요청(A `0001~0040`, B `0060~0021` 내림차순, C `0011~0050`) 테스트를 먼저 넣었다. 고치기 전 코드(2번, 대기 없음)로는 3회 모두 `UniqueConstraintViolationException: Duplicate entry 'TR3-0041'`로 실패했다. 한 요청이 첫 재시도에서 또 다른 요청에 졌다. 리뷰 지적이 맞았다.
  - 둘을 나눠 봤다(각 3회). 2번 + 무작위 대기: 2회 통과, 1회 실패(`attempt=2 ... 'TR3-0041'`). 3번 + 대기 없음: 3회 통과, 3회 모두 2번째 시도에서 한 번 더 지고 3번째에 성공. 그래서 둘 다 넣었다.
  - 3번 + 대기: 3회 통과(생성 수 A/B/C = 40/20/0, 40/10/10, 40/20/0), 마지막 확인 3회도 통과(40/20/0, 40/10/10, 40/20/0). 각 시리얼은 1번만 만들어졌고 Outbox도 시리얼마다 1건.
  - 정렬을 뺀 채 새 재시도로 2000행 임시 테스트를 1회(3번) 돌리면 통과는 했지만 3번 모두 데드락 → unique 위반 → 3번째 성공이었다. 재시도가 정렬을 대신하지 않는다.
- 보장 범위: 같은 시리얼이 겹치는 동시 요청 **3건까지** 테스트로 확인했다. 더 많으면 3번으로 모자랄 수 있고, 그때는 마지막 예외가 그대로 나간다(지금은 500). 겹친 동시 요청이 더 많아질 수 있는 경로(여러 작업자가 같은 박스를 동시에 스캔 등)가 생기면 409와 "다시 보내 주세요" 안내를 넣는다.
- 다시 볼 조건: 재시도 3번을 다 쓰고 실패한 로그가 나오면, 또는 한 요청 행 수 상한을 바꾸면.
- 갱신(Task 5): RETURN_IN은 TransitionService.transitionMany로 UPDATE 한 번(CASE). 그사이 version이 바뀐 행이 있으면 박스 전체 409, 같은 scanId로 다시 보내면 새로 처리된다.
