# 0021. 입고는 명세 밖 시리얼을 거절한다

- 날짜 / 관련 기능: 2026-10-23 / F6, F10
- 상황: 공장 명세에 없는 시리얼이 박스에 들어 있을 수 있다(세움 골칫거리). 등록하고 표시할지, 거절할지(브리프 권장: 거절).
- 선택지:
  1. 등록하고 "명세 외" 표시: 재고에 출처 불명 단말기가 섞인다. 나중에 반품하려면 상태·이력을 또 만들어야 한다.
  2. **거절(NOT_IN_DELIVERY_NOTE), 결과에만 남김**: 대조 리포트의 unexpected는 ScanBatch 결과에서 구한다. 실물은 창고가 따로 격리한다.
- 결정: 2. 명세에 섞여 온 다른 발주의 시리얼(foreignSerials)은 "명세에 있으니" 받는다 — 공장 번호 체계를 알아야 걸러낼 수 있어 하지 않는다(스펙 9장).
- 명세 받기: 처음 스캔할 때 트랜잭션 밖에서 세움전자에 물어 `purchase_order.delivery_note`에 저장한다(`delivery_note`가 null일 때만 쓰므로 동시에 받아 와도 덮어쓰지 않는다). 다음 박스부터는 다시 받지 않는다.
- 잠금 순서: 입고 트랜잭션은 **발주 행을 FOR UPDATE로 먼저** 잠근다. 단말기 INSERT의 `purchase_order_id` FK 검사가 발주 행에 S 락을 거는데, 그보다 X 락이 먼저여야 같은 발주를 동시에 스캔해도 S→X 데드락이 없다(troubleshooting/0004). 같은 발주의 스캔·마감(Task 7)이 이 잠금에서 줄을 선다. CLOSED도 이 잠금 아래에서 다시 본다.
- 입고 연결: `terminal.purchase_order_id`(nullable FK). 대조에서 입고 수를 DB에서 센다.
- 결과·대가: 같은 발주의 박스는 동시에 들어와도 한 줄로 처리된다(병렬성 없음). 발주 하나에 박스가 수십 개라도 한 박스 처리가 짧아 문제 되지 않을 것으로 본다(잰 값 아님).
- 다시 볼 조건: 공장 시리얼 체계가 정해져 다른 발주 시리얼을 거를 수 있게 되면.

## 리뷰 반영 (2026-10-23)

- 명세 밖 시리얼이 한 요청에 두 번 나오면 둘 다 NOT_IN_DELIVERY_NOTE다(두 번째가 DUPLICATE_IN_REQUEST가 아니다). 명세 검사가 중복 판단(엔진의 `precheckSerials`)보다 먼저라서다. 두 행 모두 등록하지 않는다는 결과는 같고, 운영자에게는 "명세 밖"이 더 중요한 정보라 그대로 둔다.
- 명세 검사는 입구에서 다듬은 시리얼로 한다. 전에는 끝에 공백·`
`이 붙은 시리얼이 형식 검사에서 빠져 명세 검사를 건너뛰고, 엔진이 다듬은 뒤 등록됐다(이 결정을 어긴 버그) → troubleshooting/0012.
- 등록된 행이 0개여도 발주는 RECEIVING이 된다(박스의 모든 행이 명세 밖·형식 오류·이미 있음인 경우). 의도한 동작으로 둔다. RECEIVING은 "입고 스캔이 시작됐다"는 뜻이고, 그 박스의 결과도 ScanBatch에 남아 대조 리포트(Task 7)의 unexpected 출처가 된다. "실제로 한 대라도 들어왔다"를 뜻하게 하려면 등록 수를 보고 바꿔야 하는데, 지금은 그 구분을 쓰는 곳이 없다.

## 리뷰 반영 2 (2026-10-23, Task 7 리뷰)

- 대조 리포트의 말 뜻(`purchase-order.service.ts` reconcile 주석에도 적음):
  - `shortfall = ordered - noted`. 명세가 발주보다 몇 대 적은가. 음수(공장이 더 보냄)일 수 있고 0으로 자르지 않는다.
  - `missing`: 명세에는 있는데 이 발주로 아직 입고되지 않은 시리얼. shortfall과 다르다(shortfall은 명세 자체가 모자란 수, missing은 명세에 있는데 안 들어온 것).
  - 명세에 같은 시리얼이 두 번 들어오는 일은 없다고 본다(공장이 그러지 않는다). 그래도 쉬운 방어라서 `noted`는 서로 다른 시리얼 수, missing 쿼리는 `group by n.serial_no order by min(n.ord)`(처음 나온 자리 순서)로 한 번만 센다. `select distinct … order by n.ord`는 ORDER BY 열이 SELECT 목록에 없어 MySQL이 거절하므로 GROUP BY로 했다. 테스트: 명세를 `[A, B, A]`로 바꿔 넣으면 noted 2, missing `[A, B]`.
- 대조 쿼리 세 개(received count, missing, unexpected)는 한 트랜잭션(REPEATABLE READ, 읽기 전용)에서 돌린다. 따로 돌리면 사이에 입고 박스가 커밋돼 received와 missing이 서로 맞지 않을 수 있다. InnoDB는 트랜잭션의 첫 읽기 시점 스냅숏을 끝까지 쓴다.
- 마감은 명세를 마감 트랜잭션 **전에**(밖에서) 받는다. 전에는 마감을 커밋한 뒤 대조 결과를 만들며 명세를 받았기 때문에, 명세 없는 발주에서 공장이 503이면 "발주는 CLOSED인데 응답은 502"였다. 이제 공장이 실패하면 마감하지 않고 502 PARTNER_ERROR. 이미 마감된 발주는 공장을 부르지 않고 422. 테스트: 명세 없는 발주 + 세움 `error5xxRate: 1` → 502, 발주는 ORDERED 그대로, 다시 0으로 바꾸면 마감 200.
  - 이 테스트를 위해 partners 세움전자의 `error5xxRate`가 납품 명세 조회에도 503을 내게 했다(전에는 발주만). 느림보물류의 `error5xxRate`가 발급·추적 둘 다에 걸리는 것과 같은 방식이다. partners 테스트 1개 추가.
