# 0023. 교체 출고는 한 트랜잭션과 정해진 잠금 순서(단말기 id 오름차순 → 접수)

- 날짜 / 관련 기능: 2026-10-23 / F7(A/S 교체 출고·설치 확인)
- 상황: 교체 출고는 "새 단말기 배정·출고 + 고장 단말기 회수 요청 + 운송장 + 접수 상태"를 함께 바꾼다(설계안 F7 "한 건으로 처리"). 두 단말기 행과 접수 행을 잠그므로, 여러 교체 요청이나 접수·설치 확인이 동시에 오면 잠금 순서가 엇갈릴 수 있다.
- 선택지(묶음):
  1. 단계마다 따로 커밋: 중간에 실패하면 교체 단말기만 SHIPPED인 상태가 남는다.
  2. **한 트랜잭션**: 전부 아니면 전무. 외부 호출(운송장 발급)은 트랜잭션 밖에서 먼저 한다(decisions/0012).
- 선택지(잠금):
  1. 잠금 없이 낙관적 락만: 경합에서 진 쪽이 409. 순서 문제는 UPDATE 순서에 숨는다.
  2. **행마다 FOR UPDATE를 정해진 순서로 명시**: 순서가 코드에 드러나고, 기다린 쪽은 최신 커밋 값을 보고 규칙 위반(422)으로 끝난다.
  3. 한 문장 `WHERE id IN (…) ORDER BY id FOR UPDATE`: 같은 효과지만 순서가 실행 계획에 숨는다.
- 결정: 한 트랜잭션 + 잠금 2. 순서 규칙은 아래와 같다.
  - **단말기 행을 먼저, 접수 행은 그다음.** 단말기가 둘이면 id 오름차순으로 한 행씩 잠근다.
  - 같은 트랜잭션에서 단말기를 잠그기 전에 접수 잠금(`lockOpen`)을 부르지 않는다. 단말기 id를 알아야 하면 접수를 **잠그지 않고** 먼저 읽는다(교체 출고는 사전 확인에서, 설치 확인은 트랜잭션 전에 `get`으로 교체 단말기 id를 얻는다). 접수를 잠근 뒤 상태(OPEN·REPLACING)를 다시 본다. 고장 단말기는 접수가 생길 때 정해지고, 교체 단말기는 REPLACING이 된 뒤 바뀌지 않으므로 잠그기 전에 읽은 id가 낡을 일은 없다.
  - 접수 생성(Task 8, `ServiceTicketService.open`)도 단말기 행을 먼저 잠근다. "단말기당 열린 접수는 하나" 규칙은 접수 생성이 **그 트랜잭션의 어떤 읽기보다 먼저** 단말기 행을 잠그는 데 기댄다. 잠근 뒤에 센 열린 접수 수라야 같은 단말기의 다른 접수 생성과 줄을 선다. 이 순서를 바꾸면 규칙이 깨진다.
  - 원격 점검(`remoteCheck`)은 접수 행만 잠그고 단말기를 잠그지 않으므로 규칙과 부딪히지 않는다.
  - 일반 규칙: "부모 행 X 락을 자식 INSERT보다 먼저(troubleshooting/0004, decisions/0021), 여러 행은 정해진 순서로".
- 계획과 다르게 한 것: 계획 코드는 교체 출고에서 접수 행 → 단말기, 설치 확인에서 접수 → 교체 단말기 순으로 잠갔다. Task 8 리뷰에서 순서를 "단말기 먼저"로 하나로 정하자는 지적이 있어 두 곳을 바꿨다. 접수 → 단말기 순서를 쓰는 트랜잭션과 단말기 → 접수 순서를 쓰는 트랜잭션(접수 생성처럼 단말기를 먼저 잡는 것)이 함께 있으면 서로 상대가 쥔 행을 기다리는 순환이 생길 수 있다. 지금 코드에서 실제로 순환이 나는 경로를 재현하지는 않았다(예방으로 정한 규칙).
- 출처: 교체 단말기는 ALLOCATION·SHIPMENT(교체도 배정·출고), 고장 단말기 회수 요청과 설치 확인은 SERVICE(decisions/0017).
- 실험용 옵션: `replace(id, cmd, actor, { lockOrder })`의 `'faulty-first'`(고장 단말기 → 교체 단말기)는 실험 0007 전용이고 HTTP는 늘 `'id-asc'`다. 두 경우 모두 접수 행은 단말기 뒤에 잠근다.
- 결과·대가(알려진 한계): 사전 확인은 트랜잭션 밖이라 동시 요청은 모두 통과하고 모두 운송장을 발급받는다. 진 요청 수만큼 고아 운송장이 남는다. 같은 교체 단말기 동시 2건 테스트에서 3회 모두 운송장 발급 2, 응답 [201, 422], 진 쪽 코드 `INVALID_TRANSITION`(교체 단말기 행 잠금을 기다린 뒤 최신 상태 SHIPPED를 봄). 교체 단말기를 먼저 "예약"하는 단계를 두면 고아가 줄지만 상태가 하나 더 생긴다 → Day 7 고아 정리와 함께 본다. 실험 0007에서 잰다.
- 테스트(`test/replacement.e2e.spec.ts`): 전체 흐름(교체 → 배송 완료 → 설치 → 회수 스캔), 사전 확인 실패 시 운송장 0, 트랜잭션 중 실패 시 전부 롤백(운송장 1장 고아), 같은 교체 단말기 동시 2건 → [201, 422].
- 리뷰 메모(2026-10-23, Task 9 리뷰):
  - "id 오름차순" 규칙은 행 잠금끼리의 순환만 막는다. 교체 출고 2건이 서로 다른 단말기를 쓰면 단말기 행은 겹치지 않는데도, 운송장 저장(`recordShipment`)의 `WHERE terminal_id=?` UPDATE가 같은 인덱스 gap을 잡아 INSERT끼리 데드락이 났다(troubleshooting/0014, 5회 중 5회 재현). 행이 아니라 gap이 공유 자원이라 잠금 순서로는 막을 수 없다. 이전 운송장 갱신을 PK 갱신으로 바꿔 해결했다(decisions/0018).
  - 실험 0007의 'faulty-first' 변형은 데드락을 만들기 어려울 것이다(추정, 아직 재지 않음). 순환이 생기려면 한 트랜잭션은 A → B, 다른 트랜잭션은 B → A 순서로 잠가야 하는데, 'faulty-first'는 역할 순서(고장 → 교체)다. 한 단말기가 동시에 고장 단말기(IN_SERVICE, 열린 접수가 있음)이면서 교체 단말기(IN_STOCK)일 수는 없으므로, 두 교체 요청이 같은 두 단말기를 서로 반대 역할로 잡는 경우가 없다. 역할 순서 자체가 이미 일관된 순서다. 그래서 실험 0007은 이 변형에서 "순환 없음"을 기대값으로 두고, 데드락이 나면 그것을 따로 기록한다.
- 다시 볼 조건: 접수와 단말기를 함께 잠그는 새 작업이 생길 때(이 순서를 따르는지 확인), 고아 운송장이 실제 비용이 될 때.
