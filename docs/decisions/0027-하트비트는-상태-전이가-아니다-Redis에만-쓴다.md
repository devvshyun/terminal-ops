# 0027. 하트비트는 상태 전이가 아니다, Redis에만 쓴다

- 날짜 / 관련 기능: 2026-10-23 / F8
- 상황: 설치된 단말기 수천 대가 30초마다 하트비트를 보낸다(5,000대면 초당 약 170건). 운영자가 알고 싶은 것은 "지금 살아 있나, 마지막으로 언제 봤나, 펌웨어 버전"이고, 과거 하트비트 하나하나는 의미가 없다.
- 선택지(모델):
  1. 상태 전이로 다루기(IN_SERVICE ↔ OFFLINE 같은 상태 추가) — 하트비트마다 전이 서비스(행 잠금, version, 이력, Outbox)를 거친다. 이력이 하트비트로 뒤덮이고, 접속 끊김이 lifecycle(배송·회수)과 섞인다. enum ALTER도 필요.
  2. **파생 상태**: lifecycle과 별개로 "마지막 하트비트 시각·버전"만 유지하고, 온라인 여부는 시각으로 계산한다. 전이·이력·Outbox를 거치지 않는다.
- 선택지(저장소):
  1. 하트비트마다 MySQL UPSERT — 초당 수백 건의 행 쓰기(redo·binlog·잠금). 실험 0008에서 숫자로 비교한다(Task 9의 실험용 경로).
  2. **Redis ZSET(serialNo → 마지막 시각 ms) + HASH(serialNo → 버전)** — 쓰기는 메모리 명령 2개, 최신값만 남는다. ZSET이라 "기준보다 오래된 단말기"를 범위 조회(ZRANGEBYSCORE)로 한 번에 찾는다. MySQL에는 바뀐 것(Task 5 판정)과 주기 스냅샷만.
- 결정: 모델 2 + 저장소 2. 왜 MySQL이 아니라 Redis인가(CLAUDE.md 원칙): 쓰기가 많고 최신값만 의미 있으며 잃어도 다음 하트비트(30초)가 다시 채운다(설계안 4장 Redis ②).
- 세부: lastSeen은 **서버 시계**(단말기 시계를 믿지 않는다, `sentAt` 받지 않음). 단건 엔드포인트 없음(항목 1개짜리 묶음). 묶음 안의 행이 틀려도 묶음 전체를 400으로 버리지 않고 행별 결과(decisions/0019와 같은 생각). 작업자 헤더 대신 형식 검사, 단말기 인증은 미룸(decisions/0001과 같은 이유). Redis 왕복은 묶음당 2번.
- 결과·대가: Redis가 원본이라 Redis가 죽으면 하트비트가 500이다(우회하지 않음). Redis 데이터를 잃으면 lastSeen이 비고 다음 하트비트까지 접속 상태가 MySQL 스냅샷 값으로 보인다.
- 다시 볼 조건: 하트비트에 상태 정보(배터리·오류 코드)가 붙어 이력이 필요해지면, 단말기 수가 수십만이 되어 ZSET 하나가 커지면(키 나누기).
- 갱신(Task 9): 실험 0008 — 5,000대·주기 5초(초당 1,000건) 30초 동안 Redis 경로 MySQL 쓰기 30문장(스냅샷 3회 × 10, 하트비트 수와 무관) 대 하트비트마다 MySQL 묶음 300문장·단건 30,000문장(redo 2.3배·15.8배), 묶음 p95 32~34ms 대 64~96ms, 데드락 0. 최대 처리량(동시 16 닫힌 루프) 단건 Redis 약 5,400/s 대 MySQL 약 1,370/s, 묶음 약 116,000/s 대 58,000/s. 운영 기본은 redis 그대로. 실험용 `HEARTBEAT_WRITE_MODE=mysql`(HeartbeatService.writeMode)은 비교용으로만 남긴다(decisions/0024의 enqueue 'each'와 같은 처리).
- 갱신(Task 10 뒤 fix, 0008 리뷰): `HEARTBEAT_WRITE_MODE=mysql`은 Redis lastSeen·firmware를 비워 둬서 운영에 켜면 오프라인 판정(lastSeen에 남은 옛 값은 살아 있어도 오프라인으로, 값이 없는 단말기는 판정 대상에서 빠짐)·스냅샷·접속 상태 조회(redis 경로)가 하트비트를 보지 못한다. 그래서 `NODE_ENV=production`이면 env를 읽을 때 던져 서버가 뜨지 않고(`resolveHeartbeatWriteMode`), 그 밖에서는 `HeartbeatService.onModuleInit`이 `Logger.warn`을 남긴다. `.env.example`에 경고 한 줄. 운영 거절을 경고만으로 두지 않은 이유: 로그 한 줄은 지나치기 쉽고, 이 모드는 운영에서 쓸 이유가 없다.
