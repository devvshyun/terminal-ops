# 0031. 배포 판단은 배포 행 먼저, 보고는 대상 행만

- 날짜 / 관련 기능: 2026-10-23 / F8 (Day 4 Task 7)
- 상황: 배포 판단(단계 넘기기·자동 중단·시간 초과)과 단말기 수백 대의 보고가 동시에 일어난다. 판단은 "지금 단계의 통계"를 보고 배포 행과 대상 행을 함께 바꾸고, 보고는 대상 행 하나를 바꾼다. 판단이 여러 프로세스에서 동시에 돌 수도 있다.
- 선택지(잠금):
  1. 보고도 배포 행을 FOR UPDATE. 통계는 정확하다. 하지만 보고 수백 건이 배포 행 하나에서 줄을 선다. 판단이 대상 행을 바꾸는 동안 서로 반대 순서(대상 → 배포 / 배포 → 대상)로 기다려 순환이 생길 수 있다.
  2. **판단: 배포 행 FOR UPDATE → 대상 행(PK 갱신·INSERT). 보고: 대상 행 하나만 PK + 상태 조건 UPDATE(배포 행을 잠그지 않음).** 보고는 배포 행을 기다리지 않는다. 보고가 쥐는 자원은 대상 행 하나라 판단(배포 행 + 여러 대상 행)과 순환 대기를 만들 수 없다.
  3. 판단도 잠금 없이 낙관적 락(version). 충돌하면 다시 해야 하고, 여러 프로세스가 같은 단계를 두 번 넘길 위험을 따로 확인해야 한다.
- 결정: 2. 판단끼리는 배포 행 잠금에서 줄을 선다. 뒤에 온 쪽은 앞쪽이 바꾼 단계(새 대상은 OFFERED, 결과 0)를 보고 기다린다. 그래서 주기 작업에 Redis 잠금이 필요 없다. 테스트: 배포 행 FOR UPDATE를 쥔 트랜잭션이 있어도 보고 200, 9ms.
- 대상 행 여러 개 갱신(TIMED_OUT, 재개의 offered_at)은 잠그지 않고 id를 읽은 뒤 `id IN (…) AND status='OFFERED'`(PK, id 순)로 한다. `WHERE rollout_id=? AND stage=? AND status='OFFERED'` 같은 보조 인덱스 범위 UPDATE는 RR에서 gap 락을 건다(troubleshooting/0014). 상태 조건이 있어서 그사이 보고된 행은 덮어쓰지 않는다.
- 판단이 읽는 통계는 배포 행을 잠근 뒤 첫 일반 SELECT로 정해지는 스냅숏이다(FOR UPDATE는 스냅숏을 만들지 않는다). 그 뒤 커밋된 보고는 다음 판단이 본다.
  - 정정(Task 7 리뷰, troubleshooting/0019): "다음 판단이 본다"가 늘 맞지는 않았다. TIMED_OUT UPDATE는 지금 값(current read)을 봐서 스냅숏 뒤에 FAILED로 바뀐 대상을 건너뛰는데, 통계(스냅숏)는 그 대상을 OFFERED로 세고 남은 대상에서는 빠져 있었다 → 그 실패가 어디에도 세이지 않고 단계가 넘어갔다. 이제 바뀐 행 수(`changed`)가 고른 수보다 적으면 **이번 주기는 판단하지 않고 WAITING**(`timedOut = changed`)으로 둔다. 바뀐 TIMED_OUT은 커밋한다. 다음 주기는 새 스냅숏이라 그 보고를 센다. 버린 것: 통계를 트랜잭션 안에서 locking read(FOR SHARE)로 다시 세기 — 대상 행 범위에 S 락·gap 락이 걸려 보고를 막는다(이 결정의 2번을 깬다). 같은 이유로 배포 만들기의 모델 행 FOR UPDATE는 트랜잭션의 첫 문장이어야 한다(코드 주석, Task 6 리뷰).
- 실패율: 지금 단계의 (FAILED + TIMED_OUT) / (SUCCEEDED + FAILED + TIMED_OUT). 시간 초과도 실패로 센다(아무도 성공하지 않았는데 다음 단계로 가지 않게). 자동 중단은 기준을 넘고, 결과가 minSamples 이상이거나 단계가 다 끝났을 때(작은 단계) 한다. 중단하면 남은 OFFERED는 그대로 둔다(늦은 보고를 받아 영향 범위를 센다). 제안만 모두 내린다.
- 운영에서 빠진 단말기(Task 6 리뷰): 제한 시간이 지난 OFFERED 대상 중 단말기가 지금 IN_SERVICE가 아니면(회수 요청 등) **TIMED_OUT으로 바꾸지 않고 OFFERED로 남긴다.** 실패율의 분자·분모와 "남은 대상"에서 빼고, 제안만 내린다. 응답할 수 없는 단말기를 실패로 세면 회수가 몰린 날 배포가 멈춘다.
  - 고른 이유: 새 상태(EXCLUDED 등)는 enum ALTER 마이그레이션이 필요하다(troubleshooting/0005의 down 문제도 따라온다). 중단된 배포도 이미 OFFERED를 남기므로 "끝난 배포의 OFFERED = 보고 없이 끝난 대상"으로 읽으면 뜻이 같다. 늦게라도 보고가 오면 그대로 받는다.
  - 판단 시점: 제한 시간이 지났을 때의 단말기 상태로 정한다. 제한 시간 안에 운영에서 빠졌다가 돌아오면 보통 대상과 같다.
  - 대가: 단계별 통계(`stageStats`)의 offered에 이 대상들이 남는다(제외 수를 따로 보여 주지 않음). 마지막 단계면 COMPLETED와 함께 앞 단계의 제외 대상 제안도 모두 내린다.
  - 테스트: 2대 중 1대 성공, 1대는 RETURN_REQUESTED, 기준 20%·minSamples 1, 제한 시간 지남 → ADVANCED, timedOut 0, 그 대상 OFFERED, 제안 없음(빼지 않으면 1/2 = 50% → ABORTED).
- 이미 목표 버전인 대상(최종 리뷰, troubleshooting/0021): 제한 시간이 지난 운영 중 OFFERED 대상은 TIMED_OUT으로 바꾸기 전에 Redis `hb:fw`(하트비트가 남긴 지금 버전)를 HMGET으로 읽는다. 목표 버전과 같으면 **SUCCEEDED**(`reported_version` = 목표 버전, `reported_at` = 판단 시각 now)로, 나머지만 TIMED_OUT으로 바꾼다. 둘 다 PK + `status='OFFERED'` 조건 UPDATE이고, 두 UPDATE가 바꾼 행 수의 합이 고른 수보다 적으면 앞의 규칙대로 이번 주기는 WAITING이다. 결과의 `timedOut`은 TIMED_OUT으로 바뀐 수만 센다.
  - 왜 필요한가: 하트비트는 이미 그 버전이면 update를 싣지 않고, 단말기도 보고하지 않는다. 그 대상은 영영 OFFERED라 제한 시간 뒤 실패로 세졌다(같은 버전 재배포, 설치 뒤 보고 유실이면 거짓 자동 중단).
  - 트랜잭션 안의 Redis 읽기: "트랜잭션 안에서 외부 저장소를 기다리지 않는다"의 예외다. 배포 행 잠금을 쥔 채 Redis 왕복 1번(HMGET)을 한다. 제한 시간이 지난 대상이 있는 주기에만 한다. 버린 것: 트랜잭션 밖에서 먼저 읽기 — 어느 대상이 제한 시간이 지났는지는 잠근 뒤에 읽어야 정해지므로, 밖에서 읽으려면 대상 조회를 한 번 더 하고 그 사이 새로 지난 대상은 관측 없이 TIMED_OUT이 된다.
  - 버린 것(선택): 단계에 들어갈 때 `device_connectivity.firmware_version`이 목표 버전인 단말기를 대상에서 빼기. 그 값은 스냅샷(기본 60초)이라 늦고, 빼면 그 단말기들이 배포 통계에 아예 나오지 않는다(모수가 바뀜). 관측 성공은 대상으로 세고 결과도 남는다.
  - 대가: 이미 목표 버전인 대상은 단계 제한 시간(기본 10분)이 지나야 성공으로 세진다. 같은 버전 재배포는 단계마다 제한 시간만큼 걸린다. 보고와 달리 Redis 펌웨어 버전이 "하트비트가 보낸 값"이라 단말기가 거짓 버전을 보내면 성공으로 센다(단말기 인증 없음, 남은 문제).
  - 테스트: 2대 중 1대는 하트비트로 목표 버전, 1대는 성공 보고, 기준 20%·minSamples 1, 제한 시간 지남 → ADVANCED, timedOut 0, 그 대상 SUCCEEDED·reported_version 목표 버전(고치기 전 ABORTED, timedOut 1). 목표 버전이 아닌 하트비트면 그대로 TIMED_OUT.
- 끝난 시각: `finish`의 `finished_at`은 판단 시각(`control(id, now)`의 now)이다(운영자 중단은 요청 시각). 시각을 넣어 판단하는 테스트·실험에서 끝난 시각이 판단과 어긋나지 않게(최종 리뷰 Minor).
- Redis 제안 걸기·내리기는 커밋 뒤에 한다(트랜잭션 안에서 외부 저장소를 기다리지 않는다). 대신 **판단 job이 매 주기 Redis를 MySQL에 다시 맞춘다**(Task 6 리뷰):
  - 진행 중(RUNNING) 배포: control이 계속 진행할 때(WAITING·ADVANCED) 남은 대상(제한 시간 안의 OFFERED, 새 단계면 새 대상)의 제안을 매번 다시 건다. HSET은 같은 값이면 그대로라 멱등이다.
  - 멈춤·끝남·없는 배포: `controlAll`이 끝에 Redis `fw:offers`를 HSCAN으로 훑어 배포 id별로 모은다. RUNNING이 아닌 배포의 제안을 배포 id 비교 Lua로 내린다. 끝난 배포 목록이 아니라 Redis를 훑으므로, 끝난 배포가 쌓여도 일은 지금 걸린 제안 수만큼이다.
  - 고치는 것: (a) 커밋한 뒤 Redis에 걸기 전에 죽은 경우(새 단계 대상에 제안이 없음) → 다음 주기(5초)에 걸린다. (b) 커밋 뒤 Redis 작업의 순서가 뒤바뀐 경우(멈춤의 내리기 뒤에 판단의 다시 걸기가 도착, 재개의 걸기 뒤에 맞추기의 내리기가 도착 등) → 배포 상태(MySQL)가 정답이라, 어느 쪽으로 어긋나도 다음 주기에 맞춰진다.
  - 남는 것: 맞추기 자체도 커밋(또는 상태 읽기) 뒤의 Redis 작업이라 그 주기 안에서는 틀릴 수 있다.
  - 정정(Task 7 리뷰, troubleshooting/0019): 처음에는 "판단이 스냅숏을 읽은 뒤 보고가 커밋되고 제안을 내렸는데, 판단의 다시 걸기가 그 뒤에 도착해 보고한 단말기에 제안이 다시 걸리는 경우"를 남겨 두었다(단말기가 다시 보고하면 내려진다고 봄). 하지만 실패한 단말기가 같은 버전을 다시 받아 설치를 되풀이하게 된다. 이제 **걸기 뒤에 그 대상 행들을 PK로 다시 읽어(autocommit, 지금 값) OFFERED가 아닌 것의 제안을 배포 id 비교 Lua로 내린다**(`publishOffers`, 만들기·재개·판단 모두). 보고는 커밋한 뒤에 내리므로 "걸기 → 다시 읽기"면 둘 중 하나가 꼭 지운다. 걱정했던 반대 경합(늦은 내리기가 새 단계 제안을 지움)은 생기지 않는다: 지우는 대상은 "이 배포의 이 대상 행이 OFFERED가 아님"인데, 대상 행은 OFFERED로 돌아오지 않고 한 배포에 단말기는 한 번만 대상이다. 대가: 걸 때마다 대상 수만큼 PK IN SELECT 한 번(1,000개씩).
  - 시간 초과를 "다시 건 뒤"로 미루지 않았다(리뷰가 물은 것). 제안이 빠진 시간은 판단 주기(5초) 하나로 줄었고, 기본 제한 시간은 10분이다. 미루려면 대상마다 "마지막으로 건 시각"을 따로 가져야 한다(열 추가, 또는 트랜잭션 안에서 Redis 읽기). 판단 job이 제한 시간보다 오래 멈춰 있었고 그 사이 제안도 빠졌을 때만 문제가 된다. 그 경우는 다시 볼 조건에 둔다.
- 판단 job의 오류 격리(Task 7 리뷰): `controlAll`은 배포마다 try/catch로 판단한다. 한 배포가 실패하면(데드락, Redis 오류 등) 로그를 남기고 결과 `ERROR`(stage -1, `error`)로 두고 다음 배포를 판단한다. `withdrawStaleOffers`는 finally에서 늘 돈다. 실패한 배포는 다음 주기에 다시 판단한다(배포 행 잠금으로 줄을 서므로 다시 해도 안전).
- 단계 대상 INSERT 순서: 고르기는 CRC32 순 그대로, INSERT(FK 검사의 단말기 행 S 락)는 단말기 id 순으로 한다. 다른 경로들이 id 순으로 잠그는 것과 순서를 맞춰 교착 가능성을 줄인다(재지 않음, 교착을 본 것은 아님). 대상 행 id 순이 CRC32 순과 달라졌다(테스트 하나를 집합 비교로 고침).
- 그 밖(Task 7 리뷰 Minor): 하트비트가 이미 제안 버전을 보내면 update를 싣지 않는다(설치 뒤 보고 전 하트비트). 보고 UPDATE가 0행이면 지금 상태를 다시 읽어 돌려준다. TIMED_OUT 뒤에 온 성공 보고는 Redis 펌웨어 버전을 바꾸지 않는다(다음 하트비트가 맞춤, 코드 주석). `OfferStore.byRollout`은 깨진 값(JSON 아님·rolloutId 없음)을 경고 로그와 함께 건너뛴다(값은 남는다). 제안 내리기 Lua도 같은 규칙으로 `pcall(cjson.decode, v)`가 실패하거나 객체가 아니면 건너뛴다(최종 리뷰 Minor, 고치기 전에는 깨진 값 하나에 `ReplyError`로 묶음 전체가 실패).
- 결과·대가:
  - 판단 주기(5초) + 보고 지연만큼 단계 전환이 늦다(실험 0009). 실패율은 단계마다 새로 센다(앞 단계의 실패는 다음 단계 판단에 들어가지 않는다).
  - 판단 job이 주기마다 남은 대상 수만큼 HSET을 한다(수천 대면 수천 필드, pipeline 한 번에 1,000개씩). 하트비트 HMGET과 같은 HASH라 지금 규모에서는 문제가 아니다(재지 않음).
  - 원시 SQL로 읽은 datetime은 UTC 글자다 → `fromDbDatetime`(troubleshooting/0016).
- 다시 볼 조건: 보고가 초당 수천 건이 되어 판단의 통계 쿼리(`group by stage, status`)가 무거워질 때(카운터 테이블). 단계 사이에 운영자 승인이 필요해질 때. 판단 job이 제한 시간보다 오래 멈출 수 있는 운영 환경일 때(시간 초과를 "다시 건 뒤"부터 세기). 대상이 수만 대가 되어 주기마다 다시 거는 HSET이 무거워질 때(바뀐 것만 걸기).
- 갱신(Task 10): 실험 0009 — 실패율 0% 1,000대 3단계 완료 9.6~9.7초(전환 3.7·6.4초), 30%는 2.1초에 1단계에서 자동 중단(결과 40~41건 중 실패 10~11), 끝까지 영향 100대(1단계 전부, 성공 71·실패 29 — 한 단계 대상은 같은 하트비트 주기에 지시를 받아 단계 안의 중단은 영향을 줄이지 못함), 중단 뒤 제안 0·새 지시 0·직접 하트비트 update 0, lock_deadlocks 증가 0(판단 0.5초, 3번).
