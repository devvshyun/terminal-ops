# 0033. VAN 등록 대조는 커서 수집 → 스테이징 → SQL 비교 → 재검증으로 한다

- 날짜 / 관련 기능: 2026-10-26 / F9
- 상황: 브릿지VAN이 들고 있는 등록 목록(수만 건)을 우리 DB와 맞춰 봐야 한다. 목록은 페이지 API로만 받을 수 있고, 받는 동안에도 VAN 쪽이 바뀐다.
- 페이지 방식:
  1. offset/limit — 페이지 사이 앞쪽에 등록이 생기면 다음 페이지가 밀려 같은 등록을 두 번 받고, 지워지면 하나를 건너뛴다.
  2. **커서(키셋, 마지막 tid 다음부터)** — 앞쪽 변경에 밀리지 않는다(partners 테스트 "앞에 하나 생겨도 VT-0011부터"). 지나간 자리에 생긴 등록은 이번 스캔에 없고 다음 스캔이 본다.
  - → 2. 커서는 불투명 글자로 받아 그대로 돌려준다.
- 어디서 비교하나:
  1. 메모리(앱이 목록과 우리 단말기를 다 들고 비교) — 5만 행 두 벌을 앱에 올린다.
  2. JSON_TABLE(F10처럼 JSON 한 덩어리를 SQL로 펼침) — 수만 건 한 문장 파라미터가 커지고 페이지마다 나눠 넣을 수 없다.
  3. **MySQL 스테이징 테이블 + SQL 집합 비교** — 페이지마다 한 문장씩 쌓고, 비교는 인덱스(PK (run_id, serial_no), terminal.serial_no unique)를 탄다. 실행계획은 실험 0011, 시간은 실험 0012.
  - → 3.
- 스테이징 설계: PK (run_id, serial_no)(한 실행의 행이 클러스터 인덱스에 모임), FK 없음(수만 행 INSERT가 실행 행에 S 락을 걸지 않게), 정리는 `where run_id = ? limit 5000` 반복(PK 앞부분 범위라 보조 인덱스 gap 락 걱정이 없음, troubleshooting/0014), 한 실행 안에서 같은 시리얼이 두 번 오면 나중 값.
- 재시도:
  1. BullMQ job 재시도 — 수백 페이지 중 하나가 실패하면 처음부터.
  2. **호출마다 `withPartnerRetry`(5번, 429 Retry-After, 그 밖 지수 백오프)** — 그 페이지만. 다 써도 실패면 실행 FAILED(이유)로 남기고 job은 끝낸다(attempts 1). 규칙은 택배 추적과 같은 `partnerBackoffMs`(decisions/0014).
  - → 2.
- 진행 중 실행은 하나:
  1. Redis 잠금 — 실행이 수 분이라 TTL을 정하기 어렵고, 잠금이 사라져도 DB에는 RUNNING이 남는다.
  2. **실행 행의 unique(생성 열 running_key)** — 상태가 DB 한 곳에 있다. MikroORM 부분 unique(`where: { status: 'RUNNING' }`)는 MySQL이 식에 `_utf8mb4` 글자 집합을 붙여 저장해 `db:migration:check`가 늘 다르다고 해서(사전 검증) 생성 열로 했다.
  3. 멈춘 실행: 워커가 죽으면 RUNNING이 남는다 → 다음 시작이 VAN_RUN_STALE_MS(1시간) 넘은 것을 FAILED로.
  - → 2와 3을 함께. 시작이 unique 위반이면 409 `VAN_RECONCILIATION_RUNNING`.
- 큐: report 큐를 새로 만든다(concurrency 1). device 큐(짧은 job, active 갱신·판정)에 수 초~수 분짜리 일을 넣지 않는다(experiments/0010의 줄서기).
- 결과·대가: 실행 하나가 끝날 때까지 다음 실행(수동·주기)은 409·건너뜀. 수집은 자동 커밋이라 수집 도중의 스테이징은 반쪽일 수 있다(같은 실행을 다시 하면 지우고 처음부터).
- 다시 볼 조건: 등록이 수십만 건이 되어 수집이 길어질 때(페이지 크기·동시 페이지), VAN이 스냅샷 커서(일관된 시점)를 줄 때.
- 이 Task(3)에서 한 것: 실행 행·스테이징·커서 수집·한 job 안의 재시도·report 큐. 비교·재검증·확정은 Task 4가 이 기록에 보탠다.
