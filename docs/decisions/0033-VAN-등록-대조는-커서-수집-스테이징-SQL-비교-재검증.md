# 0033. VAN 등록 대조는 커서 수집 → 스테이징 → SQL 비교 → 재검증으로 한다

- 날짜 / 관련 기능: 2026-10-26 / F9
- 상황: 브릿지VAN이 들고 있는 등록 목록(수만 건)을 우리 DB와 맞춰 봐야 한다. 목록은 페이지 API로만 받을 수 있고, 받는 동안에도 VAN 쪽이 바뀐다.
- 페이지 방식:
  1. offset/limit — 페이지 사이 앞쪽에 등록이 생기면 다음 페이지가 밀려 같은 등록을 두 번 받고, 지워지면 하나를 건너뛴다.
  2. **커서(키셋, 마지막 tid 다음부터)** — 앞쪽 변경에 밀리지 않는다(partners 테스트 "앞에 하나 생겨도 VT-0011부터"). 지나간 자리에 생긴 등록은 이번 스캔에 없고 다음 스캔이 본다.
  - → 2. 커서는 불투명 글자로 받아 그대로 돌려준다.
- 어디서 비교하나:
  1. 메모리(앱이 목록과 우리 단말기를 다 들고 비교) — 5만 행 두 벌을 앱에 올린다.
  2. JSON_TABLE(F10처럼 JSON 한 덩어리를 SQL로 펼침) — 수만 건 한 문장 파라미터가 커지고 페이지마다 나눠 넣을 수 없다.
  3. **MySQL 스테이징 테이블 + SQL 집합 비교** — 페이지마다 한 문장씩 쌓고, 비교는 인덱스(PK (run_id, serial_no), terminal.serial_no unique)를 탄다. 실행계획은 실험 0011, 시간은 실험 0012.
  - → 3.
- 스테이징 설계: PK (run_id, serial_no)(한 실행의 행이 클러스터 인덱스에 모임), FK 없음(수만 행 INSERT가 실행 행에 S 락을 걸지 않게), 정리는 `where run_id = ? limit 5000` 반복(PK 앞부분 범위라 보조 인덱스 gap 락 걱정이 없음, troubleshooting/0014), 한 실행 안에서 같은 시리얼이 두 번 오면 나중 값.
- 재시도:
  1. BullMQ job 재시도 — 수백 페이지 중 하나가 실패하면 처음부터.
  2. **호출마다 `withPartnerRetry`(5번, 429 Retry-After, 그 밖 지수 백오프)** — 그 페이지만. 다 써도 실패면 실행 FAILED(이유)로 남기고 job은 끝낸다(attempts 1). 규칙은 택배 추적과 같은 `partnerBackoffMs`(decisions/0014).
  - → 2.
- 진행 중 실행은 하나:
  1. Redis 잠금 — 실행이 수 분이라 TTL을 정하기 어렵고, 잠금이 사라져도 DB에는 RUNNING이 남는다.
  2. **실행 행의 unique(생성 열 running_key)** — 상태가 DB 한 곳에 있다. MikroORM 부분 unique(`where: { status: 'RUNNING' }`)는 MySQL이 식에 `_utf8mb4` 글자 집합을 붙여 저장해 `db:migration:check`가 늘 다르다고 해서(사전 검증) 생성 열로 했다.
  3. 멈춘 실행: 워커가 죽으면 RUNNING이 남는다 → 다음 시작이 하트비트가 끊긴 것을 FAILED로(아래 "생존 판정", 처음에는 시작 후 1시간이었다).
  - → 2와 3을 함께. 시작이 unique 위반이면 409 `VAN_RECONCILIATION_RUNNING`.
- 큐: report 큐를 새로 만든다(concurrency 1). device 큐(짧은 job, active 갱신·판정)에 수 초~수 분짜리 일을 넣지 않는다(experiments/0010의 줄서기).
- 결과·대가: 실행 하나가 끝날 때까지 다음 실행(수동·주기)은 409·건너뜀. 수집은 자동 커밋이라 수집 도중의 스테이징은 반쪽일 수 있다(같은 실행을 다시 하면 지우고 처음부터).
- 다시 볼 조건: 등록이 수십만 건이 되어 수집이 길어질 때(페이지 크기·동시 페이지), VAN이 스냅샷 커서(일관된 시점)를 줄 때.
- 이 Task(3)에서 한 것: 실행 행·스테이징·커서 수집·한 job 안의 재시도·report 큐. 비교·재검증·확정은 Task 4가 이 기록에 보탠다.

## 갱신(2026-10-26, fix 커밋): 생존 판정은 하트비트로, 끝난 실행은 다시 하지 않는다

- 문제: 멈춘 실행을 "시작한 지 VAN_RUN_STALE_MS(1시간)"로 판정했다. 등록이 늘어 수집이 1시간을 넘기면 살아 있는 실행을 다음 시작이 FAILED로 바꾸고 새 실행을 만든다. 그러면 두 실행이 함께 돌고(unique는 RUNNING 하나만 막는다), 앞 실행은 자기가 FAILED가 된 줄 모르고 끝까지 VAN을 부른다. 또 `execute`는 상태를 보지 않아, 끝난 실행의 job이 다시 돌면 그 실행의 스테이징을 지우고 다시 모았다.
- 생존 판정:
  1. 시작 후 경과 시간(그대로) — 기준을 길게 잡으면 죽은 실행을 오래 못 치우고, 짧게 잡으면 긴 정상 실행을 죽인다. 실행 길이는 등록 수에 따라 달라서 맞는 값이 없다.
  2. Redis 잠금 + TTL 연장 — 위 "진행 중 실행은 하나"의 1과 같은 이유로 버렸다(상태가 두 곳).
  3. **실행 행의 `heartbeat_at`** — 시작할 때와 페이지를 받을 때마다 `update … set heartbeat_at = now where id = ? and status = 'RUNNING'`. 멈춘 실행 = RUNNING이고 `heartbeat_at < 지금 - VAN_RUN_HEARTBEAT_STALE_MS`(기본 5분). 페이지 하나는 재시도를 다 써도 500ms·1·2·4초 백오프(429면 Retry-After)라 5분이면 넉넉하다.
  - → 3. 같은 UPDATE의 영향 행 수가 "아직 내 실행이 RUNNING인가"의 확인도 겸한다. 0행이면(다른 시작이 FAILED로 바꿈) 그 페이지를 스테이징에 넣지 않고 `VanRunNotRunningError`를 던져 멈춘다. 이때 실행 행의 이유(error)는 덮어쓰지 않는다.
  - env: `VAN_RUN_STALE_MS`(시작 후 경과)를 없애고 `VAN_RUN_HEARTBEAT_STALE_MS`로 바꿨다. 뜻이 달라 같은 이름을 두면 헷갈린다. 아직 배포 전이라 호환 이름은 두지 않는다(`.env.example` 함께 바꿈).
  - 정리 UPDATE의 조건에도 `heartbeat_at < 기준`을 다시 넣는다 — 읽은 뒤 그 실행이 하트비트를 보냈으면 건드리지 않는다.
  - 마이그레이션: 행이 있으면 `add … not null`이 실패하므로 null 허용 추가 → `coalesce(finished_at, started_at)`로 백필 → not null.
- 끝난 실행 재처리 방지: `execute`가 처음에 실행 행을 읽어 RUNNING이 아니면 아무것도 하지 않고 돌려준다. `collect`도 첫 하트비트(스테이징을 지우기 전)에서 같은 확인을 한다 — 바로 불러도 끝난 실행의 스테이징을 지우지 않는다.
- 작은 것: 스테이징 DELETE에 `order by serial_no`(PK 순서로 지운다는 것을 문장에 적어 둠, `LIMIT`만 있으면 어떤 행을 지울지 정해지지 않는다). 마지막 COMPLETED UPDATE가 0행이면(끝나는 순간 정리됨) 경고 로그.
- 스테이징 보관: 지금은 지우지 않는다(같은 실행을 다시 할 때만 지움). 보관 규칙은 Task 4의 `cleanupSnapshots`(실행이 끝나면 그보다 앞선 실행의 스테이징을 지움, 이번 것만 남김)로 미룬다 — FAILED 실행의 반쪽 스테이징도 다음 완료 때 함께 지워진다.

## 보탬(2026-10-26, Task 4): 비교·재검증·결과·알림·스테이징 정리

- 대조 키: 시리얼(`serial_no`). VAN tid는 참고값으로 스테이징에만 둔다(우리 테이블에 VAN 필드를 두지 않음). 가맹점은 `merchant.code`로 비교한다(VAN도 우리가 등록할 때 준 가맹점 코드를 들고 있다는 가정).
- 종류 4개와 우선순위(스펙 4.1 표): 우리가 운영 중이면 VAN 없음·해지 → NOT_REGISTERED, 정지 → SUSPENDED_WHILE_IN_SERVICE, 활성인데 가맹점 다름(우리 가맹점 없음 포함) → MERCHANT_MISMATCH. 우리가 운영 중이 아니거나 단말기가 없으면 VAN 활성 → REGISTERED_BUT_NOT_IN_SERVICE. 둘 다 비활성이면 어긋남 아님.
- SQL은 두 문장으로 "어긋난 행"만 거르고 종류는 TS `classify`가 정한다 — 같은 규칙을 SQL CASE와 TS에 두 번 쓰지 않으려고. 두 문장은 한 REPEATABLE READ 읽기 전용 트랜잭션(F10 대조와 같은 이유: 같은 시점).
- 재검증: 스캔에 수 초~수 분이 걸리고 VAN이 그 사이 바뀐다(가상 VAN의 mutateDuringScan). 후보마다 VAN 단건(시리얼)과 우리 쪽을 지금 값으로 다시 읽어 classify를 다시 한다.
  1. 재검증 없음 — 거짓 양성이 그대로 알림·리포트에 간다.
  2. **후보만 재검증** — 후보 수만큼 단건 호출(어긋남 2%면 5만 건에 천 번, 실험 0012가 잰다).
  3. 전체 두 번 스캔 — 호출이 두 배.
  - → 2. 재검증은 "후보 중 풀린 것"만 거른다. 지나간 자리에서 새로 생긴 어긋남(이번 스캔이 놓침)은 찾지 못하고 다음 실행이 찾는다(0012의 C).
  - 재검증도 100개 블록마다 하트비트를 보낸다(fix 커밋과 합침). 후보가 수천 개면 재검증이 수집보다 길 수 있어서, 수집 페이지에만 하트비트가 있으면 재검증 도중에 멈춘 실행으로 보인다. 0행이면 다음 블록의 VAN 호출을 하지 않고 멈춘다.
- 결과: 후보마다 한 행, verified=false는 비교 때의 값(무엇이 거짓 양성이었는지 남김). 목록은 afterId 키셋(offset을 버린 이유와 같다). run_id 인덱스 항목에는 PK가 붙어 있어 `(run_id, id)` 복합 인덱스가 필요 없다(decisions/0032의 반대 경우).
- 확정 순서: 실행 행 UPDATE(조건 status=RUNNING) → 결과 INSERT → Outbox 1행, 한 트랜잭션. 실행 행이 그사이 FAILED(멈춘 실행 정리)가 됐으면 0행 → `VanRunNotRunningError`를 던져 결과도 롤백한다. 계획은 일반 Error였는데, fix 커밋의 규칙(정리된 실행의 이유를 덮어쓰지 않고 경고 로그)과 맞추려고 같은 오류 형으로 했다. fix 커밋의 "마지막 UPDATE 0행이면 경고 로그"는 이것으로 대신한다.
- 알림 묶음: 어긋남이 천 건이어도 Outbox 1행(요약). 목록은 GET과 주간 리포트로 본다(experiments/0010의 relay 줄 교훈).
- 스테이징 정리(보관 규칙): 실행이 COMPLETED로 끝나면 그보다 앞선 실행(COMPLETED·FAILED 모두)의 스테이징을 지운다. 이번 것만 남겨 다음 비교·조사에 쓴다. FAILED로 끝난 실행은 정리하지 않으므로 그 반쪽 스테이징은 다음 완료 때 지워진다.

## 갱신(2026-10-26, fix 커밋 2): 재검증 하트비트는 시간 기준, 후보 수 안전장치, 키 정규화

- 문제(리뷰 Important 2개, Minor 몇 개):
  - 재검증 하트비트가 100개 블록마다뿐이었다. 블록 하나는 동시 8개씩 묶음 13번이고, 묶음 하나는 VAN이 느리면 재시도까지 `5 × 3초 + 7.5초`(429면 Retry-After만큼 더)다. 블록 하나가 멈춤 기준(5분)을 넘길 수 있어 살아 있는 실행을 다음 시작이 FAILED로 바꿀 수 있었다.
  - 후보 수에 상한이 없었다. VAN이 빈 목록·일부만 주는 장애면 "운영 중인데 VAN에 없음"이 우리 운영 중 단말기 수만큼 생기고, 그만큼 단건 조회를 보낸 뒤 그 수의 결과 행을 한 트랜잭션에 넣는다.
- 하트비트 선택지:
  1. 묶음마다·호출마다 하트비트 — 후보 천 개면 UPDATE 천 번. 실행 행 하나에 쓰기가 몰린다.
  2. 블록 크기를 줄임 — 블록 하나의 최악 시간이 VAN 속도에 달려 있어 맞는 크기가 없다.
  3. **시간 기준: 확인 지점마다 "마지막 하트비트 뒤 `VAN_HEARTBEAT_INTERVAL_MS`(30초)가 지났으면" 보낸다** — 확인 지점은 재검증 동시 묶음 사이, 재시도 대기 직전(`withPartnerRetry`의 새 `beforeWait`, 수집 페이지 재시도에도). 수집 페이지·재검증 블록의 하트비트(항상)는 그대로 둔다(RUNNING 확인 겸용). 마지막 하트비트 시각은 서비스의 `clock()`으로 재고, 테스트는 가짜 시계로 바꾼다.
  - → 3. 두 하트비트 사이의 최악 시간 = 간격 + 호출 하나의 최악 시간(`5 × PARTNER_TIMEOUT_MS + 500+1000+2000+4000`). 그래서 시작할 때 `VAN_RUN_HEARTBEAT_STALE_MS ≥ VAN_HEARTBEAT_INTERVAL_MS + 5 × PARTNER_TIMEOUT_MS + 7500`을 검사하고 틀리면 env 이름과 값을 담아 던진다(`van-limits.ts`, 기본값 300000 ≥ 30000 + 22500). Retry-After는 업체가 정해 상한이 없어 식에 넣지 않았다 — 대기 직전에 하트비트를 보내므로 대기 하나가 멈춤 기준보다 길 때만 문제다(업체가 5분 넘게 기다리라고 하면 멈춘 것으로 봐도 된다고 본다).
- 후보 수 안전장치(재검증 전, 둘 다 실행을 FAILED(`VanSafetyValveError: 이유`)로 끝내고 단건 조회·결과 행·알림 없음, 그때까지의 pages·fetched·candidates·phaseMs는 실행 행에 남김):
  1. 후보 > max(`VAN_CANDIDATE_ABS_CAP` 5000, 수집 수 × `VAN_CANDIDATE_MAX_PCT` 20%). 절대 상한만 두면 등록이 50만이 돼도 5000에서 막히고, 비율만 두면 등록이 적을 때(수집 10건에 후보 3건) 막힌다.
  2. 수집 수 < 마지막 COMPLETED 실행의 `VAN_FETCH_MIN_PCT` 50%. 기준은 FAILED가 아니라 COMPLETED(반쪽 수집을 기준으로 삼지 않게). 첫 실행·이전 수집 0이면 검사하지 않는다. 0으로 두면 끈다(van-collect 테스트는 실행마다 등록 수가 달라 끈다).
  - 버린 것: 후보를 상한까지만 재검증하고 나머지를 버림 — 어떤 것이 빠졌는지 알 수 없고 "확정 수"가 거짓이 된다. 운영자가 원인(VAN 장애·우리 쪽 대량 변경)을 보고 다시 돌리는 편이 낫다.
- 키 정규화(Minor): 테이블 collation이 `utf8mb4_0900_ai_ci`라 SQL 조인·스테이징 PK·`terminal.serial_no` unique는 'vk-01'과 'VK-01'을 같게 보는데, TS의 Map 키·`classify`의 가맹점 비교는 글자 그대로였다. 재검증이 우리 쪽을 못 찾아 종류가 틀어졌다(테스트 먼저 실패: VAN 'vk-01' 정지가 SUSPENDED가 아니라 NOT_REGISTERED로, 공백 붙은 ' VK-03 '은 후보 2개로).
  1. SQL에 `COLLATE utf8mb4_bin` — `terminal.serial_no` 인덱스를 못 타고, 우리 DB가 이미 같은 단말기로 보는(unique가 막는) 값을 다르다고 하게 된다.
  2. **TS를 SQL과 같은 동치로: `serialKey = trim + toUpperCase`**. Map 키·정렬·가맹점 비교에 쓰고, 수집은 시리얼·가맹점의 앞뒤 공백을 지워 넣는다(collation이 NO PAD라 공백은 SQL도 다르게 본다). 재검증 VAN 단건 조회는 스테이징의 VAN 쪽 표기로 한다(VAN이 대소문자를 구분할 수도 있어서). 결과 행의 시리얼은 우리 쪽 표기.
  - → 2. 시리얼·가맹점 코드는 ASCII라 악센트 무시는 다루지 않는다.
- "VAN에서 시리얼은 유일"을 가정으로 적는다. 깨지면(같은 serialKey의 등록이 둘) ACTIVE > SUSPENDED > CANCELLED, 같으면 updatedAt이 나중인 것(`betterRegistration`). 수집은 페이지 안은 TS에서, 페이지 사이는 이미 넣은 행을 PK로 읽어(`run_id = ? and serial_no in (…)`, 페이지마다 한 문장) 고르고, 단건 조회도 같은 규칙. 남은 한계: 나중 페이지의 등록이 이기면 스테이징 시리얼 표기는 처음 것으로 남는다(PK는 merge하지 않음).
- 후보 하나의 영구 오류(Minor): 재검증의 VAN 단건이 `PartnerPermanentError`(4xx·형식)면 그 후보만 결과 행 verified=false + `reason`(`재검증 실패: …`)으로 남기고 실행은 끝낸다. 실행 행 `unverifiable`에 수를 두고 `resolved`(풀림)에서 뺀다. 알림 문구는 있을 때만 "확인 불가 N건". 재시도를 다 쓴 429·5xx는 VAN 장애라 지금처럼 실행 FAILED. 마이그레이션 `Migration20261026033754`(run `unverifiable int default 0`, item `reason varchar(200) null`).
- 스테이징 정리(`cleanupSnapshots`)는 결과를 확정한 뒤의 일이라 따로 try/catch에서 경고만 남긴다(전에는 실패하면 `fail()`이 불렸지만 조건이 RUNNING이라 0행이었다 — 결과는 같았고, 테스트로 고정만 했다).

## 갱신(2026-10-26, fix 커밋 3): 수집 급감 확인 플래그, VAN 0건 안전장치, 후보 상한 분모

- 빠져나갈 길:
  1. env(`VAN_FETCH_MIN_PCT=0`)를 잠깐 바꿔 재시작 — 배포가 필요하고, 누가 왜 넘겼는지 남지 않는다.
  2. 기준 실행을 운영자가 고름 — 운영자가 실행 번호를 알아야 한다.
  3. **`POST /van-reconciliations` 본문 `{ acknowledgeDrop: true }`(검증된 DTO, 불리언만, 모르는 필드 400)** — 그 실행만 수집 급감 검사를 건너뛴다. 실행 행 `acknowledge_drop`(마이그레이션 `Migration20261026040250`, `tinyint(1) not null default false`)과 요약 알림 payload·문구(`(수집 급감 확인 후 실행)`)에 남아 감사할 수 있다. 확인한 실행이 COMPLETED면 다음 실행의 기준이 된다.

- VAN 0건 안전장치: 수집 0건인데 우리 운영 중 단말기가 있으면 FAILED(`수집 0건인데 운영 중 단말기가 N대입니다…`). 이전 실행이 없어도 검사한다. 정말로 비었으면 확인 플래그로 돌린다. `VAN_FETCH_MIN_PCT=0`이면 두 검사를 모두 끈다(같은 "수집 급감" 안전장치라서). 기존 테스트 중 "VAN 없음 + 우리 운영 중"을 일부러 만든 5개(재검증 블록 하트비트, 시간 기준 하트비트 3개, 확인 불가)는 확인 플래그로 돌게 바꿨다.

- 시리얼 ASCII 가정(정리): `serialKey`(trim + `toUpperCase`)가 SQL collation(`utf8mb4_0900_ai_ci`)과 같은 동치라는 것은 ASCII에서만 맞다. 악센트(`é`와 `E`는 ai_ci에서 같고 toUpperCase로는 다름), `ß`(JS 대문자는 `SS`), 터키어 i 같은 경우는 갈린다. 우리 쪽 시리얼은 `^[A-Z0-9-]{4,32}$`로 막혀 있고 VAN 쪽만 열려 있다 — VAN이 ASCII가 아닌 시리얼을 주면 SQL은 같은 단말기로, TS 재검증은 다른 단말기로 볼 수 있다(그 후보는 재검증에서 "VAN에 없음"으로 남는다). 생기면 수집 단계에서 ASCII가 아닌 시리얼을 따로 세어 경고하는 쪽을 먼저 본다.

## 갱신(2026-10-26, 최종 리뷰 Minor 1): 하트비트 시간 검사에 Retry-After 상한을 넣는다

- 문제: 위 "시간 기준" 절은 "Retry-After는 업체가 정해 상한이 없어 식에 넣지 않았다"고 했지만 사실이 아니었다. `parseRetryAfter`는 `MAX_RETRY_AFTER_MS = 60_000`으로 자른다(`common/partner-http.ts`, decisions/0014 갱신). 재시도 대기 앞 확인 지점(`beforeWait`)은 간격이 아직 안 지났으면 하트비트를 보내지 않고 최대 60초를 잔다. 그래서 두 하트비트 사이 최악은 간격 + 호출 하나의 최악 + 60초(기본값으로 30 + 22.5 + 60 = 112.5초)인데, 검사는 52.5초짜리 기준도 통과시켰다. 결과는 살아 있는 실행이 멈춘 실행으로 FAILED → `VanRunNotRunningError`로 중단(데이터는 안 깨짐).
- 선택지:
  1. **검사식 `need`에 `MAX_RETRY_AFTER_MS`를 더한다** — 상한이 코드 상수라 식이 정확해진다. 기본값(300초)은 그대로 통과한다.
  2. `beforeWait`에서 간격과 상관없이 대기마다 하트비트 — 429가 잦으면 실행 행 UPDATE가 는다. 식은 그대로지만 "대기 하나가 멈춤 기준보다 길면" 여전히 문제라 결국 상한이 식에 들어가야 한다.
- 결정: 1. `checkVanHeartbeatTiming`: `need = interval + vanWorstCallMs(timeout) + MAX_RETRY_AFTER_MS`, 오류 문구에 `Retry-After 상한 60000`을 적는다. `.env.example` 주석도 고쳤다. 테스트(먼저 실패: staleMs 100000이 통과함): 100000·112499는 시작 실패, 112500은 통과.

## 갱신(2026-10-26, 최종 리뷰 Minor 2·4): 알고 두는 한계 두 가지 (문서만, 코드 변경 없음)

- **큐에서 기다리는 수동 실행이 "멈춘 실행"으로 FAILED 될 수 있다(Minor 2)**
  - 상황: `request()`는 RUNNING 행(`heartbeat_at` = 요청 시각)을 만든 뒤 job을 report 큐(concurrency 1)에 넣는다. job이 큐에서 기다리는 동안에는 하트비트가 없다. 앞에 긴 job(주간 리포트 보내기 최악 약 10.6분, 큰 VAN 실행)이 있으면 `VAN_RUN_HEARTBEAT_STALE_MS`(5분)를 넘길 수 있고, 그 사이 다른 `start()`(주기 실행·다른 수동 요청)의 `failStale`이 이 행을 `멈춘 실행: 하트비트가 …없음`으로 FAILED 처리한다. 나중에 job이 돌면 `execute`가 RUNNING이 아닌 것을 보고 아무것도 하지 않는다.
  - 결과: 안전하다(두 실행이 겹치지 않고 데이터도 안 깨진다). 다만 이유 문구가 실제(아직 시작 안 함)와 다르고, 사용자의 수동 요청이 알림 없이 사라진다 — 실행 목록에서 FAILED와 그 이유로만 보인다.
  - 고치지 않은 이유: 고치는 길은 `failStale`에서 `pages = 0`(아직 시작 안 함)인 행이면 `queue.getJob('van-run-'+id)` 상태가 waiting/delayed일 때 건너뛰기다. 그러면 생존 판정에 BullMQ 상태 조회가 끼어 판정 근거가 둘이 되고(행 하트비트 + 큐 상태), Redis와 MySQL 사이의 경합(조회 직후 job이 시작·실패)을 새로 따져야 한다. report 큐가 밀리는 일은 드물고(주 1회 리포트, 하루 1회 대조), 사용자는 다시 요청하면 된다. Day 6 어드민에서 수동 실행을 부를 때 다시 본다(긴 동기 API를 큐로 돌리는 일 — 최종 리뷰 Minor 6 — 과 함께).
  - 다시 볼 조건: report 큐에 job 종류가 늘거나 수동 요청이 사라졌다는 보고가 생기면 위 방식(또는 큐에 넣을 때 `QUEUED` 상태를 따로 두기)으로.
- **FAILED 실행의 스테이징 행은 다음 COMPLETED까지 남긴다(Minor 4)**
  - 상황: 실패 경로는 `return`으로 `cleanupSnapshots`를 건너뛴다. 정리는 COMPLETED로 끝날 때 "그보다 앞선 실행(COMPLETED·FAILED 모두)"의 스테이징을 지운다(위 Task 4 절). 안전장치가 며칠 연속 걸리면(VAN 부분 응답 장애) 실행마다 최대 수집 수만큼(5만 행) 스테이징이 쌓인다.
  - 의도: **디버깅용으로 남긴다**. 안전장치가 걸린 실행(후보 폭증·수집 급감·0건)은 그때 VAN이 무엇을 줬는지가 원인 조사의 유일한 근거다 — 수집한 그대로의 행을 운영자가 `run_id`로 읽어 마지막 COMPLETED 실행의 스테이징과 비교한다. 다음 COMPLETED가 한꺼번에 지운다.
