# 0035. 주간 리포트와 cron 주기 작업

- 날짜 / 관련 기능: 2026-10-26 / F4, F9, F11
- 상황: Day 4까지 주기 작업은 모두 "N초마다"(`every`)였다. 이상 찾기·VAN 대조는 매일 밤, 주간 리포트는 월요일 09:00(KST)이라 달력 시각이 필요하다.
- 선택지:
  1. every 하루 + 시작 시각 맞추기 — 서버를 다시 띄우면 시각이 밀린다.
  2. **BullMQ job scheduler의 cron `pattern` + `tz`** — Redis에 한 개만 저장(같은 id면 덮음), 등록한 프로세스가 끝나도 남는다(decisions/0015와 같은 성질).
  3. OS cron·별도 스케줄러 — 배포 단위가 늘어난다.
- 결정: 2. `JOB_SCHEDULERS[].schedule()`이 `{ every }` 또는 `{ pattern, tz: 'Asia/Seoul' }`를 돌려주고 `upsertJobScheduler`에 그대로 넘긴다. report 큐에 `anomaly-scan-daily`(`ANOMALY_SCAN_CRON`, 기본 `0 2 * * *`), `van-reconcile-daily`(`VAN_RECONCILE_CRON`, 기본 `0 3 * * *`). report 큐는 concurrency 1이라 둘이 겹치지 않는다. 등록 로그는 `anomaly-scan-daily cron "0 2 * * *" Asia/Seoul`.
- 확인한 동작(사전 검증과 이번 테스트): 등록하자마자 돌지 않는다(report 큐 `delayed` 2, `waiting` 0 — `every`와 다름). `next`는 다음 시각(02:00 KST = 전날 17:00 UTC, 03:00 KST = 18:00 UTC). **tz를 빼면 서버 프로세스의 시간대로 해석한다** — 이 PC는 KST라 같았지만 UTC 서버면 9시간 밀린다. 그래서 늘 `tz: 'Asia/Seoul'`을 넘긴다. `removeJobScheduler`는 delayed job도 지운다. 테스트는 기다리지 않고 `getJobScheduler().next`를 보고, job은 큐에 직접 넣는다.
- cron 식 검증: 숫자 env처럼 미리 검사하지 않고(cron 파서를 따로 들이지 않으려고) 잘못된 식이면 스케줄러 등록 때 BullMQ가 던져 서버가 뜨지 않게 둔다.
- 주기 job과 수동 실행이 겹칠 때: `anomaly-scan` job은 수동 찾기가 잠금을 쥐고 있으면(409 `ANOMALY_SCAN_RUNNING`) `{ skipped: true }`로 끝난다(그 찾기가 같은 일을 한다). `van-reconcile-scheduled`는 진행 중인 실행이 있으면 건너뛴다(decisions/0033). 주기 VAN 실행은 급감 확인 플래그를 주지 않는다 — 사람이 확인한 실행만 안전장치를 넘긴다(fix 커밋 3).
- 결과·대가: job이 실패하면 다음 주기까지 돌지 않는다(attempts 기본 1) — 그날 것은 수동 API(`POST /anomaly-scans`, `POST /van-reconciliations`)로 다시 한다.
- 다시 볼 조건: 여러 시간대 운영, 정확히 한 번 실행이 필요할 때.

## 갱신(2026-10-26, fix 커밋): cron env를 시작할 때 검사한다

- 위 "cron 식 검증: 미리 검사하지 않고 BullMQ가 던지게 둔다"를 뒤집는다. BullMQ는 틀린 식 중 일부만 던지고 나머지는 조용히 받았다.
- 확인한 동작(BullMQ 6.4.0, `upsertJobScheduler(id, { pattern, tz: 'Asia/Seoul' })`, 테스트 접두사 `test-cronprobe-*` 큐, 끝에 지움, 2026-10-26T04:30:57Z = 13:30 KST에 실행):

  | pattern | BullMQ | next(UTC) | 뜻 |
  |---|---|---|---|
  | `0 2 * *`(네 칸) | 받음 | 2026-11-01T15:00Z | 매달 2일 00:00 KST — 앞에 칸을 채워 다르게 읽었다 |
  | `0 0 2 * * *`(여섯 칸) | 받음 | 2026-10-26T17:00Z | 첫 칸이 초. 이 식은 우연히 02:00 KST |
  | `@daily` | 받음 | 2026-10-26T15:00Z | 00:00 KST(의도한 02:00이 아님) |
  | `0 25 * * *` | 던짐 | — | `Constraint error, got value 25 expected range 0-23` |
  | `0 2 * * *` | 받음 | 2026-10-26T17:00Z | 기준 |

  cron-parser 5.10.2 `CronExpressionParser.parse(pattern, { tz: 'Asia/Seoul', currentDate })`도 같은 값·같은 오류였다(BullMQ가 이것을 쓴다). 네 칸·`@daily`는 서버가 뜨고 밤 작업이 엉뚱한 날·시각에 돈다 — 알아채기 어렵다.
- 선택지:
  1. 그대로(BullMQ에 맡김) — 위 표처럼 일부는 조용히 받는다.
  2. 정규식으로 다섯 칸·숫자 범위 직접 검사 — 범위·목록·`*/n`·요일 이름 규칙을 다시 써야 하고 BullMQ와 해석이 갈릴 수 있다.
  3. **`cronFromEnv`(config/env-cron.ts)**: 빈 글자·공백이면 기본값, `@`로 시작하면 거절, 공백으로 나눈 칸이 정확히 다섯이 아니면 거절, 그다음 BullMQ와 같은 파서 cron-parser로 `tz: 'Asia/Seoul'` 파싱이 실패하면 거절. 숫자 env(`intFromEnv`, decisions/0032)처럼 env를 읽을 때 이름과 값을 담아 던진다.
- 결정: 3. cron-parser를 직접 의존성으로 넣되 BullMQ 6.4.0이 고정한 판과 같은 `5.10.2`로 정확히 고정한다(`npm ls cron-parser`: bullmq 아래 `cron-parser@5.10.2 deduped`). 판이 다르면 검사는 통과하는데 BullMQ가 다르게 읽을 수 있다 — BullMQ를 올릴 때 함께 맞춘다.
- 시간대 값 `CRON_TZ`를 env-cron에 두고 `SCHEDULE_TZ`가 그것을 쓴다(검사와 등록이 같은 tz). `nextCronRun(pattern, from)`은 BullMQ `next`와 같은 계산이라 scheduler e2e가 기대값을 env 값으로 구한다(개발자 `.env`가 cron을 바꿔도 테스트가 깨지지 않게). 기본 식의 시각(02:00 KST = 17:00 UTC)은 unit 테스트가 고정 시각으로 본다.
- 테스트: 네 칸·여섯 칸·`@daily`·`0 25 * * *`·글자는 던짐, 공백·빈 글자는 기본값, env 모듈은 `ANOMALY_SCAN_CRON`/`VAN_RECONCILE_CRON=@daily`이면 불러올 때 던짐. 주간 리포트 cron(`WEEKLY_REPORT_CRON`)은 아직 없다(Task 8) — 생길 때 같은 함수를 쓴다.
- 주기 job 로그: `ReportProcessor`가 건너뛸 때 `warn`(`anomaly-scan 건너뜀: …`, `van-reconcile-scheduled 건너뜀: …`), 끝나면 한 줄 `log`(`anomaly-scan 끝: 새로 N, 계속 N, 풀림 N`, `van-reconcile-scheduled 끝: 실행 #id 상태`). 전에는 반환값(BullMQ job 결과)에만 남아 로그로는 그날 돌았는지 알 수 없었다. `runScheduled`가 끝난 상태도 돌려준다.

## 보탬(2026-10-26, Task 7): 주간 리포트 집계

- 주 경계: 주는 KST 월요일 00:00부터. DB는 UTC로 저장하므로(MikroORM forceUtcTimezone) 경계를 UTC 시각 `[일요일 15:00, 다음 일요일 15:00)`으로 넘긴다.
  1. SQL에서 `convert_tz`·NOW() — 세션 시간대(SYSTEM=KST)와 저장값(UTC)이 섞인다(troubleshooting/0016).
  2. **앱에서 계산해 파라미터로** — getUTC*만 써서 서버 시간대와도 무관.
  - → 2. `report/kst-week.ts`(`kstWeekOf`, `previousKstWeek`, `parseKstWeekStart`). 경계 테스트: 일요일 23:59 KST, UTC로는 일요일인 월요일 00:30 KST, 해가 바뀌는 주, 없는 날짜·월요일이 아닌 날.
  - fix 커밋과 합침: KST 오프셋·`kstDate`는 알림 문구의 `formatKst`가 있는 `common/kst.ts` 한 곳에 두고 kst-week가 가져와 다시 내보낸다(계획은 kst-week 안에 따로 정의).
- 집계는 DB에서: 행을 앱으로 가져와 세지 않는다(이상 목록만 최대 1,000행). 일곱 쿼리(모델·상태별 수, 그 주 전이, 입고·출고·회수 입고, 열린 이상, 운영 중 접속 상태, 그 주의 펌웨어 배포, 최근 완료 VAN 대조)를 한 REPEATABLE READ 읽기 전용 트랜잭션에서(같은 시점). 접속 상태는 online=1이어도 마지막 하트비트가 `HEARTBEAT_OFFLINE_AFTER_MS`보다 오래면 오프라인으로 센다.
  - fix 커밋과 합침: VAN 요약에 계획 뒤에 생긴 `unverifiable`(확인 불가 수)·`acknowledgeDrop`(급감 확인 후 실행)을 더했다 — 리포트가 확인 불가를 숨기지 않게.
- 이력 occurred_at은 datetime(초)라 밀리초가 반올림된다 — 경계에서 0.5초 안의 일은 다음 초로 센다. 주간 리포트에는 문제 없다고 보고 그대로 둔다.
- 이력 기간 집계(`occurred_at` 범위)는 인덱스가 없어 이력 전체를 훑는다. 주 1회라 두고 실험 0011이 시간·실행계획을 잰다(Task 9).
- ORDER BY enum 열은 enum 선언 순서다(`source`에서 SHIPMENT가 SCAN 앞, `rule`에서 RETURN_STALLED가 OFFLINE_TOO_LONG 앞). 리포트의 줄 순서가 글자 순서가 아니다.

## 갱신(2026-10-26, Task 6·7 리뷰 반영 fix)

- 기준 시점이 두 가지다(리포트를 읽는 사람이 헷갈리지 않게 데이터 인터페이스 주석과 xlsx 시트 머리에 적는다): **현황(statusByModel, anomalies, connectivity)은 생성 시점(generatedAt) 기준, 전이·입출고·배포는 그 주 기준.** 배포의 대상·성공·실패·시간 초과 수는 그 주 증분이 아니라 배포마다 누적이다(대상 행에 "그 주에 끝남" 시각을 따로 세지 않는다). VAN은 생성 시점까지 가장 최근에 끝난 대조.
  - 버린 선택지: 현황을 "그 주 끝(to) 시점"으로 되돌려 계산 — 단말기 상태는 이력에서 거꾸로 풀 수 있지만 열린 이상·접속 상태는 이력이 없어 같은 시점을 만들 수 없다. 월요일 09:00에 만들면 차이는 9시간이다.
- 접속 상태의 온라인 판정 부등호를 조회 API(`connectivity.service`, `lastSeen > now − 기준`)와 같게 `c.last_seen_at > ?`로 고쳤다(전에는 `>=` — 정확히 기준만큼 지난 단말기가 조회에서는 오프라인, 리포트에서는 온라인). 경계 테스트: 기준 1ms 전은 온라인, 정확히 기준이면 오프라인.
- cron-parser 판 고정을 테스트로 지킨다: `package.json`의 `cron-parser`가 정확한 판(범위 아님)이고 `node_modules/bullmq/package.json`의 `dependencies['cron-parser']`와 같아야 한다(test/unit/env-cron.spec.ts). BullMQ를 올리고 cron-parser를 안 맞추면 테스트가 깨진다 — 위 "판이 다르면 검사는 통과하는데 BullMQ가 다르게 읽는다"를 사람 기억에 맡기지 않으려고.
- VAN 대조 job(`van-reconcile-scheduled`, 수동 `van-reconcile`)이 FAILED로 끝나면 `log`가 아니라 `warn`. `execute`는 실패해도 던지지 않고 행에 이유를 남기므로 job은 "성공"으로 끝난다 — 로그 수준으로라도 거를 수 있어야 한다.
- `WeeklyReportQueries.collect`는 주의 from·to가 올바른 시각이 아니거나(NaN) to ≤ from이면 DB에 가기 전에 `주간 리포트 주 <주>: …`로 던진다.

## 보탬(2026-10-26, Task 8): 주간 리포트 보내기

- 파일 만들기: exceljs 4.4.0 쓰기(Day 3은 읽기만, decisions/0022). default import(`import ExcelJS from 'exceljs'`)만 된다. `writeBuffer()`의 타입이 exceljs 자체 Buffer라 Node Buffer로 감싼다. 시트 8장(요약, 상태·모델, 전이, 입출고, 이상 단말기, 접속 상태, 펌웨어 배포, VAN 대조), 서식은 머리글 굵게·열 너비만(차트·조건부 서식은 하지 않음). 시각은 KST `YYYY-MM-DD HH:mm`. 파일 이름 `단말온-주간리포트-<주>.xlsx`.
  - 계획과 다르게 한 것(리뷰 반영의 기준 시점): 요약을 뺀 시트 첫 줄에 기울임 안내 한 줄을 넣고 표 머리글은 2행이다. 현황 시트(상태·모델, 이상 단말기, 접속 상태)는 `생성 시점(<시각> KST) 기준 현황`, 전이·입출고는 `그 주 … 기준`, 펌웨어 배포는 "대상·성공·실패·시간 초과 수는 배포마다 누적"이고 그 네 머리글에 `(누적)`을 붙였다. 요약은 행 위치를 지키려고 마지막 행에 `기준`을 더했다.
- 첨부 방식(가상 톡톡 API를 정함):
  1. multipart/form-data — 실제 메신저들이 흔히 쓰지만 의존성 없는 node:http인 partners가 경계 문자열을 직접 풀어야 한다.
  2. **JSON 안의 base64(`POST /toktok/files` → fileId → 메시지 `attachments`)** — 기존 `readJson` 그대로, 크기는 33% 늘지만 리포트는 수십 KB.
  3. 메시지에 파일을 바로 넣기 — 재시도마다 파일을 다시 보내고 메시지 실패와 파일 실패를 나눌 수 없다.
  - → 2. 상한 5MB(`maxFileBytes`, 푼 크기, 넘으면 413 FILE_TOO_LARGE). 모르는 fileId를 첨부하면 400 UNKNOWN_FILE.
- 파일 저장:
  1. 디스크 — 워커와 API가 다른 프로세스·호스트면 같은 경로를 공유해야 하고 지우기가 따로 필요.
  2. **weekly_report 행의 mediumblob(lazy)** — 상태와 같은 행이라 어느 프로세스든 내려줄 수 있다. `blob`은 64KB 상한이라 mediumblob. lazy라 상태 조회는 파일을 읽지 않는다.
  - → 2.
- 멱등: `week_start` unique 행 하나가 상태(PENDING → GENERATED → SENT)를 들고 간다. SENT면 아무것도 하지 않는다(`alreadySent`). 파일을 먼저 저장(GENERATED)하고 다시 시도하면 같은 파일을 쓴다(다시 집계하면 그사이 데이터가 바뀌어 다른 파일이 된다). 올리기·메시지 뒤 SENT를 쓰기 전에 죽으면 다시 보낸다 — 멱등키 `weekly-report-<주>`(Outbox와 같은 "최소 한 번 + 멱등키", decisions/0016). 같은 주 동시 요청은 Redis 잠금(`<p>:report-lock:weekly-<주>`, 2분)으로 409 WEEKLY_REPORT_IN_PROGRESS. 행을 동시에 만들면 unique 위반을 잡고 다시 읽는다. 톡톡 호출은 트랜잭션 밖(행 갱신은 각각 짧은 nativeUpdate).
- 재시도: 톡톡 호출마다 3번(`withPartnerRetry`, 500ms·1s). 주기 job이 실패하면 다음 주까지 다시 돌지 않으므로 행에 `last_error`를 남기고(HTTP는 502 PARTNER_ERROR) 수동 `POST /reports/weekly`로 같은 파일을 이어서 보낸다. 다시 올리면 새 fileId가 생긴다(메신저 쪽 파일은 남는다 — 가상 API라 지우기는 두지 않음).
- 주기: report 큐 `weekly-report`, `WEEKLY_REPORT_CRON`(기본 `0 9 * * 1`)은 계획의 `process.env ?? …`가 아니라 fix 커밋의 `cronFromEnv`로 읽는다(잘못된 식이면 env를 읽을 때 던짐), tz `CRON_TZ`. `RUN_SCHEDULERS`인 프로세스만 등록한다(SchedulerModule). job은 `sendScheduled()` = 처리 시각 기준 지난주, 끝나면 한 줄 `log`, 이미 보낸 주면 `warn`.
- API: `POST /reports/weekly { weekStart? }`(기본 지난주), `GET /reports/weekly/:weekStart`, `GET /reports/weekly/:weekStart/file`(xlsx, `filename="weekly-report-<주>.xlsx"; filename*=UTF-8''<한글 이름>`). 주는 `parseKstWeekStart`로 읽어 KST 월요일이 아니면 400 INVALID_WEEK_START.
- 다시 볼 조건: 리포트가 수 MB가 되면(스트리밍 쓰기, 객체 저장소), 받는 채널이 여럿이면, 메신저가 실제로 multipart만 받으면, 다시 올린 파일이 쌓이는 것이 문제가 되면.
