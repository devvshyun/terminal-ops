# 0036. 주간 리포트 이력 기간 집계에 인덱스를 더하지 않는다

- 날짜 / 관련 기능: 2026-10-26 / F11, F2 (experiments/0011, decisions/0035)
- 상황: 주간 리포트(`src/report/weekly-report.queries.ts`)의 쿼리 2(그 주 전이, `group by source, to_status`)와 쿼리 3(그 주 입고·출고·회수 입고, 단말기·모델 조인)은 `terminal_status_history.occurred_at` 범위로 거른다. 이력 표의 보조 인덱스는 `(terminal_id, occurred_at)` 하나라 두 쿼리 모두 이력 전체를 훑는다. decisions/0035는 "주 1회라 두고 실험 0011이 잰다"고 미뤄 두었다.
- 잰 값(experiments/0011, 이력 999,979행, 한 주 = 이력의 9~11%, 5번 중앙값):

  | 선택지 | Q2 / Q3 (최근 주, ms) | 이력 10만 행 대량 INSERT ms(지금 대비) | 보조 인덱스 증가 |
  |---|---|---|---|
  | 인덱스 없음(지금) | 165.5 / 183.4 | 487.7 | - |
  | (occurred_at) | 133.1 / 133 | 578.8 (+19%) | +16.5MB |
  | (occurred_at, source, to_status) | 62.6 / 79.3 | 938.6 (+92%) | +18.5MB |
  | (occurred_at, to_status, from_status, terminal_id) | 158.4 / 61 | 837.5 (+72%) | +24.5MB |
  | (occurred_at, to_status, source, from_status, terminal_id) | 62.3 / 71.6 | 970.1 (+99%) | +25.5MB |

  한 건씩 자동 커밋 INSERT 1,000건은 대부분 건당 약 3.1~3.5ms, 일부 회차는 5~6ms로 튀어(원인 미확인) 커밋 비용과 흔들림 안에 인덱스 차이가 묻혔다.
- 선택지:
  1. **인덱스를 더하지 않는다(지금대로 전체 훑기).** 리포트 한 번에 두 쿼리 합 약 0.35초. 이력 쓰기는 그대로.
  2. `(occurred_at)` 단독 — 쓰기 +19%로 가장 싸지만 이득도 가장 적다(약 30~50ms: Q2 32ms, Q3 50ms). 범위 행마다 PK를 다시 읽어, 표가 버퍼 풀보다 크면 전체 훑기보다 느려질 수 있다(추정).
  3. 쿼리별 커버링 인덱스 하나씩(`(occurred_at, source, to_status)` + `(occurred_at, to_status, from_status, terminal_id)`) — 둘 다 빨라지지만 인덱스 두 개라 쓰기 비용이 둘의 합.
  4. 두 쿼리를 다 덮는 다섯 열 인덱스 `(occurred_at, to_status, source, from_status, terminal_id)` — 둘 다 커버링(62·72ms). 쿼리당 약 0.1초(Q2 103ms, Q3 112ms), 두 쿼리 합 약 0.2초(215ms) 줄지만 이력 대량 INSERT가 두 배(+99%), 보조 인덱스 +25.5MB.
  5. 리포트용 집계 표(일 단위 전이 수)를 전이 때 같이 올린다 — 전이 서비스에 쓰기가 하나 더 붙고, 지금 문제 크기(0.35초/주)에 비해 과하다.
- 결정: 1. 이 쿼리는 주 1회(월요일 09:00 주기 job, report 큐 concurrency 1 — 다른 사용자 요청을 막지 않는다)이고, 0.2초를 줄이려고 모든 전이가 쓰는 표의 쓰기 비용과 공간을 늘릴 이유가 없다. Task 1(decisions/0032)에서 같은 표의 중복 인덱스를 쓰기 비용 때문에 지운 것과도 같은 방향이다.
- 결과·대가: 리포트 집계는 이력 행 수에 비례해 느려진다. 이력이 버퍼 풀보다 커지면 주 1회 전체 훑기가 버퍼 풀의 다른 페이지를 밀어낼 수 있다(추정, 재지 않음).
- 다시 볼 조건(하나라도 맞으면 4를 먼저 잰다 — 두 쿼리를 한 인덱스로 덮는다):
  - 이력이 1,000만 행 안팎(전체 훑기가 선형이면 약 2초 — 추정)이거나 이력 표가 버퍼 풀보다 커질 때
  - 리포트·대시보드가 이력 기간 집계를 자주(수동 조회, 시간 단위 집계) 부를 때
  - occurred_at 범위로 읽는 다른 쿼리가 생길 때(감사 조회, 기간별 이력 내보내기)
  - 실제 이력이 몇 년치가 되어 한 주가 이력의 1% 안팎일 때 — 인덱스는 그 주 행만 읽으므로 이득이 지금보다 크다(추정)
- 버린 것: 마이그레이션 없음. 실험 중에 만든 인덱스는 테스트 DB에서 실험이 지웠다(`information_schema.statistics`로 0개 확인).
