# 0039. 목록 페이지 방식과 연관 읽기

- 날짜 / 관련 기능: 2026-10-27 / F1, 어드민 목록 전체
- 상황: 어드민은 목록이 많다(단말기, 발주, A/S, 배포, VAN 실행, 주간 리포트, 택배 수집 실행). 단말기 목록은 이미 offset(`page`·`size`·`total`), 이상·VAN 결과는 afterId 키셋(오름차순)이다. 단말기 목록은 모델·가맹점을 함께 읽는데(`populate`), MikroORM 기본은 joined(한 SQL에 조인)다.
- 선택지
  1. 모두 offset + total — 화면이 단순하다. 행이 많이 쌓이는 실행·접수 이력에서 깊은 쪽과 count가 비싸지고, 새 행이 들어오면 쪽이 밀린다.
  2. 모두 키셋 — 단말기 목록의 "n / m쪽"과 총 대수가 사라진다. 운영자는 조건으로 좁힌 결과의 대수를 본다.
  3. **단말기 목록은 offset 유지, 실행·접수 이력(새 목록)은 최근 것부터 beforeId 키셋**
  - 연관 읽기: (a) joined(기본) — 한 번에 읽지만 정렬·LIMIT 전에 조인이 끼어 인덱스로 멈추지 못한다 (b) **select-in** — 목록 SQL은 terminal만 읽고 모델·가맹점은 그 페이지 id로 `in (…)` 한 번씩 (c) 모델·가맹점 이름을 응답에서 빼기 — 화면이 이름을 따로 읽어야 한다.
- 결정(단말기 목록): 3의 앞부분 — offset 유지. 연관은 (b) select-in(`TerminalService.list`의 `strategy` 기본값).
  - 실험 0013(단말기 10만): 조건 없음 1쪽 서비스 p50 joined 91.2ms → select-in 5.2ms. joined는 10만 행을 해시 조인한 뒤 정렬해 20행을 자르고 count도 같은 조인을 탔다. select-in은 목록이 `Index scan on t0 using PRIMARY (reverse)` 20행에서 멈추고 count는 `Count rows in t0`(4.26ms).
  - 모델·가맹점 코드로 거를 때는 MikroORM이 거르기용 조인만 붙인다(모델 inner join, 가맹점 left join + where) → 각 FK 인덱스를 거꾸로 읽고 멈춘다(모델 조건 p50 3.6ms).
  - total(count)은 조건이 없으면 PK `Count rows`라 싸고, 조건이 있으면 그 인덱스를 커버링으로 읽는다(1~3ms).
  - `list(query, strategy)`의 두 번째 인자는 실험 0013이 joined와 비교하려고만 바꾼다(실험 0007의 `lockOrder`와 같은 방식).
- 결과·대가
  - 깊은 쪽은 앞 행을 다 건너뛴다: 조건 없음 2000쪽(offset 39,980) 10.1ms, 상태 IN_SERVICE 끝쪽(400쪽) 10.3ms 대 1쪽 3.3ms(실험 0013).
  - 목록이 바뀌는 중에 쪽을 넘기면 행이 겹치거나 빠질 수 있다(offset의 성질).
  - select-in은 왕복이 2번 → 4번이다. 결과가 작은 조건(시리얼 앞부분 100행)에서는 joined 2.1ms 대 select-in 2.9ms로 조금 진다.
- 다시 볼 조건: 단말기가 수백만이 되거나 조건 없는 깊은 쪽을 자주 보면 키셋으로. DB가 원격이라 왕복이 비싸지면 select-in의 4번 왕복을 다시 잰다.
