# 0039. 목록 페이지 방식과 연관 읽기

- 날짜 / 관련 기능: 2026-10-27 / F1, 어드민 목록 전체
- 상황: 어드민은 목록이 많다(단말기, 발주, A/S, 배포, VAN 실행, 주간 리포트, 택배 수집 실행). 단말기 목록은 이미 offset(`page`·`size`·`total`), 이상·VAN 결과는 afterId 키셋(오름차순)이다. 단말기 목록은 모델·가맹점을 함께 읽는데(`populate`), MikroORM 기본은 joined(한 SQL에 조인)다.
- 선택지
  1. 모두 offset + total — 화면이 단순하다. 행이 많이 쌓이는 실행·접수 이력에서 깊은 쪽과 count가 비싸지고, 새 행이 들어오면 쪽이 밀린다.
  2. 모두 키셋 — 단말기 목록의 "n / m쪽"과 총 대수가 사라진다. 운영자는 조건으로 좁힌 결과의 대수를 본다.
  3. **단말기 목록은 offset 유지, 실행·접수 이력(새 목록)은 최근 것부터 beforeId 키셋**
  - 연관 읽기: (a) joined(기본) — 한 번에 읽지만 정렬·LIMIT 전에 조인이 끼어 인덱스로 멈추지 못한다 (b) **select-in** — 목록 SQL은 terminal만 읽고 모델·가맹점은 그 페이지 id로 `in (…)` 한 번씩 (c) 모델·가맹점 이름을 응답에서 빼기 — 화면이 이름을 따로 읽어야 한다.
- 결정(단말기 목록): 3의 앞부분 — offset 유지. 연관은 (b) select-in(`TerminalService.list`의 `strategy` 기본값).
  - 실험 0013(단말기 10만): 조건 없음 1쪽 서비스 p50 joined 91.2ms → select-in 5.2ms. joined는 10만 행을 해시 조인한 뒤 정렬해 20행을 자르고 count도 같은 조인을 탔다. select-in은 목록이 `Index scan on t0 using PRIMARY (reverse)` 20행에서 멈추고 count는 `Count rows in t0`(4.26ms).
  - 모델·가맹점 코드로 거를 때는 MikroORM이 거르기용 조인만 붙인다(모델 inner join, 가맹점 left join + where) → 각 FK 인덱스를 거꾸로 읽고 멈춘다(모델 조건 p50 3.6ms).
  - total(count)은 조건이 없으면 PK `Count rows`라 싸고, 조건이 있으면 그 인덱스를 커버링으로 읽는다(1~3ms).
  - `list(query, strategy)`의 두 번째 인자는 실험 0013이 joined와 비교하려고만 바꾼다(실험 0007의 `lockOrder`와 같은 방식).
- 결과·대가
  - 깊은 쪽은 앞 행을 다 건너뛴다: 조건 없음 2000쪽(offset 39,980) 10.1ms, 상태 IN_SERVICE 끝쪽(400쪽) 10.3ms 대 1쪽 3.3ms(실험 0013).
  - 목록이 바뀌는 중에 쪽을 넘기면 행이 겹치거나 빠질 수 있다(offset의 성질).
  - select-in은 왕복이 2번 → 4번이다. 결과가 작은 조건(시리얼 앞부분 100행)에서는 joined 2.1ms 대 select-in 2.9ms로 조금 진다.
- 다시 볼 조건: 단말기가 수백만이 되거나 조건 없는 깊은 쪽을 자주 보면 키셋으로. DB가 원격이라 왕복이 비싸지면 select-in의 4번 왕복을 다시 잰다.

## 보탬(Task 3): 새 목록 — 실행·접수 이력은 beforeId 키셋

- 결정(새 목록): 발주·A/S·펌웨어 배포·VAN 실행·택배 수집 실행은 최근 것부터 `?beforeId=&limit=`(limit 1~100, 기본 20) → `{ items, nextBeforeId }`(`common/keyset.ts`의 `BeforeIdQuery`·`keysetPage`·`beforeIdWhere`). 쿼리는 `id < beforeId order by id desc limit n+1`. 실행·접수 이력은 최근 것을 먼저 보고 "더 보기"로 이어 본다 — 총 수가 필요 없고, PK 범위라 몇 번째 쪽이든 같은 비용이다. 이상·VAN 결과의 afterId(오름차순)와 방향만 다르다. 주간 리포트는 주(`week_start`, unique)가 키라 `?before=YYYY-MM-DD` → `nextBefore`.
- 연관은 모두 select-in(`strategy: LoadStrategy.SELECT_IN`) — joined면 옵티마이저가 PK 역순 읽기를 버리고 조인 뒤 정렬할 수 있다(실험 0013).
- 주간 리포트 목록의 `queued`·`queuedAt`은 주마다 큐를 본다(쪽당 최대 100번). 이미 보낸 주는 Redis를 보지 않는다(`queueState`, decisions/0038 보탬) — 보통 대부분 SENT라 실제 조회는 몇 번이다.
- 실행계획(Task 3 Step 5): 테스트 DB에 terminal·purchase_order·service_ticket·van_reconciliation_run·sync_run·weekly_report를 각 1000행 넣고 `analyze table` 뒤 HTTP 요청이 낸 select마다 `explain`(임시 `test/zz-explain-lists.e2e.spec.ts`, 커밋하지 않고 지움). firmware_rollout·inspection은 행을 넣지 않았다(빈 표라 두 줄은 참고만).
  ```
  /purchase-orders {}                 purchase_order type=index key=PRIMARY rows=21 Backward index scan; terminal_model in (1) const PRIMARY
  /purchase-orders {beforeId:500}     purchase_order type=range key=PRIMARY rows=499 Using where; Backward index scan
  /purchase-orders {status:CLOSED}    purchase_order type=index key=PRIMARY rows=21 Using where; Backward index scan
  /service-tickets {}                 service_ticket type=index key=PRIMARY rows=21 Backward index scan; terminal in (1000…980) range PRIMARY rows=21; merchant in (1) const
  /service-tickets {beforeId:500}     service_ticket type=range key=PRIMARY rows=499 Using where; Backward index scan
  /service-tickets {status:OPEN}      service_ticket type=index key=PRIMARY rows=21 Using where; Backward index scan
  /service-tickets {serialNo:EX-10}   terminal type=const key=terminal_serial_no_unique Using index; Using filesort → service_ticket type=ref key=service_ticket_terminal_id_status_index rows=1
  /firmware-rollouts {status:RUNNING} firmware_rollout type=ref key=firmware_rollout_status_index rows=1 Using where; Backward index scan (빈 표)
  /van-reconciliations {beforeId:500} van_reconciliation_run type=range key=PRIMARY rows=499 Using where; Backward index scan
  /reports/weekly {}                  weekly_report type=ALL key=null rows=1000 Using filesort
  /reports/weekly {before:2022-01-03} weekly_report type=range key=weekly_report_week_start_unique rows=104 Using index condition; Backward index scan
  /sync-runs {beforeId:500}           sync_run type=range key=PRIMARY rows=499 Using where; Backward index scan
  /sync-runs {job:track-bungae}       sync_run type=index key=PRIMARY rows=21 Using where; Backward index scan
  /terminals/EX-10/inspections {}     terminal const terminal_serial_no_unique; inspection_item ref inspection_item_model_id_code_unique rows=4 Using filesort; inspection ref inspection_terminal_id_index Backward index scan (빈 표)
  ```
  - beforeId 범위의 `rows=499`는 범위 전체의 추정이다 — `limit 21`이라 실제로는 21행을 읽고 멈춘다(EXPLAIN의 rows는 LIMIT을 반영하지 않는다).
  - 상태·큐 조건(발주 status, A/S status, sync_run job)은 인덱스가 없어 PK 역순으로 읽으며 거른다 — 최근 행 중 조건에 맞는 것이 드물면 많이 읽는다(예: 오래된 ERROR만 찾기).
  - 주간 리포트 조건 없음은 천 행에서도 week_start 인덱스를 쓰지 않고 전체 읽기 + filesort(옵티마이저가 그쪽을 싸다고 봄). 주는 1년에 52행이라 그대로 둔다.
- 다시 볼 조건(보탬): 조건에 맞는 행이 드문 목록을 자주 보면 `(status, id)`·`(job, id)` 인덱스.
- 배치 실행 이력: 실행마다 행을 남기는 배치는 택배 수집(SyncRun), VAN 대조, 주간 리포트 셋이다. 이상 찾기는 실행 기록 표가 없다(결과는 열린 이상과 알림) — 표를 만들지 않는다(이유: 하루 한 번 1초 안팎, 결과가 이미 열린 이상으로 남는다).
