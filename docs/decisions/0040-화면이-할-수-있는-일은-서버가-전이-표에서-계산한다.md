# 0040. 화면이 할 수 있는 일은 서버가 전이 표에서 계산한다

- 날짜 / 관련 기능: 2026-10-27 / F2, 어드민 단말기 상세
- 상황: 상세 화면은 "지금 상태에서 누를 수 있는 버튼"을 그려야 한다. 전이 규칙은 상태 쌍 + 출처(MANUAL·ALLOCATION·SHIPMENT·INSPECTION…) + 모델 정책(재검수 필수)으로 정해지고 `transition-rules.ts` 한 곳에 있다(decisions/0003·0007).
- 선택지
  1. 화면에 같은 표를 복제 — 규칙이 바뀌면 두 곳을 고쳐야 하고, 어긋나면 화면은 된다는데 서버가 422.
  2. 버튼을 다 그리고 서버 422로 알림 — 운영자가 해 보고 나서야 실패를 안다.
  3. **상세 응답에 서버가 계산한 `allowedTransitions`·`actions`**
  4. 별도 `GET /terminals/:serialNo/transitions` — 요청이 하나 늘고 상세와 읽은 시점이 어긋날 수 있다.
- 결정: 3.
  - `targetsFrom(from, source, policy)`가 `checkTransition()`과 같은 표(RULES)를 읽는다. 모든 상태·출처·정책 조합에서 두 함수가 같은 답을 하는지 단위 테스트(`transition-rules.spec.ts`)가 확인한다.
  - 모델 정책에 막힌 전이는 빼지 않고 `blockedReason`으로 준다(화면이 비활성 버튼과 이유를 보여 준다). 예: 재검수 필수 모델(SN-200)의 RETURNED → IN_STOCK.
  - 배정·배정 취소·출고·검수는 일반 전이 API가 아니라 전용 API라 `actions`(`allocate`·`cancelAllocation`·`ship`·`inspect`)로 따로 준다. `allowedTransitions`는 MANUAL만.
  - 상세 응답에 `modelName`·`merchantName`·`statusChangedAt`도 싣는다(목록 항목에도 `statusChangedAt`).
- 결과·대가: 응답이 커진다(전이 0~2개 + 작업 4개). 화면은 상세를 다시 읽어야 바뀐 버튼을 안다(쓰기 성공 뒤 무효화). 서버는 여전히 요청마다 다시 검사한다 — 화면 값은 안내일 뿐이다(`terminal-detail.e2e`: 막혔다고 준 전이를 보내면 422 `INVALID_TRANSITION`, 허용한다고 준 전이는 200).
- 다시 볼 조건: 권한(작업자별 허용 전이)이 생기면 같은 자리에서 작업자를 넣어 계산한다.
- 보탬(Task 3): 규칙 이름도 서버가 준다 — `GET /anomaly-rules`(규칙 순서대로 이름·기준일, env로 바뀌는 기준일까지, 가맹점 없음 규칙은 기준일 null — `ruleThresholdDays`), 이상 항목 `ruleLabel`, VAN 결과 `kindLabel`. 레이블은 decisions/0037의 상수 파일 하나(`anomaly-labels.ts`·`van-labels.ts`)를 알림·리포트·API가 같이 쓴다. 화면에는 단말기 상태·출처·택배사처럼 값이 바뀌지 않는 표시용 이름표만 둔다.
