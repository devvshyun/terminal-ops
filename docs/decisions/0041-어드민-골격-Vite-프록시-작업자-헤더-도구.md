# 0041. 어드민 골격 — Vite 프록시, 작업자 헤더, 프런트 도구

- 날짜 / 관련 기능: 2026-10-27 / 어드민 전체(설계안 4장 "어드민 화면 (React)", 6장 `apps/admin`)
- 상황: 브라우저가 api(3000)를 부르는 방식, `X-Operator`(decisions/0001)를 사람이 쓰는 화면에서 넣는 방식, 프런트 도구·버전, 스타일을 정해야 한다. Day 5 리뷰 이월 "Day 6 준비".
- 선택지(출처)
  1. api에 CORS 열기(`app.enableCors`) — 운영에서도 열어야 하는지, 허용 출처 관리가 생긴다.
  2. **Vite 개발 서버 프록시(`/api` → 3000, rewrite로 앞의 `/api`를 뗌)** — 같은 출처라 CORS가 필요 없다. 운영은 같은 모양의 역프록시(범위 밖).
  3. api가 정적 파일까지 서빙 — 빌드 결과를 api에 묶는다.
- 선택지(작업자)
  1. 요청마다 입력 — 번거롭고 빠뜨린다.
  2. **위쪽 입력 → localStorage(`terminal-ops.operator`) → `api()`가 모든 요청에 `X-Operator: encodeURIComponent(이름)`**(비면 쓰기 버튼 끔). 저장소 구독은 `useSyncExternalStore`(Provider 없음). 규칙은 서버와 같다(1~50자, `system:` 금지).
  3. 로그인 — 인증은 범위 밖(decisions/0001).
- 선택지(도구)
  - 화면: React 19 + Vite(설계안).
  - 라우터: **react-router 8(선언형 `Routes`/`Route`)** — 데이터 라우터의 loader·action은 TanStack Query와 겹쳐 쓰지 않는다. TanStack Router(타입 경로)는 화면 11개에 과하다. `react-router-dom` 없이 `react-router` 하나에서 `BrowserRouter`·`MemoryRouter`·`NavLink`를 가져온다.
  - 서버 상태: **TanStack Query**(캐시·무효화·무한 목록). 직접 `useEffect` + `fetch`는 로딩·오류·다시 읽기를 화면마다 다시 짠다. SWR은 무한 목록·변이 API가 약하다. 기본값: 4xx는 재시도 안 함(연결 실패·5xx만 한 번), 창 포커스 때 다시 읽지 않음, staleTime 5초.
  - 테스트: **Vitest + Testing Library + jsdom**(api와 같은 Vitest). Playwright는 브라우저 내려받기가 필요해 이번엔 쓰지 않는다(실제 화면은 컨트롤러가 내장 브라우저로 본다). 가짜 api는 `fetch`를 `vi.stubGlobal`로 바꾸는 `mockApi`(경로 패턴, 부른 요청 기록, 없는 경로는 404).
- 선택지(스타일)
  1. **전역 CSS 한 장**(색은 변수).
  2. CSS Modules — 화면이 작아 클래스 충돌이 없다.
  3. Tailwind·UI 라이브러리 — 의존성·설정이 늘고 학습 범위 밖.
- 결정: 위 굵은 것. TypeScript는 api와 같은 6.0 계열(6.0.3; 7.0은 Go로 다시 쓴 판이라 api와 맞추지 않으면 두 컴파일러를 쓰게 된다). 버전은 정확히 고정(`--save-exact`)하고 출시 2주 미만(2026-10-13 이후)은 피한다(Day 2 원칙). 출시일은 `npm view <패키지> time --json`의 그 버전 줄(UTC)로 확인했다.

- 시각: `formatKst`는 api `common/kst.ts`와 같은 규칙(UTC+9, 밀리초 버림, 'YYYY-MM-DD HH:mm:ss KST'). 화면 시각은 모두 KST로만 보여 준다.

- 결과·대가: 개발 서버 없이 `dist`만으로는 api를 부를 수 없다(운영 배포 때 역프록시 필요). 작업자 이름은 브라우저마다 따로다(인증 아님, 누구나 바꿀 수 있다). 시각 형식 함수가 api와 화면 두 곳에 있다(같은 테스트 값으로 맞춘다). `globals`를 켜지 않아 `afterEach(cleanup)`을 setup에 직접 둔다.
- 다시 볼 조건: 화면을 운영에 내보낼 때(역프록시·CORS·인증), 화면이 수십 개로 늘어 스타일 충돌이 생길 때(CSS Modules).

### Task 5 보탬 (단말기 화면)
- 목록 조건은 주소에(`useSearchParams`) — 뒤로 가기·새로고침·링크 공유가 같은 목록을 보여 준다. 입력 중인 값은 상태(draft), 검색 버튼을 눌러야 주소가 바뀐다(타자마다 요청하지 않는다).
- 쓰기 뒤에는 응답으로 화면을 고치지 않고 관련 쿼리를 무효화해 다시 읽는다(응답 모양이 API마다 달라도 화면은 상세 하나만 믿는다). 낙관적 갱신은 하지 않는다(전이 결과는 서버 규칙·version이 정한다).
- version 충돌은 자동으로 다시 보내지 않는다 — 다른 사람이 무엇을 바꿨는지 운영자가 보고 다시 판단한다(decisions/0004).

### Task 4 리뷰 반영 (탭 간 동기화·재시도 판정)
- 작업자 이름은 `window`의 `storage` 이벤트를 구독해 다른 탭의 변경을 따라간다(처음 결정은 "탭마다 따로"였고 대가에 적었다 — 한 탭에서 이름을 바꿔도 다른 탭의 쓰기가 옛 이름으로 나가 이력이 어긋나는 일을 막으려고 바꿨다). 이벤트의 `key`가 이 키이거나 `null`(저장소 전체 비움)일 때만 저장소에서 다시 읽고, 규칙에 어긋난 값이면 빈 이름이 된다. 버린 선택지: 탭 간 불일치를 대가에 한 줄 적고 두기(구현은 7줄이고 이력의 작업자가 틀리는 쪽이 더 비싸다).
- 조회 재시도 판정을 `shouldRetry(count, error)`로 빼 단위 테스트한다(4xx 안 함, 5xx·연결 실패 한 번).
- 이름 입력칸 `maxLength`는 서버 규칙과 같은 50(60이면 51~60자를 쓰게 두고 저장 때 막는다).

### Task 6 보탬 (박스 스캔)
- scanId는 화면이 박스마다 만들고(`crypto.randomUUID`) 결과를 받을 때까지 지킨다 — 다시 보내기가 서버의 멱등(decisions/0020)을 그대로 쓴다. 다시 보낼지 고칠지는 오류 종류로 가른다(처리 중 409 `SCAN_IN_PROGRESS`·5xx·연결 실패는 같은 scanId, 4xx 입력 오류는 새 scanId). 보낸 박스의 목록을 잠가(readOnly) "같은 scanId에 다른 내용"(422 `SCAN_ID_REUSED`)을 화면에서 만들지 않는다.
- 버린 선택지: 오류마다 scanId를 새로 만들기(응답만 못 받은 경우 서버에서 이미 처리됐는데 새 scanId로 또 보내 같은 박스가 두 번 처리되어 멱등을 깬다), 보낸 뒤에도 목록 편집 허용(SCAN_ID_REUSED를 운영자가 만나게 된다).
