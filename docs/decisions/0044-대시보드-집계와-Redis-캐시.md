# 0044. 대시보드 집계는 Redis에 30초 캐시한다 — TTL만, 프로세스 안 single-flight

- 날짜 / 관련 기능: 2026-10-27 / 어드민 처음 화면(F11 주변, 설계안 5장 Redis ⑤ "대시보드 캐시")
- 상황: 처음 화면에 운영 현황 숫자 일곱 묶음을 둔다(상태·모델별 단말기, 운영 중 접속 상태, 열린 이상 규칙별, 진행 중 배포, 열린 A/S, 최근 VAN 대조, 이번 주 전이). 모두 DB 집계다. "이번 주 전이 수"는 이력 표를 훑는다 — 주간 리포트처럼 occurred_at 인덱스를 두지 않기로 했다(decisions/0036). 처음 화면은 운영자가 가장 자주 여는 화면이라 열 때마다 이 집계를 돌리면 이력이 커질수록 MySQL이 같은 일을 되풀이한다.
- 왜 MySQL이 아니라 Redis인가(CLAUDE.md 원칙): 값은 "한 번 집계한 결과 JSON 하나"이고 몇십 초만 의미가 있다. MySQL 요약 표에 쓰면 쓰기·정리 job이 생기고 TTL이 없다. 앱 메모리 캐시는 api 프로세스마다 따로라 프로세스 수만큼 집계하고, 재시작하면 사라진다. Redis는 이미 있고(decisions/0026 공용 연결) `SET … PX`로 만료까지 한 명령이다.
- 선택지:
  1. 캐시 없이 매번 집계 — 단순. 하지만 요청마다 이력을 훑고, 동시 요청이면 MySQL 연결 풀(10)을 집계가 다 쓴다(숫자는 실험 0015).
  2. Redis 캐시 + 전이마다 무효화 — 숫자가 늘 최신. 하지만 전이는 가장 잦은 쓰기이고(스캔 한 박스에 수백 건), 무효화가 잦으면 캐시가 거의 늘 비어 1과 같아진다. 전이 서비스(상태 변경 한 곳)에 대시보드 지식이 들어간다.
  3. Redis 캐시 + TTL만 + 화면에 집계 시각 — 30초 늦을 수 있다. "운영 현황"은 그 정도 늦어도 판단이 바뀌지 않는다. 화면이 "N초 전 기준"을 보여 주고 새로고침(refresh=true)으로 바로 다시 집계한다.
  4. 주기 job이 미리 집계해 두기(warm) — 아무도 안 볼 때도 돈다. 주기 작업이 하나 더 는다.
- 결정: 3. 키 `<QUEUE_PREFIX>:dash:summary`(테스트·개발 접두사가 섞이지 않음), 값은 집계 + `cachedAt`(집계 시각) JSON, `SET … PX DASHBOARD_CACHE_TTL_MS`(기본 30초). 응답에 `fromCache`.
  - 동시 미스(캐시가 빈 순간 여러 요청): **프로세스 안 single-flight** — 도는 집계의 Promise를 함께 기다린다. Redis `SET NX` 잠금은 두지 않는다: api 프로세스는 한두 개라 최악에도 프로세스 수만큼만 집계하고, 잠금이면 기다리는 쪽의 폴링·잠금 만료(집계가 죽었을 때)를 따로 다뤄야 한다. "그냥 허용"은 동시 미스마다 집계가 요청 수만큼 돌아 버렸다(숫자는 실험 0015).
  - Redis 읽기·쓰기 실패는 경고만 남기고 캐시 없이 집계해 준다(대시보드가 Redis 때문에 멈추지 않게).
  - 새로고침(`refresh=true`)은 진행 중인 일반 집계에 **합류하지 않고** 새로 집계한다(Task 3 리뷰 Important — 합류하면 새로고침을 누르기 전에 시작한 옛 집계를 받는다). 동시에 온 새로고침끼리는 집계 하나(`refreshInflight`)를 함께 쓴다. 새로고침이 도는 동안 캐시가 빈 일반 요청은 그 새로고침에 합류한다 — 더 새로운 값이라 손해가 없고 집계가 하나 덜 돈다. 그래서 일반 집계와 새로고침이 겹치면 이 프로세스에서 집계가 최대 둘 돈다.
  - 겹친 두 집계 중 먼저 시작한 쪽이 늦게 끝나면 새 값을 옛 값으로 덮을 수 있어, 이 프로세스가 마지막으로 캐시에 쓴 집계의 시작 시각보다 먼저 시작한 집계는 캐시에 쓰지 않는다(응답으로는 준다). 프로세스가 여럿이면 다른 프로세스의 옛 집계가 덮을 수 있다 — 길어야 TTL 한 번.
  - 캐시가 빈 걸 확인한 뒤 집계를 만들기 직전에 캐시를 한 번 더 읽지는 않았다(선택 리뷰 항목). 읽기와 inflight 확인 사이에 다른 요청의 집계가 끝나 캐시가 찬 경우에만 집계가 한 번 더 돈다 — 드물고 결과가 틀리지 않는다.
  - 집계는 주간 리포트와 같은 방식: 한 REPEATABLE READ 읽기 전용 트랜잭션, 시각은 파라미터(SQL NOW() 안 씀), 접속 상태는 리포트와 같은 창(오프라인 기준 + 스냅샷 주기).
  - 실험용 인자: `summary({ cache: false, singleFlight: false })`(실험 0013의 strategy 인자처럼 기본값이 운영 동작).
- 결과·대가: 처음 화면 숫자가 늦을 수 있다(화면에 표시). `cachedAt`은 집계를 **시작한** 시각이라 화면이 받는 값의 최대 나이 = TTL(30초) + 집계 시간이다. Redis가 죽어 있으면 요청마다 Redis 읽기·쓰기가 실패할 때까지 기다린 뒤 집계한다(`maxRetriesPerRequest: 1` — 그 지연은 재지 않았다). 프로세스가 여럿이면 캐시가 빈 순간에 프로세스 수만큼 집계한다. 새로고침을 여러 사람이 동시에 누르면 프로세스마다 한 번씩 다시 집계한다.
- 다시 볼 조건: api 프로세스가 여러 개로 늘어 동시 미스가 문제가 되면 `SET NX` 잠금. 숫자가 실시간이어야 하는 요구가 생기면 이벤트로 카운터를 갱신(Redis HINCRBY)하는 쪽을 다시 본다. 이력이 수천만이 되어 30초마다의 집계도 무거우면 주기 warm 또는 이력 occurred_at 인덱스를 다시 잰다(decisions/0036).
