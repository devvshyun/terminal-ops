# 0045. 상태 조건 단말기 목록에 (status, id) 인덱스를 더하지 않는다

- 날짜 / 관련 기능: 2026-10-27 / F1 (decisions/0039 다시 볼 조건, 실험 0016)
- 상황: 단말기 목록 `?status=` 1쪽은 `where status = ? order by id desc limit 20`이다. 실험 0013에서 상태 조건이 PK 역순으로 읽으며 거르는 것을 봤고, decisions/0039는 "드문 상태면 20행을 채울 때까지 많이 읽으니 자주 보면 (status, id)를 잰다"고 적었다.
- 선택지:
  1. `(status, id)` 인덱스를 더한다 — 장점: 어떤 상태든 그 상태의 끝에서 20행만 읽는다. 단점: terminal 행의 상태가 바뀔 때마다 보조 인덱스 항목이 하나 더 옮겨 간다(전이는 가장 잦은 쓰기), 크기.
  2. 지금 그대로(`(status, status_changed_at)` + PK) — 장점: 쓰기 비용 없음. 단점: 옵티마이저 선택에 기댄다.
  3. `(status, status_changed_at)`을 `(status, id)`로 바꾼다 — F4 이상 찾기가 상태별 "N일 넘게" 범위를 못 쓴다(decisions/0034). 버림.
- 결정: 2. 실험 0016(단말기 10만): 드문 상태(DEFECTIVE 450대, DISPOSED 50대)는 옵티마이저가 이미 `(status, status_changed_at)` 인덱스로 찾아 20행만 정렬했고, 흔한 상태(IN_SERVICE 약 1만·RECEIVED 약 5천 대)는 PK 역순으로 175·396행만 읽었다. 인덱스를 더해도 계획이 바뀐 것은 IN_SERVICE 하나뿐이고 목록 p50은 모두 1.73~2.89ms 안에서 차이가 0.3ms 이하(IN_SERVICE 2.89 → 2.84ms)로 측정 흔들림 수준이었다. 사전에 정한 채택 기준(p50 2배 이상 그리고 1ms 이상 감소)에 해당하는 상태가 없다. 한 건 UPDATE 1,000번 평균 2,982ms 대 3,164ms(+6.1%), INSERT 2,987ms 대 3,110ms(+4.1%), 보조 인덱스 +1.46MB(14.56 → 16.02MB).
- 결과·대가: 옵티마이저가 고르는 경계(몇 대부터 PK 역순으로 바뀌는지) 근처의 상태에서는 수천 행을 읽을 수 있다 — 10만 대에서는 그래도 1~2ms 안쪽(실험 0013 끝쪽 offset 비용과 같은 자릿수). 그 경계는 재지 않았다.
- 다시 볼 조건: 단말기가 수백만이 되어 경계 근처 상태의 목록이 느려지면, 또는 상태 조건 + 다른 정렬(최근 바뀐 순 등)이 생기면 다시 잰다. 실험 파일 `test/experiments/status-index.spec.ts`를 그대로 돌리면 된다.
