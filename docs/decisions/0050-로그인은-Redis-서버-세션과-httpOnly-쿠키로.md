# 0050. 로그인은 Redis 서버 세션과 httpOnly 쿠키로 한다

- 날짜 / 관련 기능: 2026-10-28 / 보강 2(로그인), 어드민. decisions/0001을 대체한다
- 상황: 사람이 로그인하고, 서버가 요청마다 누구인지·어떤 역할인지 알아야 한다. 화면(어드민, 앞으로 매장·현장·관제 화면)은 Vite 프록시로 api와 같은 출처다(decisions/0041). 비교 기준은 로그아웃이 바로 되는가, 계정을 막으면(사용 중지) 바로 끊기는가, 역할을 바꾸면 바로 반영되는가, 구현·의존성, 토큰 탈취 위험.
- 선택지:
  1. JWT(액세스 15분 + 리프레시) — 장점: 서버가 상태 없이 서명만 검증, 다른 출처·모바일에 쉽다. 단점: 로그아웃·사용 중지·역할 변경이 액세스 토큰 만료까지 남는다. 바로 막으려면 거부 목록(denylist)이나 토큰 버전을 서버(Redis·DB)에 둬야 해 결국 상태가 생긴다. 리프레시 토큰 회전·저장, 라이브러리(`@nestjs/jwt`·`jose`) 의존성. 토큰을 화면 JS가 들고 있으면 XSS에 털리고, 쿠키에 넣으면 CSRF 문제는 세션과 같다
  2. **서버 세션 + httpOnly 쿠키** — 장점: 로그아웃 = 키 삭제, 사용 중지·역할 변경 = 그 계정 세션 일괄 삭제가 바로 반영된다. 화면 JS가 토큰을 못 읽는다. 같은 출처라 쿠키가 그대로 간다. 의존성 0. 단점: 요청마다 저장소 조회 한 번, 다른 출처 클라이언트에는 CORS·SameSite 설정이 필요
  - 세션 저장소: MySQL 테이블(요청마다 SELECT, 만료 행 청소 작업 필요) 대 **Redis**(요청마다 읽기 한 번 — `GETEX`로 읽으며 TTL을 늘림, 만료는 TTL이 알아서). 잃어도 다시 로그인하면 되는 값이라 Redis의 휘발성이 문제가 되지 않는다(CLAUDE.md "Redis를 쓰는 이유")
- 결정: 2 + Redis.
  - 토큰 32바이트 무작위(base64url) = 쿠키 `sid`(HttpOnly, SameSite=Strict, Path=/, Secure는 `SESSION_COOKIE_SECURE`). Redis 키는 토큰의 SHA-256(`<접두사>:sess:<hex>`) — Redis 내용이 새어도 쿠키를 만들 수 없다. 로그인마다 새 토큰(세션 고정 공격 없음).
  - 세션 값 = 계정 id·로그인 아이디·표시 이름·역할·가맹점 id·코드 + 세대값(`gen`)·만든 시각(`createdAt`)(JSON). 요청마다 MySQL을 읽지 않는다. 대신 계정 API가 역할·가맹점·비밀번호를 바꾸거나 사용 중지하면 `<접두사>:sess-of:<계정 id>` SET에 모아 둔 그 계정의 세션을 모두 지운다(Task 5).
  - **계정 세대값**(Task 2 보안 리뷰 반영): `<접두사>:sess-gen:<계정 id>` 정수. 일괄 끊기(`destroyAllFor`)는 이것을 **먼저** `INCR`한 뒤 색인의 세션을 지운다. 로그인은 계정 행을 읽기 **전에** 세대값을 읽어 세션에 넣고, 세션 읽기(Lua 스크립트 하나: 세션 값·세대값 비교·절대 만료·TTL 늘리기)는 세대값이 다르면 세션을 지우고 401. 그래서 "로그인이 옛 역할을 읽은 뒤·세션을 만들기 전"이나 "끊기가 색인을 읽은 뒤·지우기 전"에 생긴 세션도 살아남지 못한다(처음 버전은 SMEMBERS → DEL 사이에 생긴 세션을 놓쳤다). 세대값·색인 키에는 TTL을 붙이지 않는다(세대값이 만료돼 0으로 돌아가면 옛 세대 세션이 살아날 수 있고, 색인이 세션보다 먼저 사라지면 끊기가 세션을 못 찾는다). 남는 틈: 세션 읽기를 이미 통과한 **처리 중 요청 1건**은 옛 역할로 끝날 수 있다(다음 요청부터 401).
  - 유휴 만료 8시간(`SESSION_IDLE_TTL_MS`), 요청마다 늘린다. **절대 만료** 7일(`SESSION_MAX_AGE_MS`, Task 2 보안 리뷰 반영): 로그인부터 이만큼 지나면 쓰고 있어도 끝난다(TTL도 남은 시간보다 길게 늘리지 않는다). 쿠키에는 만료를 두지 않는다(브라우저 세션 쿠키, 서버가 정한다).
  - 세션 쿠키를 들고 다시 로그인하면 성공한 뒤 옛 세션을 지운다(한 브라우저에 세션 둘을 남기지 않는다). 지우기가 실패해도(Redis 순간 오류) 로그인은 200과 새 쿠키로 끝내고 경고 로그만 남긴다 — 옛 세션은 유휴 만료로 사라진다(보강 2 마감, Task 4 보안 리뷰).
  - `POST /auth/login`은 JSON 본문(`Content-Type: application/json`)만 받는다 — 아니면 415(본문 검증보다 먼저, 가드). HTML 폼은 JSON을 보낼 수 없어 다른 사이트의 폼이 이 브라우저를 공격자 계정으로 로그인시키는 로그인 CSRF를 SameSite와 별도로 막는다. Origin 검사도 고려했지만, 같은 출처 프록시·curl·테스트가 Origin을 안 보내 "없으면 허용"이 돼야 해서 JSON 강제 쪽이 단순하다. 판단은 `req.is('application/json')`이라, JSON 헤더에 빈 본문이어도 `Content-Length: 0`이 붙어 있으면 본문이 있는 것으로 보고 통과한 뒤 빈 객체가 검증에서 400이 된다(Node http 클라이언트로 헤더만 보내고 본문 없이 끝낸 요청도 400이었다 — 빈 본문으로 415가 나는 경우는 확인하지 못했다. type-is 소스상 `Content-Length`·`Transfer-Encoding`이 모두 없으면 `req.is()`가 null이라 415일 것이나 추측이다). 리뷰는 415를 예상했으나 테스트로 400을 확인해 그대로 둔다 — 어느 쪽이든 쿠키는 나가지 않는다(auth.e2e).
  - 로그인 실패 제한: 아이디별 Redis 카운터(`<접두사>:login-fail:<정규형 아이디>`). 첫 시도부터 15분(`LOGIN_LOCK_MS`) 창에 5번(`LOGIN_MAX_FAILURES`)까지만 비밀번호를 본다. 그 뒤는 창이 끝날 때까지 429 `LOGIN_LOCKED`(맞는 비밀번호여도). 성공하면 카운터를 지운다. 틀린 이유(없는 아이디·틀린 비밀번호·사용 중지)는 모두 같은 401 `LOGIN_FAILED`.
    - **시도를 먼저 예약한다**(Task 2 보안 리뷰 반영): 요청 맨 앞에서 `MULTI INCR + PEXPIRE … NX`로 번호를 받고, 번호가 한도를 넘으면 비밀번호를 보지 않고 429. 실패는 예약이 그대로 남는 것, 성공은 DEL. 처음 버전은 "읽고 → 검증하고 → 틀리면 INCR"이라 같은 아이디로 동시에 몰리면 모두 0을 읽고 검증까지 갔다(e2e: 동시 10건 → 401 10개였다. 지금은 401 ≤ 5).
    - **정규형 아이디**(Task 2 보안 리뷰 반영): 테이블 collation `utf8mb4_0900_ai_ci`는 `op1`·`óp1`·`ｏｐ１`을 같은 계정으로 찾는데 카운터 키는 글자가 달라 따로 셌다(변형마다 5번씩). 그래서 로그인 DTO가 아이디를 ASCII `[A-Za-z0-9._-]{3,50}`로 막고(악센트·전각·공백은 400, 카운터에 안 닿는다) 서비스가 NFKC + 소문자로 접은 값으로 카운터 키를 만들고 계정을 찾는다. 계정 만들기(Task 5)도 같은 글자만 받고(`LOGIN_ID_INPUT` 공유), 대문자는 받아 소문자로 저장한다(`AuthService.normalizeLoginId`) — 로그인이 소문자로 접어 찾으므로 저장된 아이디가 대문자를 가지면 그 계정으로 로그인할 수 없게 된다. 대소문자만 다른 아이디는 collation이 같게 봐 409 `DUPLICATE`.
  - **`destroyAllFor`는 반드시 DB 커밋 뒤에 부른다**(Task 4 보안 리뷰 → Task 5): 트랜잭션 안에서 부르면 세대값 INCR은 이미 보이는데 역할·중지 변경은 아직 커밋 전이라, 그 사이 로그인이 새 세대값을 읽고도 옛 행(옛 역할)을 읽어 새 세대값의 옛 권한 세션을 만들 수 있다. 커밋 뒤에 부르면 새 세대값을 읽은 로그인은 이미 새 행을 읽는다. 대가: 좁은 틈에 로그인이 200을 받고 바로 다음 요청에서 401을 받을 수 있다(커밋과 INCR 사이에 읽은 옛 세대값 세션이 무효가 됨) — 거부하는 쪽으로 틀리는 안전한 방향이다. `AccountService.update`가 `transactional` 콜백이 끝난 뒤에 부르고, e2e가 호출 순간 다른 연결에서 새 상태가 보이는지 확인한다.
  - API: `POST /auth/login`(공개, 200 MeView + Set-Cookie), `POST /auth/logout`(204, 쿠키 지움), `GET /auth/me`(MeView).
- 다룬 보안 범위와 다루지 않은 범위(학습·로컬 시연용):
  - 다룸: 비밀번호 해시(0051), httpOnly(XSS가 토큰을 못 읽음), SameSite=Strict(다른 사이트에서 시작한 요청에 쿠키가 붙지 않음 — CSRF), 토큰 해시 저장, 실패 제한, 로그인마다 새 토큰.
  - 다루지 않음: CSRF 토큰(SameSite에만 기댄다 — `localhost`의 다른 포트는 같은 사이트로 본다), HTTPS(로컬 http, Secure 기본 꺼짐), IP별 실패 제한(아이디별만 — 남이 일부러 틀려 15분 잠글 수 있다. 또 아이디마다 창당 5번은 scrypt를 돌리므로, 많은 아이디로 동시에 몰면 libuv 스레드 풀(기본 4개)이 해시로 차서 다른 요청의 crypto·파일 작업이 밀린다 — IP·전체 동시 해시 수 제한이 없는 대가), 비밀번호 변경·재설정 화면, 2단계 인증, 동시 세션 수 제한.
- 결과·대가: 요청마다 Redis 명령 하나(세션 읽기 Lua 스크립트 — 처음엔 GETEX, 세대값·절대 만료 검사를 넣으며 스크립트로 바꿨다). 로그인한 사람의 역할은 세션에 고정돼, 계정 행을 SQL로 직접 고치면 세션이 끊길 때까지 옛 역할이다(계정 API를 쓴다). 계정 색인 SET·세대값은 TTL 없이 남고(계정마다 키 둘), 색인의 끝난 세션 해시는 다음 로그인 때 치운다.
- 다시 볼 조건: 화면이 다른 출처로 나가거나 모바일 앱이 사람 API를 부를 때(토큰 방식 또는 SameSite=None + CSRF 토큰), 실제 서비스로 내보낼 때(HTTPS·Secure, IP·동시 해시 수 제한), Redis 클러스터로 갈 때(세션 읽기 스크립트가 KEYS로 넘기지 않은 세대값 키를 읽는다 — 해시 태그로 같은 슬롯에 두거나 세대값을 쿠키·키에 넣는 방식으로).
