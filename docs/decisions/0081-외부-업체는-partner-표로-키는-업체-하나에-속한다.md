# 0081. 외부 업체는 partner 표로, 키는 업체 하나에 속한다

- 날짜 / 관련 기능: 2026-10-29 / 보강 7, 외부 연동(decisions/0054)
- 상황: 키(`partner_api_key`)에는 업체 이름이 글자(`name`)로만 있다. 개발자센터는 "이 업체의 키들", "이 업체의 호출"을 보여 줘야 하는데, 글자가 조금만 달라도(띄어쓰기) 다른 업체가 된다. 호출 로그(0082)도 업체로 묶어 본다.
- 선택지:
  1. 키 이름 글자로 묶기 — 표가 늘지 않는다. 오타 하나로 업체가 갈리고, 업체에 메모·코드를 둘 곳이 없다
  2. **`partner` 표(code unique·name·memo) + 키에 `partner_id`(필수, FK)** — 키의 `name`은 "어디에 쓰는 키인지" 이름표로 바꾼다
  3. 2에 `partner_id`를 null 허용으로 — 옛 키를 건드리지 않지만 "업체 없는 키"가 영원히 남고, 화면·로그가 그 경우를 따로 다뤄야 한다
- 결정: 2.
  - 업체 코드 `^[A-Z0-9-]{2,20}$`, 같은 코드는 409 `DUPLICATE`(unique 위반을 전역 필터가 바꾼다), 이름 1~50자(공백만 안 됨), 메모 0~200자. 지우는 API는 없다 — 키를 폐기한다.
  - `POST /admin/partner-keys`가 `partnerId`를 받는다(없으면 400, 없는 업체 404). 기존 e2e는 업체를 먼저 만들도록 바꿨다(사내 API라 바꿀 수 있다 — 화면은 아직 없었다). `GET /admin/partner-keys?partnerId=`로 거른다. 키 응답에 `partnerId·partnerCode·partnerName`.
  - 업체 목록의 키 수: 살아 있는 키(폐기 안 됐고 만료 전 — 키 확인과 같은 기준, 시각은 api 시계)와 전체, 마지막 사용 = 그 업체 키들의 `last_used_at` 중 가장 늦은 것. 키 표를 업체별로 한 번에 세는 SQL 한 문장(업체 수만큼 쿼리하지 않는다).
  - 마이그레이션(`Migration20261029061906`): 열을 null 허용으로 넣고 → 키 이름마다 업체를 만들어(코드 `P-1, P-2 …` 처음 발급 순, `created_by = system:migration`) 잇고 → not null·FK. 테스트 DB에서 키 셋(이름 둘)으로 up → 업체 2개·키 3개 연결 확인 → down(키 이름 그대로) → up → `check` "최신 상태"(devlog 2026-10-29).
  - 시드: 시연 업체 `DEMO`(데모 연동 업체(시연)) 아래 시연 키(이름표 "시연 키").
- 결과·대가: 보강 7 전에 시드한 개발 DB는 시연 키가 이미 있어 마이그레이션이 만든 `P-1`(이름 = 옛 키 이름) 아래 남고 DEMO 업체는 생기지 않는다(시드는 키가 있으면 건너뛴다). 이름 비교는 표의 collation(대소문자·악센트 무시)이라 대소문자만 다른 옛 이름은 한 업체로 합쳐진다. 키 이름 칸의 뜻이 바뀌었다(업체 이름 → 이름표) — 옛 키는 이름표가 업체 이름과 같다.
- 다시 볼 조건: 업체가 수백 곳이 되어 목록에 쪽 나누기가 필요할 때, 업체를 멈추는(모든 키를 한 번에 막는) 기능이 필요할 때.
