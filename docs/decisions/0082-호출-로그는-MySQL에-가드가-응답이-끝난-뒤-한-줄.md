# 0082. 호출 로그는 MySQL에, 가드가 응답이 끝난 뒤 한 줄

- 날짜 / 관련 기능: 2026-10-29 / 보강 7, 외부 연동(decisions/0054가 이 묶음으로 미룬 것)
- 상황: 외부용 API(`/partner/v1`)를 누가 언제 무엇을 불렀고 어떻게 끝났는지를 개발자센터에서 업체별·키별로 봐야 한다. 지금은 키의 `last_used_at`(1분에 한 번 갱신)만 있다.
- 선택지(어디에):
  1. **MySQL 표 `partner_api_call`** — 업체·키 외래키, 최근부터 키셋 목록(0039)이 다른 이력 화면과 같다. 쌓이는 양은 외부 호출 수만큼
  2. Redis(스트림이나 리스트, 길이 제한) — 쓰기가 가볍다. 하지만 업체별·키별로 거르려면 키를 업체마다 따로 두거나 다 읽어 걸러야 하고, 재시작·만료 정책에 따라 사라진다. 이 기록은 "언제 무엇이 거절됐나"를 나중에 묻는 감사 성격이라 남아야 한다. CLAUDE.md "Redis는 필요한 자리에만" — 여기는 MySQL로 충분하다
  3. 파일 로그(접근 로그) — 화면에서 거르고 쪽 나누기가 어렵다
- 선택지(어디서 쓰나):
  1. 인터셉터 — 가드가 던진 예외(403 scope 밖)는 인터셉터까지 오지 않아 "왜 거절됐나"를 놓친다
  2. 미들웨어 — 키 확인(가드) 전이라 어느 업체인지 모른다. 키를 두 번 확인하게 된다
  3. **AuthGuard의 partner 분기에서 키를 알아본 뒤 `res.once('finish')`** — scope 검사(403)보다 먼저 걸어 403·404·200·5xx가 모두 남는다. 걸린 시간은 가드 시작(키 확인 포함)부터 응답 끝까지
- 결정: 1 + 3.
  - 401(키 없음·모양 틀림·해시 다름·폐기·만료)은 남기지 않는다 — 어느 업체인지 모르고, 접두사만 맞춘 요청을 남기면 남의 키 접두사로 기록을 채울 수 있다.
  - 쓰기는 기다리지 않는다(`record` → `insert().catch(warn)`). 응답은 이미 나갔고, 기록 실패(DB 끊김)가 외부 업체 응답을 바꾸지 않는다(e2e: `insert`를 한 번 실패시켜도 200).
  - 경로는 쿼리를 뺀 `req.path`를 200자에서 자른다(쿼리에 무엇이 들어올지 모른다). 메서드·상태 코드·걸린 시간(ms)·시각(밀리초).
  - 인덱스 (partner_id, id)·(key_id, id) 둘. 외래키 열 하나짜리 인덱스는 두지 않는다(`@ManyToOne({ index: false })`) — 복합 인덱스의 앞부분이 외래키 검사도 맡는다(실험 0019).
  - 목록 `GET /admin/partner-calls?partnerId=&keyId=&beforeId=&limit=`(ADMIN, 기본 50·최대 100), 업체 코드·키 접두사는 select-in.
- 결과·대가: 클라이언트가 응답 전에 끊으면('finish' 없이 'close'만) 남지 않는다. 기록 쓰기가 실패한 호출은 빠진다(다시 넣지 않는다, 경고 로그 한 줄). 외부 호출마다 INSERT 한 번(보조 인덱스 둘) — 쓰기 비용은 재지 않았다. **보관 기간 정리 작업이 없다** — 표는 계속 자란다(시연 규모에서는 문제없다). 응답 본문·요청 헤더는 남기지 않는다(키가 헤더에 있다).
- 다시 볼 조건: 외부 호출이 초당 수십을 넘어 INSERT가 응답 지연이나 DB 부하로 보일 때(묶어 쓰기·Redis 버퍼), 표가 수백만 줄이 될 때(보관 기간 정리 주기 작업 — 30일, 날짜 파티션).
