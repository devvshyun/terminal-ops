# 0090. 시연 이미지의 api 버전은 빌드 인자로(기본 demo)

- 날짜 / 관련 기능: 2026-10-30 / 보강 9 이어서(시연 리허설 반영)
- 상황: 2026-10-30 로컬 컨트롤러 리허설에서 운영 관제(`apps/console`) 대시보드의 api 버전이 `dev`로 보였다. `env.appVersion`은 `APP_VERSION`이 없으면 `dev`(decisions/0071 "띄우는 쪽이 넣는다")인데, 시연 묶음(0086)이 넣지 않았다. `apps/api/package.json`에는 `version` 필드가 없다.
- 선택지:
  1. **api Dockerfile `ARG APP_VERSION` → `ENV`, compose가 빌드 인자 `${APP_VERSION:-demo}`로** — 값이 이미지에 굳어 "이 이미지가 어느 빌드인가"와 맞는다. migrate·api·worker·demo-seed가 같은 이미지라 한 곳에서 끝난다. 커밋을 보이려면 `APP_VERSION=$(git rev-parse --short HEAD)`로 빌드
  2. compose `environment`에 `APP_VERSION` — 쉽지만 컨테이너 설정이라, 이미지를 다시 빌드하지 않고 값만 바꾸면 실제 코드와 다른 버전을 보여 준다
  3. `package.json`에 `version`을 두고 api가 읽기 — 릴리스마다 버전을 올리는 절차가 이 프로젝트에 없어 늘 같은 값(예 0.0.0)이 된다. 읽는 코드도 늘어난다
  4. 빌드 때 git 해시를 자동으로 — Dockerfile 안에서는 `.git`이 없고(`.dockerignore`), compose 변수는 명령을 실행하지 못한다. 셸 래퍼가 필요하다
- 결정: 1. 기본값은 `demo`(로컬 개발 `dev`와 구별되면 충분하다). `ARG`는 마지막 층에 둬 값이 바뀌어도 `npm ci`·빌드 층 캐시를 그대로 쓴다. Dockerfile의 `ARG` 기본은 `dev` 그대로 — compose 없이 `docker build`하면 지금과 같다.
- 결과·대가: 기본 화면은 `demo`라 어느 커밋인지는 모른다 — 알고 싶으면 4를 손으로(명령 앞에 `APP_VERSION=…`). `.env`에 `APP_VERSION`을 적으면 `env_file`이 실행 때 이미지 값을 덮는다(compose 변수 치환도 `.env`를 읽어 빌드 인자에 같은 값이 들어가므로 보통은 같다). 확인: 이 컨테이너에서 빌드 → `docker run … echo $APP_VERSION` → `demo`, 묶음을 띄워 `GET /api/ops/system`(console 호스트)의 `api.version` = `"demo"`.
- 다시 볼 조건: 릴리스 버전을 매기기 시작하면 3과 함께, CI가 이미지를 만들면 CI가 해시를 빌드 인자로 넣는다.
