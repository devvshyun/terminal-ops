# 0093. 시연 홈을 녹화 재생본으로 GitHub Pages에 올린다

- 날짜 / 관련 기능: 2026-10-30 / 보강 11(시연 홈 공개본)
- 상황: 사용자가 시연 홈을 "pdfHandler처럼"(정적 사이트, GitHub Pages) 누구나 링크로 열어 보게 하고 싶어 했다. 시연 홈은 [실행]마다 api·MySQL·Redis·가상 업체·시뮬레이터를 부른다 — Pages는 정적 파일만 내므로 그대로 올리면 모든 단계가 연결 오류다. 저장소는 공개(public)라 Pages를 무료로 쓸 수 있다
- 선택지:
  1. **녹화 재생** — 시연 묶음에서 7막을 실제로 돌리며 받은 응답을 저장하고, 재생본이 fetch를 받아 그 응답을 녹화 순서대로 낸다. 장점: 보이는 숫자·글이 모두 실제 서버가 낸 것, 서버·비용·비밀 값 노출 없음. 단점: 입력을 바꿔 볼 수 없다, 녹화한 흐름 밖은 "녹화에 없음", 화면이 바뀌면 다시 찍어야 한다
  2. 브라우저 안 가짜 서버 — 상태 전이·배포 중단 규칙을 브라우저에서 다시 구현. 장점: 마음대로 눌러 볼 수 있다. 단점: 약 20개 API의 업무 규칙이 두 군데가 된다 — "상태 변경은 전이 서비스 한 곳"(CLAUDE.md)과 정면으로 부딪히고, 보이는 반응이 실제 백엔드의 것이 아니게 된다
  3. 서버까지 외부 호스팅(클라우드 VM 등) — 장점: 지금과 똑같이 진짜로 동작. 단점: 계정·비용·운영, 시연 계정·키가 공개 인터넷에 열린다, 누가 데이터를 망가뜨리면 다시 띄워야 한다
  4. 영상 — 장점: 가장 싸다. 단점: 눌러 볼 수 없다
- 결정: 1. 이 프로젝트가 보여 주려는 것이 "백엔드가 진짜로 반응한다"인데, 2는 그것을 꾸며 내고 3은 공개 운영 부담이 학습 프로젝트에 맞지 않는다. 1은 반응이 실제였다는 것을 지키면서 링크 하나로 열린다. 재생본 화면에는 녹화본이라는 띠와 "직접 돌려 보려면 docker compose" 안내를 늘 보인다
- 구조:
  - 녹화기 `apps/demo-home/scripts/record.cjs`(Playwright) → `public-replay/recording.json`(재생본이 시작할 때 받아 온다 — 빌드에 묶으면 녹화 전에는 보통 빌드의 타입 검사가 깨졌다) + `public-replay/shots/*.jpg`(다른 화면 사진)
  - 재생본 시작점 `src/replay/main.tsx`(HashRouter, fetch 바꾸기) + `replay.html` + `vite.replay.config.ts` → `dist-replay/`
  - 보통 빌드(시연 묶음 web 이미지)는 그대로 — 재생 코드는 `getReplay()`가 null이면 아무 일도 하지 않는다. 녹화본·사진은 재생본 빌드의 publicDir에만 있다
  - 배포 `.github/workflows/pages.yml`(master에 demo-home이 바뀌면 테스트 → 재생본 빌드 → Pages)
- 결과·대가: 녹화본 파일(수백 KB)과 사진이 저장소에 들어간다. 화면·API가 바뀌면 녹화본이 낡는다 — 다시 찍는 것은 명령 하나지만 사람이 기억해야 한다. 녹화본 안의 시각·시리얼은 녹화한 날의 것이다
- 비밀 값: 녹화기는 응답 본문만 남기고(요청 본문·쿠키·헤더 없음, 로그인·로그아웃 응답 제외), 다 쓴 뒤 시연 비밀번호가 들어 있으면 파일을 쓰지 않고 멈춘다
- 다시 볼 조건: 방문자가 입력을 바꿔 보고 싶어 하는 요구가 크면 3(읽기 전용 공개 서버)을, 녹화본이 자주 낡으면 CI에서 시연 묶음을 띄워 다시 찍는 것을 본다
