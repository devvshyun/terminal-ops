# 0094. 녹화 재생은 "녹화 시계" 하나로 응답을 고른다

- 날짜 / 관련 기능: 2026-10-30 / 보강 11
- 상황: 시연 홈은 실행 단추 말고도 결과 패널이 5초마다 다시 읽고(배송 상태·429 재시도·배포 단계·오프라인), 실행 하나가 여러 요청을 차례로 보낸다(재고 고르기 → 등록 → 검수 → 출고). 재생본은 "지금 이 요청에 어떤 녹화 응답을 낼까"를 정해야 한다. 기다리는 단계(배송 완료 46~52초, 오프라인 판정 96초)는 실제 시간대로 보이면 지루하다
- 선택지:
  1. **녹화 시계** — 녹화 시작부터의 ms 하나를 둔다. GET은 "그 경로의 t ≤ 시계인 마지막 응답". 실행 단추를 누르면 시계를 그 실행 시각으로 옮기고, 끝나면 다음 실행 시각까지 배속(8배)으로 흐르다 멈춘다. 실행 안에서는 GET이 아닌 요청을 녹화 순서대로 꺼내고, 그 사이 GET은 "다음 GET이 아닌 요청 바로 앞" 시각으로 답한다
  2. 단계별 스냅샷 — 단계마다 화면이 읽는 응답 묶음을 한 벌씩 저장. 장점: 단순. 단점: 기다리는 단계의 변화(배송 중 → 완료, ERROR → OK)가 한 장면으로 뭉개진다. 실행 안의 읽기·쓰기 순서를 따로 다뤄야 한다
  3. HAR을 순서대로 재생 — 장점: 녹화가 표준 파일. 단점: 재생본의 폴링 횟수·순서가 녹화 때와 같을 수 없다(브라우저 탭 전환·시간). 순서가 어긋나면 엉뚱한 응답이 나온다. 쿠키·비밀번호가 담겨 지워야 한다
- 결정: 1. 폴링 횟수와 상관없이 "그때의 상태"를 낸다. 기다리는 단계를 시계 배속으로 빨리 감을 수 있고, 실행 사이에 다른 화면에서 한 일(현장 스캔·점주 접수·설치 확인)이 시계가 흐르며 저절로 지나간다
- 녹화 쪽 약속:
  - 같은 GET 경로는 본문이 바뀔 때만 남긴다(크기)
  - 실행마다 `t`(누른 때)와 `end`(끝나고 1.5초 — 결과 패널이 다시 읽은 뒤)를 적는다
  - `end`가 없으면 실행 직후 읽기가 실행 전 값을 낸다 — 처음 엔진(시계를 POST 시각으로만 옮김)이 테스트에서 바로 이것으로 틀렸다
- 결과·대가:
  - 녹화한 횟수만큼만 같은 실행을 누를 수 있다. 더 누르면 안내하고, "처음 상태로"가 시계와 쓴 실행을 되돌린다
  - 뒤 막을 먼저 실행하면 시계가 건너뛰어 그 사이 일이 모두 지난 상태가 된다(되돌아가면 시계도 되돌아간다)
  - 녹화에 없는 경로는 599와 안내 글 — 앱의 오류 상자가 그대로 보인다
- 다시 볼 조건: 막 사이를 자주 오가는 사용 방식이 많으면 막마다 시계를 따로 두는 것을 본다
