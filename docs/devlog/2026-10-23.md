- 일괄 등록 INSERT 정렬(troubleshooting/0011): 정렬을 빼면 반대 순서로 1000행 겹친 두 요청이 9번 모두 `DeadlockException`(unique 인덱스 키를 엇갈려 쥠), 정렬하면 9번 통과. 재시도는 unique 위반·데드락 3번 + 20 ~ 80ms jitter(c38e4d7)
- 스캔 입력 정규화 우회(troubleshooting/0012): 끝에 공백·`\r`이 붙은 시리얼이 명세 검사를 건너뛰고 입고됐다. 입구에서 한 번 다듬고 그 값을 해시·검사·저장 모두에 씀(ae23d7f)
- exceljs 결과 0 수식(troubleshooting/0013): `cell.value` 게터가 falsy result를 버려 결과 0 수식이 빈 글자로 읽혔다. 셀 형식별로 읽고 수식은 `cell.result`(f6517c6)
- JSON_TABLE collation(troubleshooting/0008): JSON_TABLE 열은 연결 collation(mysql2 기본 `utf8mb4_unicode_ci`)을 따라 테이블 열(`utf8mb4_0900_ai_ci`)과 `=` 비교 시 ERROR 1267. 테스트에서는 `schema.refresh()`의 `set names`가 연결 하나만 바꿔 오류를 가렸다. 근본 해결은 연결 collation을 테이블과 맞춘 것(`driverOptions.charset`, decisions/0025, cc3f8fe), 열의 `collate`는 방어로 남김
- 출고 gap 락 데드락(troubleshooting/0014): `recordShipment`의 `UPDATE shipment … WHERE terminal_id=? AND status='IN_TRANSIT'`가 RR에서 `shipment_terminal_id_index` supremum에 X 락을 걸어, 서로 다른 단말기의 출고·교체 출고가 INSERT insert intention에서 데드락 → 500 + 고아 운송장. 잠그지 않고 id를 읽은 뒤 PK로 갱신(b18804d). 안전성은 "운송장을 쓰는 경로는 모두 단말기 행 X 락을 먼저 잡는다"에 기댐
- 잠금 순서 규칙(decisions/0021·0023): 부모 행(발주·단말기)을 자식 INSERT보다 먼저 FOR UPDATE, 여러 단말기는 id 오름차순, 접수 행은 단말기 다음. id 오름차순은 행 잠금 순환은 막지만 gap 락 데드락(0014)은 막지 못한다
