**쿼리·인덱스·실행계획 관련 발견**
- status_changed_at 대 이력 서브쿼리: 규칙 하나가 `(status, status_changed_at)` 범위 하나 — 이력을 단말기마다 훑지 않는 것이 핵심(인덱스를 빼도 10만에서 15~18ms). 대가는 전이 서비스가 상태와 같은 UPDATE에서 갱신해야 한다는 것과 백필
- 중복 인덱스와 ERROR 1553: FK 인덱스는 같은 열로 시작하는 다른 인덱스가 있을 때만 지울 수 있다. MikroORM은 `@ManyToOne({ index: false })`로 FK 인덱스를 안 만든다
- 부분 unique 두 방식: `@Unique({ where })` 함수 인덱스는 `is null` 조건이면 안정적, 글자 상수 조건은 MySQL이 `_utf8mb4` 붙은 글자로 바꿔 저장해 `migration:check`가 계속 다르다고 함 → 생성 열(`running_key`) + unique
- 스테이징 + SQL 집합 비교: 메모리 Map 대신 MySQL 스테이징(PK (run_id, serial_no))과 LEFT JOIN 두 문장, 종류는 TS `classify` 한 곳. 16KB 넘는 INSERT 문장이 이 PC에서 약 43ms 늘어남(troubleshooting/0023)
- 키셋 페이지: VAN 목록(커서)·결과·이상 목록 모두 afterId
- NOT NULL 열 추가와 strict 모드(ERROR 1292) → null 허용 추가·백필·not null. `insertMany`는 엔티티 기본값을 쓰지 않음(troubleshooting/0022)
- ORDER BY enum은 선언 순서, 이력 `datetime(0)`은 밀리초를 반올림, `em.execute`의 DELETE·UPDATE는 `'run'`이어야 affectedRows. 거의 빈 표에서 옵티마이저가 PK 대신 보조 인덱스를 골라 `force index (primary)`
