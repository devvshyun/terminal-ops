# 0001. 같은 단말기 동시 전이

- 날짜 / 관련 기능: 2026-10-22 / F2
- 질문: 같은 단말기에 전이 20건이 동시에 오면 1건만 반영되는가? 나머지는 올바른 이유(409 충돌 또는 422 규칙 위반)로 실패하는가?
- 설정: 로컬 Docker MySQL 8.4(InnoDB, 기본 격리 수준 REPEATABLE READ), 앱 1개 프로세스, N=20, `Promise.all`로 한꺼번에 보냄.
  - A: HTTP `POST /terminals/CC-0001/transitions`, IN_STOCK → ALLOCATED, 20건 모두 같은 `expectedVersion`.
  - B: `TransitionService.transition`을 직접 호출(시스템 작업 흉내), ALLOCATED → IN_STOCK, `expectedVersion` 없음, 요청마다 `em.fork()`.
  - 테스트 파일: `apps/api/test/terminal-concurrency.e2e.spec.ts`
- 재현 (`apps/api`에서):
  ```bash
  for i in 1 2 3; do npx vitest run test/terminal-concurrency.e2e.spec.ts --reporter=verbose 2>&1 | grep -E "\[실험|passed|failed"; done
  ```

## 결론

- 낙관적 락만으로 "1건만 반영"은 수정 전에도 지켜졌다. 하지만 이력 INSERT가 단말기 UPDATE보다 먼저 나가는 순서 때문에 데드락이 섞였고, 응답이 500이었다. UPDATE를 먼저 flush하자 A는 3회 모두 `{"200":1,"409":19}`, B는 실패 사유가 OptimisticLock과 InvalidTransition 두 가지뿐이 됐다.
- A의 409가 전부 충돌인 이유: `expectedVersion`을 규칙보다 먼저 검사하므로(decisions/0004), 승자가 커밋된 뒤에 읽은 요청도 version이 달라 409가 된다. "같은 상태로 전이" 422는 나오지 않는다.
- B에서 실패 이유가 두 가지로 갈리는 이유: `expectedVersion`이 없으면 조회 직후 version 검사를 하지 않는다.
  - 승자가 커밋하기 전에 단말기를 읽은 요청은 상태가 아직 ALLOCATED라 규칙을 통과하고 UPDATE까지 간다. 승자의 X 락을 기다렸다가, 승자가 커밋한 뒤 `WHERE version = 옛값`이 0행이 되어 OptimisticLock으로 실패한다.
  - 승자가 커밋한 뒤에 읽은 요청은 이미 IN_STOCK을 본다. IN_STOCK → IN_STOCK은 "같은 상태로의 전이"라 규칙 위반(InvalidTransition)으로 실패한다.
  - 비율은 각 요청이 승자 커밋 전후 어느 쪽에서 SELECT를 했느냐로 정해진다. 계획에서는 회차마다 달라질 수 있다고 봤지만, 이번 3회는 9:10으로 같았다. 같은 PC, 같은 커넥션 풀에서 요청이 도착하는 순서가 거의 똑같았기 때문으로 보인다(추측. 타이밍을 따로 재지는 않았다).
- 데드락이 없어진 것은 숫자(500 → 0, Deadlock → 0)와 `SHOW ENGINE INNODB STATUS`의 마지막 데드락 시각(수정 전 13:11:14에서 바뀌지 않음)으로 확인했다.
