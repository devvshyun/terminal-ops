# 0002. 같은 단말기 동시 검수

- 날짜 / 관련 기능: 2026-10-22 / F13 (Task 7)
- 질문: 같은 단말기에 검수 10건이 동시에 오면 1건만 반영되는가? 나머지는 409·422로 실패하고 500은 없는가? 검수 기록 INSERT를 전이보다 먼저 하는 계획 순서에서 데드락이 다시 나는가?
- 설정: 로컬 Docker MySQL 8.4(InnoDB, REPEATABLE READ), 앱 1개 프로세스, N=10, `Promise.all`로 한꺼번에 보냄.
  - SN-100 단말기 `IC-0001`(RECEIVED) 하나에 `POST /terminals/IC-0001/inspections`, 4개 항목 전부 합격, `X-Operator: choi`.
  - 검수 API는 `expectedVersion`을 받지 않는다. 전이 서비스가 flush할 때 `WHERE version = ?` 검사만 한다.
  - 응답 코드(+ 응답의 `code`), 그 단말기의 `inspection` 행 수, `toStatus = INSPECTED` 이력 행 수를 센다. 행 수는 단언보다 먼저 세서 실패해도 숫자가 남는다.
  - 테스트 파일: `apps/api/test/inspection-concurrency.e2e.spec.ts`
- 재현 (`apps/api`에서):
  ```bash
  for i in 1 2 3; do npx vitest run test/inspection-concurrency.e2e.spec.ts --reporter=verbose 2>&1 | grep -E "\[실험|Tests "; done
  # 마지막 데드락 시각
  docker exec terminal-ops-mysql sh -c 'mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "show engine innodb status\G"' | grep -A2 "LATEST DETECTED DEADLOCK"
  ```
  계획 순서는 `inspection.service.ts`에서 `tx.create(Inspection ...)`·`InspectionResult` 블록을 `transition()` 호출 앞으로 옮겨(단말기는 `terminal` 사용) 돌렸다. 확인 후 되돌렸다.

### 계획 순서 (검수 기록 먼저, 전이 나중) — 기록한 3회 모두 실패

| 회차 | 응답 | 검수 기록 | 이력 | 소요 | 테스트 |
|---|---|---|---|---|---|
| 1 | `{"201":1,"500":9}` | 1 | 1 | 72ms | failed |
| 2 | `{"201":1,"500":9}` | 1 | 1 | 73ms | failed |
| 3 | `{"201":1,"500":9}` | 1 | 1 | 73ms | failed |

원문:
```
[실험 C] N=10 결과={"201":1,"500":9} 검수기록=1 이력=1 소요=72ms
AssertionError: expected [ 500, 500, 500, 500, 500, 500, …(3) ] to have a length of +0 but got 9
[실험 C] N=10 결과={"201":1,"500":9} 검수기록=1 이력=1 소요=73ms
[실험 C] N=10 결과={"201":1,"500":9} 검수기록=1 이력=1 소요=73ms
```
그 전 3회(숫자 줄은 grep에서 잘려 기록하지 못함)도 Nest 로그에 `DeadlockException` 이 매번 찍혔다. 실패한 SQL은 모두 `update terminal set status = 'INSPECTED', ... where id = 1 and version = 1`이었다.

마지막 실행 뒤 `SHOW ENGINE INNODB STATUS`(요약):
```
2026-10-22 13:20:18
*** (1) TRANSACTION: ... undo log entries 5
update `terminal` set `status` = 'INSPECTED', ... where `id` = 1 and `version` = 1
*** (1) HOLDS THE LOCK(S): ... index PRIMARY of table `terminal_ops_test`.`terminal` ... lock mode S locks rec but not gap
*** (1) WAITING FOR THIS LOCK TO BE GRANTED: ... `terminal` ... lock_mode X locks rec but not gap waiting
*** (2) TRANSACTION: ... undo log entries 5
update `terminal` set `status` = 'INSPECTED', ... where `id` = 1 and `version` = 1
*** (2) HOLDS THE LOCK(S): ... `terminal` ... lock mode S locks rec but not gap
*** (2) WAITING FOR THIS LOCK TO BE GRANTED: ... `terminal` ... lock_mode X locks rec but not gap waiting
*** WE ROLL BACK TRANSACTION (2)
```
`undo log entries 5`는 검수 1행 + 결과 4행을 INSERT한 뒤라는 뜻이다. Task 6(troubleshooting/0004)과 같은 S→X 데드락이다. 순서 A로 되돌린 뒤 마지막 데드락 시각은 13:20:18에서 바뀌지 않았다.

## 결론

- 계획 순서는 데드락을 재현했다. 전이 서비스 안에서 `flush()`를 불러도, 그 전에 같은 작업 단위에 쌓인 검수 INSERT가 같은 flush에서 UPDATE보다 먼저 나가기 때문이다. 동시 요청 10건 중 9건이 500이었다.
- 순서 A(전이 먼저)는 6회 모두 1건 201, 9건 409 `VERSION_CONFLICT`, 500 0건, 새 데드락 없음. 결정은 decisions/0006.
- 계획 순서에서도 검수 기록·이력은 1건이었다(데드락 희생 트랜잭션은 통째로 롤백). 데이터는 맞고 응답 코드만 틀렸다. 이번에는 단언 전에 세서 실제로 쟀다.
- 나머지 9건이 422가 아니라 전부 409인 이유(추정): 10건 모두 승자가 커밋하기 전에 단말기를 RECEIVED로 읽고 UPDATE까지 가서, 승자 커밋 후 `version = 1` 조건이 0행이 됐다. 검수 트랜잭션은 단말기·검수 항목 조회 등 SELECT가 더 많아 실험 0001의 B보다 요청이 몰려 있었을 수 있다. 타이밍은 따로 재지 않았다.

## 한계

- 단일 프로세스, 로컬 DB, N=10, 순서별 3~6회만 돌렸다.
- 422(이미 검수됨)가 섞이는 경우는 이번에 나오지 않았다. 테스트는 409와 422를 모두 허용한다.
- 데드락(1213)은 여전히 필터에 매핑이 없다. 순서를 지키지 않는 새 코드가 생기면 다시 500이 된다.
