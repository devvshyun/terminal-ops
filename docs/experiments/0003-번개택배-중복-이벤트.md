# 0003. 번개택배 중복 이벤트

- 날짜 / 관련 기능: 2026-10-22 / F3, F12 (Day 2 Task 9)
- 질문: 번개택배가 이벤트를 30% 확률로 두 번 보낼 때, 우리 DB에 같은 이벤트가 두 번 저장되거나 배송 완료가 두 번 반영되는가?
- 설정
  - partners(가상 업체 서버, 테스트 포트 4011): `seed=3`, `bungae.duplicateRate=0.3`, `advancePerPoll=1`(조회할 때마다 이벤트가 하나씩 늘어 4번째 조회에 DELIVERED). 그 밖에는 기본값(한도 초당 20, 강제 429 0)
  - 운송장 N=30(등록 → 검수 → 재고 → 배정 → 번개택배 출고를 실제 API로 준비)
  - 워커 1개 프로세스(테스트 앱 안, `createTestApp({ workers: true })`), `track-bungae` limiter 초당 10·동시 5, 스케줄러 끔
  - 테스트가 `sweep()` → 큐가 빌 때까지 대기를 IN_TRANSIT가 0이 될 때까지 반복(최대 10번)
  - 로컬 Docker MySQL 8.4, Redis 7.4
  - 테스트 파일: `apps/api/test/experiments/carrier-duplicates.spec.ts` (EXPERIMENTS=1일 때만 돈다)
- 재현 (`apps/api`에서):
  ```bash
  for i in 1 2 3; do EXPERIMENTS=1 npx vitest run test/experiments/carrier-duplicates.spec.ts --silent=false 2>&1 | grep -E "\[실험 0003\]|Tests |FAIL"; done
  ```

숫자 읽는 법
- "받은 이벤트"는 SyncRun.fetched 합계(중복 포함). 조회 k번째 응답에는 서로 다른 이벤트가 k개 있으므로 중복이 없으면 운송장당 1+2+3+4 = 10개, 30건이면 300개다. 381 − 300 = 81이 "응답 안 중복"이다.
- "건너뜀" 261 = 응답 안 중복 81 + 이미 저장돼 있던 이벤트 180(중복을 뺀 300개 − 새로 저장 120). 계산이 맞아떨어진다.
- 결과별 SyncRun: OK 90 + DELIVERED 30 = 120 = 조회 수. ERROR·NOOP·SKIPPED는 없었다.
- 3회의 개수가 모두 같은 것은 partners가 시드 난수(`seed=3`)를 쓰기 때문이다. 소요만 회차마다 조금 다르다(11211~11248ms).

## 결론

- 중복 반영 0건: 30% 중복(응답 안 중복 81개)이 실제로 일어났는데도 3회 모두 `carrier_event=120`(운송장당 4개), DELIVERED 이력 30(단말기당 최대 1)이었다.
- 중복을 막는 장치는 3단이다(`carrier-sync.service.ts`의 이벤트 저장).
  1. 응답 안에서 같은 eventKey를 하나로 줄인다(이번 81개는 여기서 걸렸다).
  2. 이미 저장된 키를 한 번에 조회해 뺀다(180개).
  3. 그래도 겹치면 `(shipment, event_key)` unique 제약이 INSERT를 막고, 그 예외는 건너뜀으로 센다.
- 이번 실험에서는 3단계(unique 위반)가 일어날 수 없다. 같은 운송장의 track job은 jobId `track-<shipmentId>`로 큐에 하나뿐이라, 같은 운송장을 두 워커가 동시에 처리하는 경쟁이 없기 때문이다. "저장 120 = carrier_event 120"이고 건너뜀이 1·2단계 합(81 + 180)과 정확히 같아 unique 위반 경로로 간 이벤트는 0개다(측정 숫자로 계산).
- 소요 약 11.2초: sweep 4회 × 30건 = 조회 120번이 limiter 초당 10에 묶인 시간(약 12초)과 비슷하다. 그래서 병목은 우리 쪽 limiter라고 본다(추정. 구간별 시간은 재지 않았다).

## 한계

- 워커 1개, 같은 운송장 동시 처리 없음 → unique 제약 경로는 시험하지 못했다. 워커 2개는 experiments/0005에서 본다.
- 실제 택배사의 중복 패턴(같은 이벤트를 시간을 두고 재전송, eventId가 바뀐 채 다시 오는 경우 등)은 흉내 내지 않았다. partners는 같은 응답 안에 같은 이벤트를 한 번 더 넣을 뿐이다.
- 시드가 하나(3)라 3회가 같은 입력이다. 반복은 "같은 입력에서 결과가 흔들리지 않는다"만 보여 준다.
