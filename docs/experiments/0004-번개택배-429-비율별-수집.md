# 0004. 번개택배 429 비율별 수집

- 날짜 / 관련 기능: 2026-10-22 / F3, F12 (Day 2 Task 9)
- 질문: 번개택배가 429를 10/30/50% 비율로 줄 때 수집이 끝나는가, 얼마나 걸리고 몇 번 더 부르는가?
- 설정
  - partners: `seed=4`, `bungae.force429Rate ∈ {0.1, 0.3, 0.5}`(조회마다 이 확률로 429), `retryAfterSec=1`, 한도 초당 20(기본), `advancePerPoll=1`
  - 운송장 30건, 비율마다 DB·큐·partners를 초기화하고 새로 준비
  - sweep은 스케줄러 대신 테스트 루프가 500ms 간격으로 부른다. IN_TRANSIT가 0이 되거나 120초가 지나면 멈춘다(넘으면 미완료로 센다)
  - 재시도: job당 최대 5회 시도(`attempts: 5`). 429는 Retry-After(1초)만큼, 그 밖에는 500ms 지수 백오프(decisions/0014). limiter 초당 10·동시 5. 워커 1개 프로세스(테스트 앱 안)
  - 표의 "재시도(ERROR 실행)"는 결과가 ERROR인 SyncRun 수, "재시도 소진"은 5번째 시도도 ERROR로 끝난 SyncRun 수, "최대 시도"는 SyncRun.attempt 최댓값
  - 테스트 파일: `apps/api/test/experiments/carrier-429.spec.ts` (EXPERIMENTS=1일 때만)
- 재현 (`apps/api`에서):
  ```bash
  EXPERIMENTS=1 npx vitest run test/experiments/carrier-429.spec.ts --silent=false 2>&1 | grep -E "\[실험 0004|^\||Tests |FAIL"
  ```
  2번 돌렸다(15:27, 15:28 시작).

## 결론

- 세 비율 모두 2회 다 30/30 완료, 중복 반영 없음(단말기당 DELIVERED 이력 ≤ 1 단언 통과).
- 조회 수는 언제나 "성공 조회 120 + 429 수"였다(135 = 120 + 15, 155 = 120 + 35, 210 = 120 + 90). 429가 아닌 오류는 없었고, ERROR 실행 수 = 429 수다. 즉 429 한 번이 정확히 재시도 한 번을 만들었다.
- 비율이 오를수록 더 부른 횟수는 15 → 35 → 90으로, 비율보다 빠르게 는다. 성공 한 번에 필요한 평균 시도가 1/(1−p)라서 p가 커지면 급해진다(10%면 1.11배, 50%면 2배가 기댓값. 측정은 1.13배, 1.29배, 1.75배).
- 소요는 10%·30%에서 약 14.6~16.1초, 50%에서 약 21.3~22.3초. 10%와 30%는 거의 차이가 없고 50%에서 5초 이상 늘었다. 늘어난 이유는 429마다 Retry-After 1초를 기다리고, 한 운송장이 연속으로 429를 받으면 그 운송장 차례가 그만큼 밀리기 때문이라고 본다(추정. 운송장별 시간은 재지 않았다).
- 재시도 소진: 50%에서 1건 있었다(5번 모두 429). 그런데도 완료가 30/30이므로 그 운송장은 IN_TRANSIT로 남았다가 다음 sweep에서 새 job으로 다시 들어가 끝났다(완료 수로 확인, 어느 sweep에서 끝났는지는 재지 않았다). 최대 시도는 30%·50%에서 5로 한도에 닿았다.
- 30%의 실제 429 비율이 22.6%로 설정보다 낮다. partners가 시드 난수(`seed=4`)로 429를 정하므로 이 시드에서 나온 값일 뿐이다(추정. 다른 시드는 돌리지 않았다). 2회 숫자가 같은 것도 시드가 같아서다.

## 한계

- 429를 조회마다 독립된 확률로만 냈다. 실제는 시간대·버스트로 몰려 온다.
- 우리 limiter(초당 10)가 partners 한도(초당 20)보다 낮아 "진짜 한도 초과 429"는 재지 않았다. 표의 429에 한도 초과분이 섞였을 수는 있지만, limiter 때문에 없었을 것으로 본다(1·2회차 당시는 추정. partners가 두 종류를 따로 세지 않았다). → 아래 "추가: 429 원인 분리 후 3회차"에서 한도 초과 0으로 확인
- Retry-After 1초 고정, 백오프에 지터 없음. 429가 많을 때 같은 시점에 재시도가 몰리는지는 보지 않았다(study/backlog).
- 시드 하나, 운송장 30건, 워커 1개, 2회. 분포를 말할 만큼의 표본은 아니다.

## 추가: 429 원인 분리 후 3회차 (2026-10-22 15:34)

Task 9 리뷰 뒤 partners가 429를 원인별로 따로 센다: `status429Limit`(초당 한도 초과), `status429Forced`(force429Rate 난수). `status429`는 둘의 합으로 그대로 둔다. 실험 스펙도 바꿨다: 표의 429 열을 `합(강제/한도)`로 찍고, 미완료가 있으면 실패하도록 `expect(remaining).toBe(0)`을 넣었다(전에는 완료 수를 찍기만 했다). 같은 재현 명령으로 1번 더 돌렸다.
