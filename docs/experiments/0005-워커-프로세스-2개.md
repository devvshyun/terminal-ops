# 0005. 워커 프로세스 2개

- 날짜 / 관련 기능: 2026-10-22 / F3, F5 (Day 2 Task 10)
- 질문: 워커 프로세스 2개가 같은 큐를 나눠 처리할 때 같은 운송장을 동시에 조회하거나, 배송 완료를 두 번 반영하거나, 알림을 두 번 보내는가?
- 설정
  - 처리: `node dist/worker.js` 자식 프로세스 2개(`WORKER_NAME=w1`, `w2`, `RUN_SCHEDULERS=0`, `NODE_ENV=test`, 테스트와 같은 `QUEUE_PREFIX`). 각자 `track-bungae` 프로세서 concurrency 5, outbox 프로세서 concurrency 5
  - 테스트 프로세스는 job을 넣기만 한다(`createTestApp({ workers: false })`). 300ms마다 `sweep()` + `relay()`를 IN_TRANSIT 0이고 outbox PENDING·QUEUED 0이 될 때까지(최대 120초) 반복, 그 뒤 큐가 빌 때까지 대기
  - 운송장 30건(번개택배), partners `seed=5`, `bungae.delayMs=100`(응답을 늦춰 겹칠 기회를 넓힘), 나머지 기본값(한도 초당 20, 중복·429 0, `advancePerPoll=1`)
  - limiter 초당 10(BullMQ limiter는 큐 단위라 두 워커 합산)
  - 로컬 Docker MySQL 8.4, Redis 7.4, 한 PC
  - 테스트 파일: `apps/api/test/experiments/two-workers.spec.ts` (EXPERIMENTS=1일 때만)
- 재현 (`apps/api`에서):
  ```bash
  npm run build
  for i in 1 2 3; do EXPERIMENTS=1 npx vitest run test/experiments/two-workers.spec.ts --silent=false 2>&1 | grep -E "\[실험 0005\]|Tests |FAIL"; done
  ```
  3번 돌렸다(15:37:12, 15:37:31, 15:37:49 시작).

## 결론

- 같은 운송장을 두 워커가 동시에 조회한 일은 3회 모두 0번(동시 최대 1). 추적 job id가 `track-<shipmentId>`라서 그 운송장 job이 큐에 있거나 처리 중이면 sweep이 같은 id로 또 넣어도 새 job이 생기지 않는다. 그래서 워커가 몇 개든 같은 운송장 job은 한 번에 하나다. 300ms마다 sweep을 불러 겹칠 기회를 일부러 늘렸는데도 0이었다.
- DELIVERED 반영 중복 0(단말기당 최대 1), 알림 중복 0(톡톡 수신 180 = outbox 180, 중복 수신 키 0). outbox 180은 단말기 30대 × 전이 6번(등록부터 DELIVERED까지)이고, 모두 SENT, 시도 수 최대 1이라 알림 재시도도 없었다. 이번 조건(워커를 죽이지 않음, 톡톡 실패 0)에서는 "최소 한 번"이 "정확히 한 번"으로 끝났다는 뜻이지, 중복이 불가능하다는 증명은 아니다.
- 일은 두 워커가 실제로 나눴다. SyncRun이 3회 모두 정확히 60/60이었고, 3회차는 DELIVERED도 15/15였다. 왜 딱 반반인지는 보지 않았다(추정: limiter가 풀릴 때마다 두 워커가 번갈아 job을 가져가서).
- 소요는 약 11.8초로 워커 1개였던 0003(약 11.2초)과 거의 같다. 조회 120번을 limiter 초당 10으로 나누면 12초 안팎이라, 두 실험 모두 limiter가 소요를 정한 것으로 본다. BullMQ limiter는 큐 단위라 워커를 늘려도 택배사 호출 속도의 상한은 그대로다. 0005가 0.6초쯤 긴 것은 응답 지연 100ms와 마지막 outbox 처리까지 기다린 차이로 본다(추정. 구간별 시간은 재지 않았다. 0003은 지연 0, 루프 방식도 달라 직접 비교용 실험은 아니다).
- 낙관적 락 충돌이나 재시도: SyncRun에 ERROR가 없었고(OK 90 + DELIVERED 30, 3회차 DB 기준) outbox 시도 최대 1이라, 이번 실행에서는 나타나지 않았다. 워커 로그에서 따로 찾지는 않았다.

## 한계

- 워커를 강제로 죽이지 않았다. 설계안 7장 "워커 강제 종료 → 알림 유실 0건"은 Day 7에서 본다.
- 한 PC, 한 Redis, 한 MySQL. 네트워크 지연·Redis 장애 없음.
- 429·중복 이벤트·톡톡 실패를 모두 끈 상태다. 섞으면 재시도가 생겨 결과가 달라질 수 있다.
- 시드 하나, 운송장 30건, 3회. 소요가 limiter에 묶였다는 결론은 limiter 값을 바꿔 보지 않은 추정이다.
- 자식 프로세스는 매 실행 뒤 남지 않았다(실행 후 `worker.js`가 명령줄에 있는 node 프로세스 0개 확인).
