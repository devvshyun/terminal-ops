# 0006. 대량 처리 — N+1 대 일괄, 박스 500대, 엑셀 1,000행·5,000행, outbox relay addBulk

- 날짜 / 관련 기능: 2026-10-23 / F1, F6, F5 (Day 3 Task 10)
- 질문:
  1. 행마다 조회하는 N+1과 일괄 엔진의 쿼리 수·시간 차이는?
  2. 박스 500대·엑셀 1,000행을 한 요청·한 트랜잭션으로 처리하면 얼마나 걸리나?
  3. 엑셀 상한 5,000행 파일 하나를 받을 때 시간과 메모리(RSS)는?(decisions/0022가 재라고 남긴 것)
  4. relay에 addBulk를 쓰면 relay 1회 시간(= PENDING 행 락을 쥐는 시간)이 줄어드나?(Day 2 리뷰 Minor 3)
- 설정
  - `EXP_BOX=500`, `EXP_EXCEL=1000`, `EXP_EXCEL_MAX=5000`, `EXP_OUTBOX=1000`(모두 기본값), relay limit 100
  - 테스트 앱은 워커·스케줄러 없음(`createTestApp()` 기본). D는 job을 쌓기만 하고 waiting 수를 센다
  - 쿼리 수는 `test/helpers/query-log.ts`(MikroORM 연결의 logQuery를 감쌈, begin·commit 포함)
  - RSS는 테스트 프로세스(앱과 같은 프로세스)의 `process.memoryUsage().rss`를 10ms마다 표본으로 잼. before = 요청 직전, peak = 표본 최고값, growth = peak - before
  - 로컬 한 PC(Windows 11), Docker MySQL 8.4, Redis 7.4, 테스트 DB `terminal_ops_test`, 큐 접두사 `test-*`
  - 테스트 파일: `apps/api/test/experiments/bulk-ops.spec.ts`(EXPERIMENTS=1일 때만)
  - A의 N+1 쪽: 한 트랜잭션에서 행마다 `findOne(Terminal, { serialNo })` → 없으면 `create` + `recordRegistration`(이력·Outbox). 일괄 쪽: `BulkRegistrationService.register`(source SCAN)
  - B: `orderPurchase(t, 500)`으로 발주·명세를 만든 뒤 `POST /scans`(RECEIVE, 500대). C·E: exceljs로 만든 .xlsx(머리글 + `EXX-00001…`)를 `POST /terminals/imports`로 올림
  - D: outbox 행 1,000개를 `insertMany`로 넣고 PENDING이 없을 때까지 `relay(100, { enqueue })`를 반복. 변형마다 행·큐를 지우고 같은 조건에서 시작
- 재현 (`apps/api`에서):

## 결론

- A: N+1은 쿼리가 행 수에 비례했다(500행 → 2503개). select 1001 = 모델 1 + 행마다 존재 확인 500 + 행마다 INSERT 뒤 version 재조회 500으로 보인다(추정, 쿼리 문장별로 나눠 세지는 않았다). insert 1500 = 행마다 단말기·이력·Outbox 3개. FlushMode AUTO 때문에 다음 행의 `findOne` 전에 flush가 일어나 INSERT도 묶이지 않고 행마다 나갔다(계획의 사전 검증과 같은 모양). 일괄 엔진은 12개(select 4, insert 6)로 약 6.5 ~ 7배 빨랐다.
- 일괄 쿼리 수는 행 수에 따라 조금씩 는다: 500행 select 4 / insert 6, 1,000행 6 / 12, 5,000행 19 / 51. MikroORM batchSize 300으로 테이블마다 INSERT가 ceil(n/300)번(500 → 2, 1,000 → 4, 5,000 → 17), select는 모델·기존 시리얼 2 + 단말기 INSERT 묶음마다 version 재조회 1이라고 보면 숫자가 맞는다(추정, 문장별로 확인하지 않음). 그래도 행 수에 비례하는 N+1과는 자릿수가 다르다.
- B: 박스 500대 입고는 HTTP 한 요청 약 0.4초(명세 조회·발주 잠금·Redis 처리 중 잠금 포함). 한 트랜잭션에서 발주 행 락을 쥐는 시간은 이보다 짧다.
- C·E: 엑셀 1,000행 약 0.5 ~ 0.6초, 5,000행 약 2.2 ~ 2.7초. 5,000행이 1,000행의 약 4 ~ 5배로 행 수에 거의 비례했다. 한 트랜잭션이라 5,000행 요청 하나가 2초 넘게 걸리고 그동안 일괄 등록 트랜잭션이 열려 있다(파일 읽기 시간을 따로 나눠 재지는 않았다).
- E의 메모리: 우리가 만든 5,000행 파일(75KB)은 RSS를 31 ~ 42MB 올렸다. decisions/0022의 리뷰어 측정(20만 행 2.78MB → 약 780MB)과 비교하면 상한 5,000행 안의 정상 파일은 메모리 부담이 작다. 다만 우리 앱은 5,000행 검사를 시트를 다 읽은 뒤에 하므로, 2MB 안에 5,000행보다 훨씬 많은 행을 넣은 파일은 여전히 크게 올릴 수 있다(이번 실험에서는 재지 않음) → decisions/0022 갱신.
- D: addBulk가 relay 1회 최대 시간(= PENDING 행 락을 쥐는 시간)을 52 ~ 103ms에서 15 ~ 34ms로, 1,000행 전체를 510 ~ 567ms에서 120 ~ 158ms로 줄였다. 두 순서 모두 같은 방향이다. each의 최대값이 "each 먼저"일 때 약 100ms, "bulk 먼저"일 때 약 50ms인 것은 처음 도는 쪽이 첫 relay에서 준비 비용(연결·스크립트 로드 등)을 내기 때문으로 보인다(추정). 순서를 바꿔도 addBulk 쪽이 짧다 → relay 기본값을 addBulk로 둔다(decisions/0024).
- job 수는 두 변형 모두 1,000(QUEUED 1,000). addBulk도 같은 수를 넣는다.

## 한계

- 한 PC, 동시 요청 없음, MySQL·Redis가 같은 PC라 네트워크 왕복이 거의 없다. 원격 DB·Redis면 N+1과 each의 왕복 비용이 더 커질 것이다(추정).
- 쿼리 수에 begin·commit이 포함된다. 쿼리를 문장 종류별로 나눠 세지 않아 select·insert 구성 설명은 추정이다.
- RSS는 테스트 프로세스 전체(vitest·테스트 코드·앞 단계에서 남은 힙 포함)의 값이고, 10ms 표본이라 최고값을 놓칠 수 있다. GC 시점에 따라 흔들린다(C의 growth 4MB ~ 13MB).
- 엑셀 파일은 글자 셀 두 열뿐인 단순한 파일이다. 서식·공유 문자열이 많은 실제 파일, 2MB 안에 5,000행을 넘게 넣은 파일은 재지 않았다.
- D는 워커 없이 큐에 넣기만 했다. relay와 등록·전이가 동시에 도는 상황의 락 대기 시간은 재지 않았다(그 경우의 gap 락 문제는 troubleshooting/0007).
