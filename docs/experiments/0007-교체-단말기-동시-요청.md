# 0007. 교체 출고 동시 요청 — 같은 교체 단말기, 잠금 순서, 서로 다른 교체 단말기

- 날짜 / 관련 기능: 2026-10-23 / F7 (Day 3 Task 11)
- 질문:
  1. 같은 교체 단말기를 접수 10건이 동시에 요청하면 정확히 1건만 성공하는가? 500·데드락은 0인가? 고아 운송장은 몇 장인가?
  2. 잠금 순서를 id 오름차순(`id-asc`, 운영)에서 고장 단말기 먼저(`faulty-first`)로 바꿔도 결과가 같은가? 교체 단말기를 먼저 만들어 id를 가장 작게 하므로 `faulty-first`는 실제로 id 오름차순과 반대 순서가 된다.
  3. (계획에 없던 변형, Task 9 리뷰 뒤 더함) 서로 다른 교체 단말기 10대로 동시에 교체 출고하면 모두 201인가? troubleshooting/0014(이전 운송장 UPDATE의 gap 락 데드락)의 회귀 시나리오다.
- 예상:
  - 같은 교체 단말기: 공유되는 행은 교체 단말기 하나뿐이다. 각 트랜잭션이 "자기 고장 단말기 + 공유 교체 단말기"를 잡으므로 순서를 바꿔도 서로 상대가 쥔 행을 기다리는 순환이 생기지 않는다 → 두 순서 모두 데드락 0. `faulty-first`도 "순환 없음"이 기대값이다(decisions/0023 리뷰 메모: 역할 순서 "고장 → 교체" 자체가 일관된 순서. 한 단말기가 동시에 고장 단말기(IN_SERVICE, 열린 접수)이면서 교체 단말기(IN_STOCK)일 수 없다).
  - 서로 다른 교체 단말기: 단말기 행이 겹치지 않고, 운송장 없는 새 교체 단말기는 `recordShipment`가 UPDATE를 보내지 않는다(decisions/0018, b18804d) → 모두 201, 데드락 0.
- 설정
  - N=10(`EXP_N`), 3회(`EXP_ROUNDS`), 번개택배(`BUNGAE`), 가맹점 GANGNAM-KIMBAP
  - 같은 교체 단말기: 서비스 직접 호출 `ReplacementService.replace(id, cmd, 'exp7', { lockOrder })`(같은 프로세스·같은 커넥션 풀), 순서 `id-asc`·`faulty-first`. 회차마다 교체 단말기 1대(`R7nn-REPL`)를 먼저 재고로 만들고, 고장 단말기 10대를 운영 중(IN_SERVICE)으로 만들어 접수를 연다
  - 서로 다른 교체 단말기: HTTP `POST /service-tickets/:id/replacements`(운영 경로, 순서는 늘 `id-asc`). 회차마다 고장 단말기 10대·접수 10건을 먼저 만들고 그 뒤 교체 단말기 10대(`R7nn-S001…`)를 재고로 만든다 → 교체 단말기 id가 가장 크고 운송장이 없다(0014에서 supremum gap을 함께 잡던 모양)
  - 고장 단말기는 준비 과정(`prepareInService`)에서 출고된 적이 있어 각자 운송장 1장(IN_TRANSIT)이 있다. 교체 출고는 교체 단말기의 운송장만 저장하므로 영향 없음
  - 운송장 발급 수는 partners의 `bungae.waybill` 호출 수(회차 직전에 `partners.reset()`), 저장 수는 교체 단말기의 shipment 행 수, 고아 = 발급 - 저장
  - 데드락 수는 테스트 밖에서 root로 `information_schema.innodb_metrics`의 `lock_deadlocks`를 실행 전후로 읽음(앱 계정은 PROCESS 권한이 없어 테스트 안에서 못 읽음)
  - 로컬 한 PC(Windows 11), Docker MySQL 8.4(REPEATABLE READ), 테스트 DB `terminal_ops_test`
  - 테스트 파일: `apps/api/test/experiments/replacement-race.spec.ts`(EXPERIMENTS=1일 때만)
- 재현 (`apps/api`에서):

## 결론

- 같은 교체 단말기 10건 동시: 두 잠금 순서 모두 6회 내내 정확히 1건 성공, 나머지 9건은 `INVALID_TRANSITION`(HTTP로는 422), 500 0, 데드락 0. 예상과 같다.
- 잠금 순서를 바꿔도 같은 이유: 이 경합에서 여러 트랜잭션이 함께 잡는 행은 교체 단말기 하나다. 각자의 고장 단말기는 겹치지 않는다. 기다리는 쪽은 늘 "공유 행 하나"를 기다리고, 그 행을 쥔 쪽은 다른 트랜잭션이 쥔 행을 기다리지 않으므로 순환이 생기지 않는다. `faulty-first`에서 공유 행을 둘째로 잡아도(id 오름차순과 반대) 마찬가지다. 더 일반적으로는 decisions/0023 리뷰 메모대로 "고장 → 교체" 역할 순서 자체가 일관된 순서라, 두 교체 요청이 같은 두 단말기를 반대 역할로 잡는 경우가 없다(추론, 그런 상태를 만들 수 없어 재현하지 않음).
- 진 요청은 어디서 걸렸나: 6회 × 2순서 모두 9건 전부 `INVALID_TRANSITION`이었고 `REPLACEMENT_NOT_IN_STOCK`(사전 확인 단계)은 0이었다. 10건이 거의 동시에 사전 확인을 지나 모두 IN_STOCK을 보고 운송장을 발급받은 뒤, 트랜잭션에서 교체 단말기 행 잠금을 기다렸다가 승자가 커밋한 최신 상태(SHIPPED)를 보고 전이 규칙 위반으로 끝났다(Task 9 테스트·사전 검증과 같음).
- 고아 운송장: 같은 교체 단말기 경합에서 매회 9장(= 진 요청 수). 사전 확인이 트랜잭션 밖이라 동시 요청을 하나도 거르지 못했다. 알려진 한계(decisions/0012·0023)이고 이번에 숫자로 확인했다: N건 동시면 고아 N-1장. 예약 단계·고아 정리는 Day 7 검토.
- 서로 다른 교체 단말기 10대 동시: 6회 모두 10건 201, 고아 0, 데드락 0. 옛 코드로 되돌리면 같은 시나리오가 500 8건과 데드락 8건을 냈다 → b18804d의 PK 갱신이 이 경합을 고쳤다는 근거가 하나 더 생겼다.

## 한계

- 데드락이 날 수 있는 모양(두 트랜잭션이 같은 두 행을 반대 순서로)은 이 기능에서 만들 수 없어 재현하지 않았다. 같은 두 단말기를 다루는 다른 기능이 생기면 그때 같은 규칙(id 오름차순)을 적용하고 실험한다.
- 같은 교체 단말기 변형은 서비스 직접 호출이라 HTTP 계층(검증 파이프·예외 필터)은 지나지 않는다. `INVALID_TRANSITION` → 422는 replacement.e2e 테스트가 HTTP로 확인한다.
- 한 PC·같은 프로세스에서 10건을 `Promise.all`로 띄운 것이라 실제 동시성은 커넥션 풀과 이벤트 루프에 묶인다. 소요 시간(53 ~ 89ms)은 참고값이다.
- 데드락 수는 실행 전체 증가분이다. 변형별로 나눠 세지 않았다(모두 0이라 나눌 필요가 없었다).
