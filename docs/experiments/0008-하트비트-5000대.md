# 0008. 하트비트 5,000대 — Redis 대 MySQL 직접 쓰기, 묶음 대 단건, 오프라인 판정 시간

- 날짜 / 관련 기능: 2026-10-23 / F8 (Day 4 Task 9)
- 질문:
  1. 5,000대가 5초마다 보낼 때(초당 1,000건) Redis 경로는 다 받는가, 응답 p50·p95는? MySQL에는 무엇이 몇 번 쓰이나(스냅샷만)?
  2. "하트비트마다 MySQL `device_connectivity` UPSERT" 경로(실험용, `writeMode = 'mysql'`)와 비교하면 쓰기 문장 수·바뀐 행 수·응답 시간·데드락은?
  3. 묶음 100 대 단건(묶음 1): 요청 수·Redis 명령 수·응답 시간은?
  4. 하트비트를 끊은 1%(50대)가 오프라인으로 판정되기까지 걸린 시간은(기준 = 주기 × 3, 판정 1초마다)? 살아 있는 단말기가 잘못 판정되지 않는가?
  5. (필수로 정함) 이 환경에서 경로별 최대 처리량은?
- 예상: Redis 경로의 MySQL 쓰기는 스냅샷 횟수 × ⌈5,000/500⌉ 문장뿐이고, MySQL 경로는 요청마다 한 문장(단건이면 하트비트 수만큼). 단건은 요청·Redis 명령이 묶음의 약 100배. 판정 시간은 "기준 - (끊기 직전 마지막 하트비트 뒤 지난 시간) + 판정 주기" 범위, 즉 기준 - 주기 ~ 기준 + 판정 주기(10,000 ~ 16,000ms).

## 설정

- N=5,000(`EXP_N`, `seedInService`로 IN_SERVICE 단말기 INSERT, active 재구성), 주기 5초(`EXP_INTERVAL_MS`), 30초(`EXP_DURATION_MS`), 동시 요청 16(`EXP_CONCURRENCY`, keep-alive 소켓 16), 묶음 100/1, 요청 제한 시간 5초(device-sim 기본).
- redis 변형은 스냅샷을 10초마다(`EXP_SNAPSHOT_MS`, 운영 기본 60초보다 짧게 — 30초 안에 몇 번 일어나게) + 끝에 1번. 앞 스냅샷이 끝나길 기다린 뒤 마지막 스냅샷을 돈다(잠금에 막혀 건너뛰지 않게). mysql 변형은 스냅샷 없음.
- 오프라인: 1%(`EXP_OFFLINE_RATE`, 시드로 고른 50대), 기준 15초(주기 × 3), 판정 1초(`EXP_DETECT_MS`). 10초(2주기) 돌린 뒤 `offlineRate`를 바꾼 순간을 "끊은 시각"으로 잡는다.
- 최대 처리량: 주기를 1초 → 100ms → 20ms로 줄여 건너뛴 주기가 생길 때까지 밀었다(`EXP_LOOSE=1`이면 오류·받음=보냄을 단언하지 않고 적기만 한다).
- API는 테스트 앱 한 프로세스(워커·스케줄러 꺼짐, `t.app.listen(0)`, Node http 서버 keepAliveTimeout 5,000ms — 실행 로그 첫 줄), device-sim은 별도 프로세스(`startDeviceSim`, 포트 4021). 로컬 한 PC(Windows 11, 논리 프로세서 16), Docker MySQL 8.4.13(`innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`, `log_bin=1`, 버퍼 풀 128MB)·Redis 7.4. 테스트 DB `terminal_ops_test`, 테스트 접두사 키만.
- 파일: `apps/api/test/experiments/heartbeat-load.spec.ts`(EXPERIMENTS=1일 때만), `apps/api/test/helpers/metrics.ts`, 실험용 경로 `HeartbeatService.writeMode`(`HEARTBEAT_WRITE_MODE=mysql`).

## 측정 방법

- 처리량 = 받은 하트비트 / 걸린 초. 기본 부하에서는 "주어진 부하(초당 1,000건)를 다 받았나"이지 한계가 아니다.
- 응답 시간: 시뮬레이터가 잰 요청 단위 p50·p95·max(히스토그램 근삿값, 최대 1% 크게). **성공(`latencyOk`)과 실패(`latencyFailed`)를 나눠 적는다** — 이번 실행은 모두 실패 0건이라 전체 = 성공이다.
- MySQL 쓰기: 앱이 보낸 insert·update 문장 수(`captureQueries`) + `SHOW GLOBAL STATUS` 차이(`Com_insert`·`Com_update`·`Com_select`·`Innodb_rows_inserted`·`Innodb_rows_updated`·`Innodb_row_lock_waits`·`Innodb_os_log_written`, 앱 계정으로 읽음, 서버 전체 값, 0인 것은 출력에서 빠짐).
- Redis: `INFO commandstats` 호출 수 차이(서버 전체 값. `info` 1번은 측정 자신).
- 데드락: 테스트 밖에서 root로 `information_schema.innodb_metrics`의 `lock_deadlocks` 전후(변형마다 따로 실행, Day 3 실험 0007과 같은 방법).
- 매 실행 뒤: 실행 전후 node.exe PID 목록 비교(새로 남은 PID), 포트 3000·4010·4020·4011·4021 리스너.

## 부하 모델의 한계 (decisions/0009 그대로)

- **주기 시작에 몰린다(burst)**: 한 주기가 시작되면 온라인 단말기의 하트비트를 한꺼번에 만들어 `concurrency`(16)까지 동시에 보낸다. 실제 단말기는 각자 다른 시각에 보내 부하가 퍼지므로, 여기 p95는 "주기 시작에 16개가 한꺼번에 들어올 때"의 값이다.
- **닫힌 루프(closed-loop), 동시 요청 상한 16**: 응답이 늦어지면 동시 요청 수는 그대로이고 보내는 속도만 준다. 서버가 느려져도 대기열이 쌓이지 않아 "견딘 것처럼" 보일 수 있다. 최대 처리량 실행의 값은 **이 상한(16) 아래의 값**이다(처리량 ≈ 16 / 응답 시간).
- **응답 시간은 보낸 시각부터**: 소켓을 기다린 시간(`maxSockets` 대기)과 연결을 새로 맺은 시간이 들어간다. 서버 처리 시간만이 아니다.
- **keep-alive와 서버 keepAliveTimeout**: API 서버의 keepAliveTimeout이 5,000ms이고 기본 부하의 주기도 5,000ms다. 주기 사이 유휴 시간이 거의 5초라 서버가 유휴 연결을 끊었을 수 있고, 그러면 주기 첫 묶음들이 연결을 다시 맺는다(이번 실행에서 연결 오류는 0건).
- 다 못 보낸 주기는 건너뛰고 `skippedTicks`로 센다.

## 재현 (Git Bash, `apps/api`)

```bash
DL() { MSYS_NO_PATHCONV=1 docker exec terminal-ops-mysql sh -c 'mysql -N -uroot -p"$MYSQL_ROOT_PASSWORD" -e "select count from information_schema.innodb_metrics where name=\"lock_deadlocks\""' 2>/dev/null; }
run() { v=$1; shift; b=$(DL); env "$@" EXP_VARIANTS=$v EXPERIMENTS=1 npx vitest run test/experiments/heartbeat-load.spec.ts --silent=false 2>&1 | grep -E "\[실험 0008|Tests "; a=$(DL); echo "$v lock_deadlocks 전=$b 후=$a"; netstat -ano | grep -E ':(3000|4010|4020|4011|4021) .*LISTENING'; }
for v in redis-batch redis-single mysql-batch mysql-single offline; do run $v; run $v; done        # 기본, 2번씩
for v in redis-batch mysql-batch; do run $v EXP_INTERVAL_MS=1000 EXP_DURATION_MS=20000 EXP_LOOSE=1; run $v EXP_INTERVAL_MS=1000 EXP_DURATION_MS=20000 EXP_LOOSE=1; done
for v in redis-single mysql-single; do run $v EXP_INTERVAL_MS=100 EXP_DURATION_MS=20000 EXP_LOOSE=1; run $v EXP_INTERVAL_MS=100 EXP_DURATION_MS=20000 EXP_LOOSE=1; done
for v in redis-batch mysql-batch; do run $v EXP_INTERVAL_MS=100 EXP_DURATION_MS=20000 EXP_LOOSE=1; run $v EXP_INTERVAL_MS=20 EXP_DURATION_MS=20000 EXP_LOOSE=1; done
```

## 결론 (질문별, 잰 숫자로)

1. **Redis 경로는 초당 1,000건을 다 받았다**(30,000/30,000, 오류 0, 두 번 모두). 묶음 100의 응답 p50 12~13ms, p95 32~34ms. MySQL 쓰기는 **스냅샷만**: 30초에 INSERT…ON DUPLICATE 30문장 = 스냅샷 3회 × ⌈5,000/500⌉ 10문장(예상과 같음). 주기 1초·100ms·20ms로 하트비트를 5~78배 늘려도 Com_insert는 20~24로 그대로였다 — **MySQL 쓰기는 하트비트 수가 아니라 스냅샷 횟수에 비례**한다.
2. **하트비트마다 MySQL**: 쓰기 문장이 요청 수만큼 늘었다(묶음 300문장 = Redis 경로의 10배, 단건 30,000문장 = 1,000배). 바뀐 행은 25,000(첫 INSERT 5,000 뒤 매 주기 5,000행 UPDATE) 대 Redis 경로 10,000(스냅샷 2회 × 5,000), redo는 묶음 2.3배·단건 15.8배. 응답 시간은 묶음 p50 28~32ms·p95 64~96ms(Redis 경로의 약 2.5배·2~3배), 단건 p50 10.4~10.7ms(Redis 단건 3.0ms의 약 3.5배). **데드락·행 잠금 대기는 0**(lock_deadlocks 148 그대로, `Innodb_row_lock_waits` 차이 0). 행을 terminal_id 오름차순으로 넣고, 동시에 도는 묶음끼리는 서로 다른 단말기라 같은 행을 두고 다투지 않은 것으로 본다(추정).
3. **묶음 대 단건**: 요청 300 대 30,000(100배), Redis 명령 1,234 대 120,034(약 97배 — 요청당 HMGET 2·ZADD·HSET으로 4개가 고정이라 묶음이 그만큼 줄인다). 요청 하나의 응답은 단건이 짧지만(p50 3.0 대 12~13ms) 하트비트 하나당으로 보면 묶음이 훨씬 싸다. MySQL 경로에서도 문장 수가 100배 차이(300 대 30,000).
4. **오프라인 판정**: 50대 모두 판정, 첫 판정 10.1초·마지막 15.2초(두 번 모두), 예상 범위(10~16초) 안. 살아 있는 단말기의 잘못된 판정 0(판정 뒤 한 주기 더 돌려 추가 오프라인 0, 온라인 복귀 0). 판정 시각이 10초대와 15초대 두 무리로 나뉜 것은 끊은 순간(시작 10초 뒤)과 세 번째 주기 시작(역시 10초 뒤)이 겹쳐, 세 번째 주기 하트비트를 이미 보낸 단말기(→ 15초)와 못 보낸 단말기(마지막이 5초 전 → 10초)로 갈린 것으로 본다(추정, 단말기별 마지막 하트비트 시각은 남기지 않았다). 50대는 묶음 기준(50 초과)을 넘지 않아 단말기별 이벤트 50건.
5. **최대 처리량(동시 16 상한 아래)**: 단건은 Redis 약 5,400~5,500건/s, MySQL 약 1,360~1,390건/s(약 4배 차이)에서 주기를 따라가지 못했다(건너뛴 주기 177·193). 묶음 100은 Redis 약 116,000건/s, MySQL 약 58,000건/s(주기 20ms, 건너뛴 주기 353·604). 오류·시간 초과는 어디서도 없었다. 닫힌 루프라 이 값은 "서버가 무너지는 점"이 아니라 "동시 16개 요청의 응답 시간이 정하는 상한"이다: 단건 16 / 2.8ms ≈ 5,700, 16 / 10.8ms ≈ 1,480으로 잰 값과 비슷하다(리틀의 법칙 근사, 추정). 묶음 MySQL은 16 / 17.7ms × 100 ≈ 90,000보다 낮은 58,000이었는데, 한 주기가 50요청을 다 끝내야 다음 주기를 시작해 주기 끝에 동시 요청이 16보다 적은 시간이 있기 때문으로 본다(추정, 확인 안 함).
- 운영 기본(Redis)을 그대로 둔다. MySQL 경로도 초당 1,000건을 받기는 했지만 쓰기·redo가 요청 수에 비례하고 응답이 2~3배 길다. 실제 운영 부하(5,000대 × 30초 주기, 초당 약 170건)는 어느 경로로도 여유가 있지만, MySQL 경로는 단말기 수·주기에 비례해 쓰기가 늘고 Redis 경로의 MySQL 쓰기는 스냅샷 주기에만 비례한다.

## 한계

- 한 PC(네트워크 왕복 거의 없음). API·device-sim·Docker가 같은 CPU를 나눠 쓴다. 주기 100ms 실행의 주기수가 200이 아니라 184였다 — device-sim 이벤트 루프가 바빠 setInterval이 늦게 돈 것으로 본다(추정).
- 닫힌 루프 동시 16의 값이다. 동시 요청을 늘리면 처리량이 더 나올 수 있고(특히 묶음), MikroORM 연결 풀 크기(설정 안 함, 기본값)도 상한이 될 수 있다(확인 안 함).
- 서버 전체 카운터라 다른 연결의 쿼리가 섞일 수 있다(실험 중 다른 작업 없음). Redis `ping` 4~6회는 연결 확인으로 보이며 실험과 관계없다(추정).
- MySQL 경로도 active·offers 확인은 Redis로 했다(완전히 Redis 없는 경로는 아님). MySQL 경로는 autocommit으로 문장마다 커밋한다(`innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`).
- 스냅샷 주기를 운영(60초)보다 짧게(10초) 잡았다. 운영 주기면 Redis 경로의 MySQL 쓰기는 더 적다.
- 기본 부하에서 묶음 응답(p50 12~13ms)이 주기 1초(9.4ms)·100ms(6.5ms)보다 오히려 길었다. 주기 5초 = 서버 keepAliveTimeout 5초라 주기마다 연결을 다시 맺었거나, 부하가 드물어 CPU·JIT가 덜 데워진 탓으로 보지만 **확인하지 않았다**(추정). 그래서 기본 부하의 p95는 서버 처리 시간보다 크게 나왔을 수 있다.
- 오프라인 판정 시각은 테스트 프로세스가 `detect`를 부른 시각 기준이다(판정 job·큐를 거치지 않음).
