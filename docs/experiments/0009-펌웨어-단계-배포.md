# 0009. 펌웨어 단계 배포 — 실패율 0% 완료 시간, 30% 자동 중단까지 시간과 영향 범위

- 날짜 / 관련 기능: 2026-10-23 / F8 (Day 4 Task 10)
- 질문:
  1. 1,000대, 단계 10% → 50% → 100%, 실패율 0%면 단계가 언제 넘어가고 몇 초에 끝나나?
  2. 실패율 30%(기준 20%, 최소 표본 20)면 시작부터 자동 중단까지 몇 초인가? 그때 결과가 몇 건 모였고(실패/결과), 끝까지 몇 대가 영향(설치 성공·실패)을 받았나?
  3. 중단 뒤 제안이 정말 사라지나(offers 0, 끝난 뒤 시뮬레이터가 새 지시를 받지 않음)?
- 예상: 1은 단계마다 "하트비트 주기(지시 받기) + 업데이트 시간(300ms + 0~2초) + 판단 주기"쯤이라 세 단계 합 수 초~10초. 2는 첫 단계(100대) 안에서 결과가 20건을 넘는 첫 판단에서 멈춘다(실패율 30% 근처). 그 뒤에도 이미 업데이트 중이던 단말기는 보고를 마치므로 영향은 첫 단계 100대 이내. 다음 단계 대상은 만들어지지 않는다.

## 설정

- N=1,000(SN-100, `seedInService`로 IN_SERVICE 단말기 INSERT, active 재구성), 단계 10·50·100(`EXP_STAGES`), 기준 0.2(`EXP_THRESHOLD`), 최소 표본 20(`EXP_MIN_SAMPLES`), 단계 제한 30초(`EXP_STAGE_TIMEOUT_MS`).
- device-sim: 하트비트 1초(`EXP_INTERVAL_MS`)·묶음 100·동시 8, 업데이트 300ms + 0~2,000ms(`EXP_UPDATE_DELAY_MS`, `EXP_UPDATE_JITTER_MS`), 실패율 0·0.3(`EXP_FAIL_RATES`), 시드 43·44(실패율 순서대로 42 + 회차).
- 판단: 0.5초마다 `RolloutService.control(id)`를 테스트가 직접 부른다(`EXP_CONTROL_MS`, 운영 기본 5초보다 짧게). 스케줄러는 꺼져 있다(`controlAll`·`withdrawStaleOffers`는 돌지 않는다).
- 단말기별 결과는 (시드, 시리얼, 배포 id, 버전)의 결정적 함수다(직전 fix 503f817, decisions/0009). 실험마다 DB를 새로 만들어(`schema.refresh`) 배포 id가 1, 2로 같으므로 같은 설정이면 실패하는 단말기 집합이 같다 — 출력의 `실패시리얼지문`(FAILED 시리얼 정렬 목록의 sha1 앞 10자리)으로 확인한다. 단계 대상은 CRC32(시리얼) 순으로 고르므로 이것도 매번 같다.
- API는 테스트 앱 한 프로세스(`t.app.listen(0)`), device-sim은 별도 프로세스(`startDeviceSim`, 포트 4021). 로컬 한 PC(Windows 11), Docker MySQL 8.4·Redis 7.4. 테스트 DB `terminal_ops_test`, 테스트 접두사 키만.
- 파일: `apps/api/test/experiments/firmware-rollout.spec.ts`(EXPERIMENTS=1일 때만).

## 측정 방법

- 시각은 배포 만들기 요청 직전부터의 ms. `타임라인`은 WAITING이 아닌 판단만, `판단(ms:단계:실패/결과)`는 판단마다 그 직후 GET으로 읽은 그 단계의 (FAILED+TIMED_OUT)/(SUCCEEDED+FAILED+TIMED_OUT)이다 — 판단 직후에 읽으므로 판단이 본 값보다 조금 많을 수 있다(판단이 본 값은 중단 이유 문장의 괄호).
- "끝날때"는 COMPLETED/ABORTED 판단 100ms 뒤, "뒤"는 그로부터 업데이트 최대 시간 + 하트비트 2주기(4.3초) 뒤.
- 제안이 사라졌는지 세 가지로 본다: ① Redis offers HASH 필드 수(`OfferStore.count`) ② 끝난 뒤 시뮬레이터가 받은 지시 수가 늘지 않음(`지시받음(끝날때→뒤)`) ③ 끝난 뒤 테스트가 1,000대 모두를 처음 버전 1.0.0으로 직접 하트비트를 보내 응답에 `update`가 실린 수(`뒤직접하트비트update`). ②만으로는 업데이트 중인 단말기가 지시를 무시해 세지 않을 수 있어 ③을 더했다.
- 데드락: 테스트 밖에서 root로 `information_schema.innodb_metrics`의 `lock_deadlocks` 전후(읽기만).
- 매 실행 뒤: 포트 3000·4010·4020·4011·4021 리스너, 실행 전후 node.exe PID 목록 비교.

## 부하 모델의 한계 (decisions/0009, 실험 0008과 같음)

- 하트비트는 주기 시작에 몰린다(burst, 묶음 100 × 10개를 동시 8로). 그래서 한 단계 대상 전부가 거의 같은 주기(1초 안)에 지시를 받는다.
- 닫힌 루프라 서버가 느려지면 보내는 속도가 스스로 준다(이번에는 1,000대 × 1초라 부하가 작아 해당 없음).
- 실패는 단말기마다 독립(같은 모델·같은 원인 실패의 몰림은 흉내 내지 않음), 실패를 바로 보고한다(꺼져서 보고하지 못하는 경우는 TIMED_OUT으로만 보이고, 이번에는 0건).

## 재현 (Git Bash, `apps/api`)

```bash
DL() { MSYS_NO_PATHCONV=1 docker exec terminal-ops-mysql sh -c 'mysql -N -uroot -p"$MYSQL_ROOT_PASSWORD" -e "select count from information_schema.innodb_metrics where name=\"lock_deadlocks\""' 2>/dev/null; }
run() { b=$(DL); env EXPERIMENTS=1 "$@" npx vitest run test/experiments/firmware-rollout.spec.ts --silent=false 2>&1 | grep -E "\[실험 0009|Tests "; a=$(DL); echo "lock_deadlocks 전=$b 후=$a"; netstat -ano | grep -E ':(3000|4010|4020|4011|4021) .*LISTENING'; }
run X=1; run X=1; run X=1                                   # 기본(실패율 0, 0.3) 3번
run EXP_MIN_SAMPLES=5 EXP_FAIL_RATES=0.3; run EXP_MIN_SAMPLES=5 EXP_FAIL_RATES=0.3        # (선택) 최소 표본 5
run EXP_UPDATE_JITTER_MS=0 EXP_FAIL_RATES=0.3; run EXP_UPDATE_JITTER_MS=0 EXP_FAIL_RATES=0.3  # (선택) 지터 0
```

1·2회차는 판단마다의 결과 수(`판단(…)`)를 적기 전 코드로 돌렸다(나머지 출력은 같다). 실패율 0.3만 돌린 선택 실행은 회차가 1이라 시드 43·배포 id 1이다(기본의 실패율 0.3은 시드 44·배포 id 2) — 그래서 첫 단계 실패 수가 기본과 다르다(39 대 29).
