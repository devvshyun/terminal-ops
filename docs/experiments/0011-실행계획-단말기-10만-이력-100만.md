## 결론

1. **F4는 (b)가 맞다.** (b) 8.2·9.8ms 대 (a) 102·220ms — 12~22배. (a)와 윈도 함수 (a')는 같은 실행 모양(그 상태의 단말기마다 이력 인덱스 조회)이라 시간이 같다. 차이는 규칙에 걸린 상태의 단말기 수에 비례해 커진다. 다만 단말기 10만에서는 (b)에서 인덱스를 빼도(전체 훑기) 15~18ms라, 지금 규모에서 결정의 몫은 인덱스보다 "이력을 훑지 않는 것"이다. 찾기 전체는 1.2초(첫 실행, 새 이상 3만 3천 행 INSERT 포함)·0.8초(두 번째).
2. **오프라인 규칙 식**은 status 앞부분만 쓰고 운영 중 단말기 전부를 읽는다(14.7ms). 같은 뜻의 열 비교로 바꾸면 12.9ms — 고칠 이유가 없다. 운영 중 단말기가 수십만이 되면 다시 본다.
3. **주간 리포트 이력 집계에는 인덱스를 더하지 않는다(decisions/0036).** 전체 훑기 165~192ms가 주 1회. 가장 좋은 커버링 인덱스는 쿼리당 약 0.1초(Q2 103ms, Q3 112ms), 두 쿼리 합 약 0.2초(215ms) 줄이지만 이력 대량 INSERT를 +99%, 보조 인덱스를 +25.5MB 늘린다. 이력은 모든 전이가 쓰는 표다.
4. **중복 인덱스 삭제(Task 1)는 숫자로도 맞다.** terminal_status_history 단독 terminal_id 인덱스는 대량 INSERT +29%(487.7 → 627.1ms), 보조 인덱스 +20MB(37.6 → 57.7MB). firmware_rollout_target은 +17%(658.6 → 772.3ms). inspection_item은 쓰기가 거의 없는 표라 숫자가 의미 없다(공간·정리 차원).
5. 검수 통계 0.1초, VAN 비교 두 문장 각각 약 27ms(인덱스·PK 조회만, 전체 훑기 없음), 열린 이상 목록 25ms(열린 이상 3만 7천 행을 정렬 — 열린 이상이 수십만이면 `(resolved_at, rule, detected_at, id)` 순서 인덱스를 검토, 지금은 하지 않음).

- INSERT…SELECT는 한 문장 대량 입력이라 운영의 한 건씩 INSERT와 비용 구성이 다르다. 한 건씩 측정은 커밋 비용에 가려 인덱스 차이를 가리지 못했다.
- `show table status`의 Index_length는 `analyze table` 뒤의 통계값이고, 지운 행이 정리되기 전이라 작은 표에서는 흔들린다.
- F10 발주 대조(JSON_TABLE), 주간 리포트의 나머지 다섯 쿼리는 재지 않았다(모두 이력 범위가 아니다).
- ①의 (a)=(b) 결과 일치는 시드가 "마지막 이력 시각 = status_changed_at"이 되게 만든 구성상 결과다. 실제 데이터에서는 백필(Task 5 마이그레이션)이나 이력 없이 바뀐 상태 때문에 둘이 어긋날 수 있다 — 여기서 확인한 것은 "같은 데이터면 같은 답"까지다.
- 명시적 워밍업 회차 없이 5번 중앙값으로 첫 회차의 차가운 캐시를 흘려보냈다(첫 값이 튄 행이 있다 — 원값 열).
- 변형 순서가 늘 같고(앞 변형의 인덱스를 지운 뒤 다음 변형), 인덱스 삭제 뒤 InnoDB의 정리(purge·페이지 병합)가 끝났는지 통제하지 않았다. 순서 효과가 섞였을 수 있다.
