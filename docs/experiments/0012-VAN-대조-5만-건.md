# 0012. VAN 등록 대조 — 등록 5만, 어긋남 2%, 스캔 도중 변경

- 날짜 / 관련 기능: 2026-10-26 / F9 (decisions/0033, troubleshooting/0023)
- 질문
  1. 등록 5만 건 대조가 얼마나 걸리고 어디(수집·비교·재검증)에 시간이 드나. 쿼리는 몇 개이고 무엇에 비례하나. 업체 호출은 몇 번인가.
  2. 스캔 도중 VAN 등록이 바뀌면(이미 받은 페이지의 등록) 비교 후보 중 거짓 양성이 몇 개 생기고 재검증이 몇 개를 거르나. 무엇을 놓치고, 다음 실행이 찾나.
- 설정
  - 로컬 한 PC(Windows 11), Docker MySQL 8.4(`innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`, 버퍼 풀 128MB), 테스트 DB `terminal_ops_test`, 가상 partners(테스트 포트 4011, 지연 0, 429·5xx 0). env 기본값: `BRIDGEVAN_PAGE_SIZE=500`, `VAN_REVERIFY_CONCURRENCY=8`, 후보 상한 `max(5000, 20%)`, `VAN_FETCH_MIN_PCT=50`.
  - 데이터: 우리 쪽 운영 중(IN_SERVICE) 단말기 5만(`VZ-000001`…, 가맹점 세 곳을 돌아가며, `insertTerminals`). VAN 등록은 우리 목록에서 만들고 50대마다 어긋남 하나, 네 종류를 돌아가며(미등록 = 등록 없음, 가맹점 다름, 정지, 운영 아님 = 우리 DB에 없는 시리얼 `VZ-X…`가 ACTIVE) — 심은 어긋남 1,000(종류마다 250). 종류마다 절반(미등록 제외)에 `healTo`(스캔 도중 변경이 고르면 그 값으로 고쳐져 어긋남이 풀림).
  - 실행: A 기본(변경 없음) → B 스캔 도중 변경(`mutateDuringScan` 10 = 둘째 페이지부터 목록 요청마다 이미 지나간 등록 10건을 시드 12 난수로 골라, healTo가 있으면 고치고 없으면 ACTIVE↔SUSPENDED를 뒤집음) → C B 바로 뒤 변경 없이 한 번 더. 실행마다 `svc.start` + `svc.execute`를 직접 부른다(큐·워커 없음).
  - 기대값은 숫자를 박지 않는다: 실행 뒤 VAN 전체를 변경 없이 다시 받아 모든 시리얼에 `classify`를 돌린 **정답 집합**을 만들고, 확정·후보 집합을 정답·심은 집합과 비교한다(A 정답 = 심은 1,000, B는 "후보 = 심은 집합", "확정 = 심은 것 중 정답에 남은 것", "재검증 뒤 거짓 양성 0", "놓침 = 지나간 자리에서 새로 생긴 정답", C는 "확정 = 정답, 풀림 0").
  - 측정: 전체 ms, 단계 ms(실행 행 `phase_ms`의 collect·compare·reverify, other = 전체 − 셋 = 시작·완료 트랜잭션·스테이징 정리), 페이지·수집 수, partners `bridgevan.list` 호출 수(목록 + 시리얼 조회), 시리얼 조회 수(= 호출 − 페이지 − 재시도), 앱이 보낸 쿼리 수(종류별, `captureQueries`)와 DB 왕복 시간 합(MikroORM `context.took`, 종류별: 스테이징 INSERT·페이지 중복 확인 SELECT·하트비트 UPDATE), 바뀐·고쳐진 등록 수(partners 통계). 참고 측정: 같은 100페이지를 HTTP로 받고 JSON만 푼 시간(DB 없음).
  - 계획(task 10)과 다르게 한 것
    1. 운영 아님 등록의 tid를 `TX<i>`가 아니라 `T<i>X`로 — VAN 목록은 tid 오름차순이라 `TX…` 250건이 모두 마지막 페이지 뒤에 몰려 "이미 지나간 자리"가 되지 못하고 스캔 도중 변경이 한 번도 고르지 못한다(마지막 요청은 커서 49,500에서 끝남). `T<i>X`는 원래 단말기 바로 뒤에 끼어 고르게 퍼진다.
    2. healTo를 "짝수 번째 어긋남(k % 2 = 0)"이 아니라 "네 개 한 바퀴씩 번갈아(⌊k / 4⌋ % 2 = 0)" — 종류가 k % 4로 돌아 짝수 k는 미등록(등록이 없어 붙을 수 없음)·정지뿐이라 계획대로면 healTo가 정지에만 붙었다(첫 다섯 번 실행에서 그랬다, 아래 "앞선 실행").
    3. 계획의 세 확인(A 후보 = 확정 = 심은 수, B 후보 = 확정 + 풀림, C 풀림 0)에 정답 집합 비교를 더했다(위). B의 식은 지금 코드의 `unverifiable`(재검증 확인 불가)까지 넣어 `후보 = 확정 + 풀림 + 확인 불가`.
    4. 계획 뒤 바뀐 코드에 맞춤: 하트비트(`heartbeat_at`, 페이지·재검증 블록마다 UPDATE), 페이지마다 같은 시리얼 확인 SELECT(`pickPageRows`, serialKey 정규화), 안전장치(수집 급감·후보 상한 — 이번 규모에서는 걸리지 않음: 첫 실행은 이전 COMPLETED가 없고, 후보 최대 1,943 < 상한 10,000), 확인 불가 항목. `acknowledgeDrop`은 필요 없었다.
    5. DB 왕복 시간을 재려고 `test/helpers/query-log.ts`의 `captureQueries`에 `took` 배열을 더했다(기존 사용처는 그대로). 수집 시간이 예상보다 커서 HTTP만 받는 참고 측정과 종류별 DB 시간을 더했다 → troubleshooting/0023.
    6. 끝나면 `resetDatabase`로 테스트 DB를 되돌린다(확인: terminal·스테이징·실행·결과·outbox 0행) — 계획은 앱만 닫았다.

## 결론

1. **시간: 5만 건 약 6.8~7.2초, 그중 수집이 91%(6.2초)**. 비교(SQL 두 문장, 한 트랜잭션)는 약 215ms, 재검증은 후보 1,000건에 약 240ms·1,943건에 약 370ms(동시 8). 여섯 번 실행의 흔들림은 수집 ±0.5초 안(2번 A가 6,670으로 가장 컸다).
   - 수집 6.2초 중 HTTP·JSON은 약 0.11초뿐이고, DB 왕복이 대부분이다: 스테이징 INSERT 100번 4,968ms(한 번 약 50ms), 하트비트 UPDATE 101번 373ms, 페이지 중복 확인 SELECT 100번 219ms. 나머지 약 0.5초는 JS(행 만들기·정규화·MikroORM 쿼리 빌더) — 이것은 남은 값으로 본 **추정**.
   - 500행 INSERT 한 번 50ms 중 MySQL 안의 시간은 약 6ms이고, 약 41ms는 16KB가 넘는 문장을 호스트 → Docker Desktop으로 보낼 때 생기는 기다림이다(troubleshooting/0023, 원인은 추정). 그래서 이 PC의 수집 6.2초 중 **약 4.2초(≈ 42ms × 100)는 개발 환경의 전송 기다림으로 추정**한다. 운영 환경에서 같은지 모르므로 코드(페이지 크기·INSERT 묶음)는 바꾸지 않았다.
2. **쿼리 수는 등록 수가 아니라 페이지 수와 후보 블록 수에 비례한다**. A 343개 = select 119 · insert 104 · update 112 · delete 1 · 트랜잭션 6. 코드에서 센 구성(추정이 아니라 코드와 숫자가 맞는지 맞춰 본 것): insert 104 = 페이지 100 + 결과 묶음 2(1,000행 ÷ 500) + 실행 행 1 + Outbox 1(계획의 예상과 같음), update 112 = 페이지 하트비트 100 + 수집 시작 1 + 재검증 블록 10(1,000 ÷ 100) + 완료 1, select 119 = 페이지 중복 확인 100 + 재검증 블록의 우리 쪽 10 + 그 밖 9. C(후보 1,943 → 블록 20, 결과 묶음 4)는 select +10·update +10·insert +2로 그만큼만 늘었다. B·C의 delete 12 = 시작 때 이번 실행 스테이징 지우기 1 + 이전 실행 스테이징 5만 행을 5,000행씩 11번(마지막은 0행).
3. **업체 호출 = 페이지 수 + 후보 수**(재시도 0). A 1,100 = 목록 100 + 시리얼 조회 1,000, C 2,043 = 100 + 1,943. 재검증 조회 수 = 후보 수.
4. **스캔 도중 변경(B)**: 페이지마다 10건, 모두 990건이 바뀌었고 그중 healTo로 고쳐진 것 3건. 지나간 자리만 바뀌므로 스냅샷은 심은 그대로라 **후보 = 심은 1,000건(정답과 같은 집합)**. 그중 6건은 실행이 끝났을 때 이미 어긋남이 아니었다 — **재검증 없이 확정했다면 거짓 양성 6건(0.6%)이 알림·리포트에 갔다**. 재검증이 6건 모두 풀림(verified=false)으로 걸렀고, **재검증 뒤 거짓 양성 0**. 확정 994 = 심은 것 중 정답에 남은 수와 같다. 종류가 바뀐 것도 있다(가맹점 다름 250 → 244, 정지 250 → 253 — 추론: 가맹점 다름 등록이 ACTIVE → SUSPENDED로 뒤집혀 재검증이 지금 값의 종류 "정지"로 확정 — 재검증이 종류도 지금 값으로 다시 정한다는 것이 보인다). 풀린 6건이 어느 경로(healTo 3건, 운영 아님 등록이 ACTIVE → SUSPENDED로 뒤집힘)로 풀렸는지 건별로는 세지 않았다.
5. **놓침**: B는 정답 1,943건 중 949건을 놓쳤다 = 지나간 자리에서 새로 생긴 어긋남(정상 ACTIVE 등록이 SUSPENDED로 뒤집힘) 949건과 정확히 같다(`bMissed = newInPassed`). 재검증은 후보만 다시 보므로 비교 뒤·지나간 자리의 새 어긋남은 이번 실행이 찾을 수 없다(설계대로, 스펙 8장 "같은 실행에서 놓친 어긋남 잡기"는 하지 않음). **C가 949건을 모두 찾았다**(확정 1,943 = 정답, 놓침 0, 거짓 양성 0, 풀림 0) — 다음 실행이 메운다. 하루 한 번 주기면 놓친 어긋남은 최대 하루 늦게 알려진다.
6. 변경 10건/페이지(실행 한 번에 990건, 등록의 2%)가 현실보다 많은지 적은지는 모른다(가정). 이 숫자에서는 놓침(949)이 거짓 양성(6)보다 훨씬 크다 — 변경 모델이 "정상 등록의 상태 뒤집기"를 대부분으로 만들기 때문이다(고칠 값이 있는 등록은 375건뿐).
- 결정에 보탠 것: decisions/0033에 숫자 한 줄. 코드는 바꾸지 않았다(재검증이 필요하다는 것, 쿼리·호출 수가 페이지·후보에 비례한다는 것이 설계 그대로였고, 수집 시간의 대부분은 개발 환경 전송 기다림으로 추정).
- 한계: 가상 VAN이 같은 PC(HTTP 지연 0, 429·5xx 0), 변경 모델이 단순(지나간 자리만, 균등 선택, 실행 사이에는 바뀌지 않음), 우리 쪽은 실험 동안 바뀌지 않음, 시드 하나(12), 규모 하나(5만). 수집 시간은 Docker Desktop 전송 기다림이 섞인 값(troubleshooting/0023). 동시 8의 재검증은 지연 0이라 동시성 효과를 재지 못했다.
