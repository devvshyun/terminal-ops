# 0013. 단말기 목록 API — 단말기 10만 대, joined 대 select-in

- 날짜 / 관련 기능: 2026-10-27 / F1(어드민 단말기 목록), decisions/0039
- 질문
  1. 어드민 단말기 목록(`GET /terminals`, offset + total, 모델·가맹점 함께)이 단말기 10만 대에서 조건별로 얼마나 걸리나.
  2. MikroORM 기본(joined)과 select-in의 실행계획·시간 차이는. count(total)는 각각 얼마를 차지하나.
- 설정
  - 로컬 한 PC(Windows 11), Docker MySQL 8.4, 테스트 DB `terminal_ops_test`. 같은 프로세스의 supertest(HTTP), 네트워크 왕복 없음.
  - 데이터: 단말기 N = 100,000을 SQL 한 번으로 넣음(`EXP-000000`…). 상태 12개 고르게(`n % 12`), 모델 `(n div 12) % 3`, 가맹점은 배정~운영 중(ALLOCATED·SHIPPED·DELIVERED·IN_SERVICE) 상태만 `(n div 36) % 3`. 넣은 뒤 `analyze table terminal`.
  - 측정: 조건 8개 × 방식 2개(joined·select-in)마다 서비스 `list(query, strategy)`를 한 번 불러 보낸 SQL을 잡고(`captureQueries`), 다시 RUNS = 20번 불러 p50·p95(ms). 잡은 SELECT마다 `EXPLAIN ANALYZE`. 그다음 HTTP(지금 코드 = select-in)를 한 번 데운 뒤 20번. size 20.
  - 서비스 호출은 `RequestContext.create`로 요청마다 컨텍스트를 만든다(HTTP 요청 하나와 같게 — 아이덴티티 맵이 쌓이지 않는다).
- 재현(`apps/api`, Git Bash, 다른 api vitest가 돌지 않을 때):
  ```bash

  grep -E "실험 0013|^\|" "$TEMP/exp13.log"
  ```

  규모: `EXP_TERMINALS`(기본 100000), `EXP_RUNS`(20). 끝나면 `resetDatabase`로 테스트 DB를 되돌린다(확인: `terminal_ops_test.terminal` 0행).

## 사전 검증(계획)에서 예상한 모양과 비교

- 같음: 조건 없음 joined의 목록 `Sort: t0.id DESC, limit input to 20 row(s) per chunk` 아래 `Table scan on t0` 100000행 + 해시 조인, count가 `terminal_model_id_index` 룩업으로 100000행을 도는 Nested loop. 조건 없음 select-in의 `Index scan on t0 using PRIMARY (reverse)` 20행·`Count rows in t0`·`where id in (…)`. 모델 조건 select-in의 거르기용 `inner join … where t1.code = 'SN-200'` → `terminal_model_id_index (reverse)`. offset 끝쪽(상태 400쪽)의 `limit input to 8000 row(s)`. 시리얼 앞부분의 `terminal_serial_no_unique` 범위.
- 다름: 계획은 상태 조건이 `terminal_status_status_changed_at_index`를 쓴다고 적었는데, **상태 1쪽 select-in의 목록 SQL은 그 인덱스가 아니라 PK를 거꾸로 읽으며 status로 거른다**(225행 읽고 20행에서 멈춤 — IN_SERVICE가 12개 중 하나라 앞쪽에서 금방 20개가 찬다). 상태 인덱스는 count와 400쪽(offset 7980) 목록에서만 쓰였다. 옵티마이저가 LIMIT 20 + 고른 분포에서 "PK 역순으로 읽다 멈추기"를 더 싸게 본 것으로 보이며(추측), 분포가 치우친 상태(예: 드문 상태)에서는 다를 수 있다 — 이번에 재지 않았다.
- 가맹점 조건의 거르기용 조인은 계획이 적은 inner join이 아니라 `left join … where m1.code = …`로 나갔다(MikroORM이 nullable 연관이라 left join을 붙인 것). where가 m1 값을 요구하므로 결과는 inner join과 같고, MySQL은 `terminal_merchant_id_index (reverse)`로 읽었다.

## 결론

- **select-in으로 바꾼 이유(숫자)**: 조건 없음 1쪽 서비스 p50이 joined 91.2ms → select-in 5.2ms(약 17.5배). joined는 LIMIT 20인데도 10만 행 전체를 모델·가맹점과 해시 조인한 뒤 정렬하고(목록 실측 102ms), count도 같은 조인으로 10만 행을 돈다(67.3ms). select-in은 목록이 PK 역순 20행에서 멈추고, count는 `Count rows in t0`(4.26ms). 모델 조건 36.1 → 3.6ms(약 10배), 가맹점 조건 21.1 → 3.5ms(약 6배), 상태 조건 21.7 → 3.3ms(약 6.6배).
- **select-in이 지는 곳**: 결과가 작은 조건(시리얼 앞부분, total 100)은 joined 2.1ms 대 select-in 2.9ms — 왕복이 2번에서 3~4번으로(목록·count에 모델·가맹점을 따로 읽는다. 쪽에 가맹점이 하나도 없으면 3번 — decisions/0039와 같은 셈) 늘어난 몫이 이긴다. 1ms 안팎이라 그대로 둔다.
- **offset 끝쪽 비용**: 상태 IN_SERVICE 1쪽 3.3ms 대 400쪽(끝) 10.3ms(약 3배) — offset 7980을 건너뛰려고 8,000행을 정렬한다. 조건 없음 2000쪽은 PK 역순 4만 행을 읽어 10.1ms(1쪽 5.2ms의 약 2배). 10만 대에서는 끝쪽도 HTTP p95 16ms 아래다.
- **count의 몫**: select-in에서 조건 없음 count는 4.26ms로 1쪽 서비스 p50 5.2ms의 대부분이다(목록 자체는 0.04ms). 조건이 있으면 count는 해당 인덱스를 커버링으로 읽어 1~3ms(상태 1.76ms, 모델 3.16ms).
- HTTP(select-in) p50은 서비스 p50보다 1.8~2.2ms 더 걸린다(직렬화·파이프·검증).

## 한계

- 같은 PC·같은 프로세스, 네트워크 왕복 없음(실제 DB가 원격이면 select-in의 왕복 3~4번이 더 비싸진다), 버퍼 풀이 데워진 상태, 동시 요청 없음.
- 모델 3·가맹점 3이라 조인 표가 아주 작다. 가맹점이 수만이면 joined의 해시 조인은 더 무거워지고, select-in의 `in (…)`은 페이지 20행이라 최대 20개로 그대로다.
- 상태 분포가 고르다(각 1/12). 드문 상태의 1쪽 계획(PK 역순 대 상태 인덱스)은 재지 않았다.
- 한 번 실행한 값이다(p50·p95는 같은 실행 안의 20회).
- 정정(2026-10-27 Day 7): "왕복 2→4번"을 "2→3~4번"으로 고쳤다(Day 6 최종 리뷰 이월). 다시 재지 않고 쿼리 구성(목록·count + 모델 + 가맹점, 가맹점 없는 쪽은 셋)으로 센 것이다.
