## 결론

- **요청 하나: 캐시 없음 약 170ms 대 적중 0.4ms(서비스), HTTP로는 약 175ms 대 2ms**. 서비스 호출 기준 p50 약 420배(169.1/0.4, 172.5/0.4), HTTP 기준 약 86~95배(172.8/2.0, 180.0/1.9). HTTP 적중 2ms의 대부분은 Nest 파이프라인·supertest·JSON(1,018바이트)이고 Redis GET은 0.4ms 안에 든다.
- **비용은 쿼리 두 개에 몰려 있다**: 상태·모델 집계(`terminal ⋈ terminal_model group by`) 84·86ms, 이번 주 이력 훑기 69·77ms. 나머지 다섯은 합쳐 약 10ms(접속 상태 8ms). 이력 훑기보다 상태·모델 집계가 더 컸다(계획 사전 검증 84 대 67ms와 같은 방향). 둘 다 캐시가 가리므로 쿼리는 바꾸지 않았다.
- **캐시가 빈 순간에는 캐시만으로는 아무것도 줄지 않는다**: 동시 50개에서 "캐시 없음"과 "캐시만"이 똑같이 SELECT 350(= 50 × 7), 이력 훑기 50번, 전체 약 1.5초, 요청별 p50 약 0.9초였다. 50개 모두 캐시를 읽고 비어 있음을 본 뒤 각자 집계하기 때문이다. 요청별 최소가 약 300ms(혼자일 때 170ms의 약 1.8배)이고 p50이 약 900ms인 것은 연결 풀 10개를 넘는 집계가 줄을 서고, 동시에 도는 무거운 쿼리 10개가 서로 느려졌기 때문으로 본다(추정 — 풀 대기 시간을 따로 재지 않았다).
- **single-flight가 집계 한 번으로 줄였다**: SELECT 7, 이력 훑기 1번, 전체 169~190ms — 50개 모두 그 집계 하나를 기다려 요청별 시간이 집계 한 번과 같다. 캐시가 빈 순간의 비용이 "집계 50번 1.5초"에서 "집계 1번 0.17~0.19초"가 됐다.
- **새로고침 50개도 집계 한 번**(SELECT 7): 새로고침끼리는 `refreshInflight` 하나를 함께 쓴다.
- **④ 새로고침은 진행 중 일반 집계에 합류하지 않았다**: 2회 모두 집계 2번(SELECT 14, 이력 훑기 2번). 일반 25개는 모두 같은 cachedAt, 새로고침 25개는 모두 그보다 25~32ms 늦은 cachedAt을 받았고, 끝난 뒤 캐시에는 새로고침 값이 남았다. 2회차는 일반 집계가 더 늦게 끝났지만(198.1 대 174.7ms, 둘이 겹쳐 서로 느려짐) 캐시를 덮지 않았다 — 먼저 시작한 집계는 더 나중에 시작한 집계가 쓴 캐시를 덮지 않는 규칙(decisions/0044) 그대로. 겹치는 동안 두 집계가 함께 돌아 각자 혼자일 때(약 170ms)보다 조금 느렸다.
- **적중 꼬리**: 동시 50개 적중이 1회차 전체 1.2ms(p95 0.9ms), 2회차 전체 16.7ms(p50 16.1ms)로 갈렸다. 2회차는 50개가 거의 다 같이 약 16ms 기다렸다 — 그 순간 이벤트 루프가 다른 일(GC 등)로 막혔던 것으로 보이나 원인은 확인하지 않았다(추정). 계획 사전 검증에서도 p95 22.6ms 꼬리가 한 번 있었다. 어느 쪽이든 집계(170ms)보다 한 자릿수 작다.
- decisions/0044의 결정(TTL 30초 + 프로세스 안 single-flight, Redis 잠금 없음)을 숫자가 받친다: 캐시가 빈 순간의 동시 미스가 이 프로세스에서 집계 한 번으로 줄었고, 새로고침이 겹쳐도 최대 두 번이다.

## 한계

- 같은 PC·같은 프로세스(네트워크 왕복 없음, HTTP는 supertest). 실제 브라우저까지의 시간은 재지 않았다.
- 버퍼 풀이 데워진 상태(첫 집계 한 번으로 데움). 128MB 버퍼 풀에 이력 100만 행이 다 들어가는지는 확인하지 않았다 — 차가운 캐시의 첫 집계는 더 느릴 수 있다.
- 프로세스 하나. api 프로세스가 여럿이면 캐시가 빈 순간에 프로세스 수만큼 집계한다(decisions/0044) — 재지 않음.
- "이번 주 전이 수"는 돌린 요일에 따라 결과(4,347)만 다르고 훑는 범위는 같다(occurred_at 인덱스 없음 — 이력 전체 훑기, decisions/0036).
- 쿼리 자체를 줄이는 시도(상태·모델 집계를 model_id로 묶고 모델 코드는 따로 붙이기 등)는 하지 않았다.
- ④의 "20ms 뒤"는 setTimeout 기준이라 실제 간격은 25.4·31.9ms였다. 새로고침이 일반 집계가 거의 끝난 뒤에 오는 경우(겹침이 짧은 경우)는 따로 보지 않았다.
- Redis 장애 시 지연(decisions/0044 결과·대가)은 이 실험에서 재지 않았다.
