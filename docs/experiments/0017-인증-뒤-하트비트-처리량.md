## 결론

- 기본 부하는 인증 뒤에도 다 받는다(두 번 실행 모두 30,000/30,000·오류 0, p50·p95 차이는 회차 사이 차이 안). Redis 명령 수도 같다. 0008의 결론(Redis 경로, 묶음 보내기)은 그대로다.
- 단건 최대 처리량은 이번에 평균 −3.3%(사전 검증 −4.9%), p50은 약 0.1ms(사전 검증 0.2ms) 늘었다. 라운드별로는 −7.2%·+6.4%·−7.2%로 갈려, 라운드 사이 흔들림(최대 약 20%)이 차이보다 크다. 두 번의 측정 모두 기준(10% 안)에 들어 공유 키를 그대로 둔다(decisions/0055). 시뮬레이터 기본 묶음은 100이다.
- 묶음 100 최대는 사전 검증에서 차이가 없었고, 이번에는 −14.4%·−2.0%·+0.9%(평균 −5.4%)로 갈렸다. 요청 수가 단건의 1/100이라 요청당 약 0.1~0.2ms가 p50 6~9ms에 비해 몇 %를 넘기 어렵다고 보지만, 1라운드의 −14%는 설명하지 못했다(2·3라운드에서 되풀이되지 않음 — 잡음으로 본다. 확인한 것은 아님). 이 차이로 결정이 바뀌지는 않는다(기준은 단건 최대).
- 결론은 사전 검증과 같다: 인증을 더해도 0008의 부하를 다 받고, 한계 처리량 감소는 기준 안이다.
- 한계: 닫힌 루프(동시 16 상한)라 처리량은 16 / 응답 시간이다. 요청당 비용 중 가드(Reflector 조회·분기)와 SHA-256의 몫을 나눠 재지 않았다. 같은 PC의 다른 일·온도에 따라 같은 코드가 20% 가까이 달라졌다 — 번갈아 잰 값만 믿고, 그것도 라운드 3개로는 몇 % 차이를 가르기에 부족하다.
