# 0018. 현장 앱에 글꼴을 넣기 전후 첫 화면 전송량

- 날짜 / 관련 기능: 2026-10-29 / 현장 화면(`apps/field`), decisions/0077
- 질문: `@fontsource` IBM Plex Sans KR·Mono를 앱에 넣으면 첫 화면(캐시 없음)에서 CSS·글꼴을 얼마나 더 받나? 굵기를 셋에서 둘로 줄이면 얼마나 줄어드나?
- 설정: `apps/field`를 `npx vite build` 뒤 `npx vite preview --port 4175`. Playwright Chromium(컨테이너에 설치된 것), 새 컨텍스트(캐시 없음), 375×812, `/api/*`는 가짜 응답(Playwright route). Chrome DevTools Protocol `Network.loadingFinished`의 `encodedDataLength`(압축된 전송 바이트, 헤더 포함)를 파일 확장자별로 더했다. `document.fonts.ready` 뒤 0.5초 기다림. 클라우드 컨테이너(Linux), localhost — 네트워크 시간은 재지 않았다.
  - 전 = 커밋 10a3f6c의 현장 앱(시스템 글꼴, `git stash -u`로 작업 트리를 되돌려 빌드)
  - 후(굵기 3) = Sans 400·600·700 + Mono 400·600
  - 후(굵기 2) = Sans 400·700 + Mono 400·600 (채택)
- 재현: 측정 스크립트는 세션 scratchpad의 `measure.cjs`(저장소 밖). 핵심: 새 컨텍스트 → CDP `Network.enable` → `page.goto(base + path, { waitUntil: 'networkidle' })` → `document.fonts.ready` → 확장자별 `encodedDataLength` 합계.

## 결론

- 글꼴을 넣으면 첫 화면이 약 290KB(CSS +68KB, 글꼴 +204~223KB) 늘어난다. 굵기 셋보다 둘이 CSS 31KB·글꼴 90KB 적다 → 굵기 둘로(decisions/0077).
- CSS가 커진 것은 unicode-range 조각마다 `@font-face` 규칙이 있어서다(굵기 하나에 규칙 94개). 이 CSS는 화면을 그리기 전에 받아야 하므로, 글꼴 파일보다 첫 화면을 더 늦출 수 있다.

## 한계

- 네트워크 시간(창고 Wi-Fi·PDA)은 재지 않았다. 바이트만 잰 것이다.
- 화면마다 받는 조각은 그 화면에 나온 글자에 따라 다르다(`/scan`이 하나 더 받았다). 데이터가 바뀌면 조금씩 달라진다.
- 한 번씩만 쟀다(결정적인 값이라 반복하지 않았다 — 같은 빌드·같은 화면이면 같은 파일을 받는다).
