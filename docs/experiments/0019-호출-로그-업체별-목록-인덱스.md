# 0019. 호출 로그 업체별 목록 — (partner_id, id) 인덱스

- 날짜 / 관련 기능: 2026-10-29 / 보강 7 호출 로그(`partner_api_call`), decisions/0082
- 질문: `GET /admin/partner-calls?partnerId=&beforeId=`(최근부터 51줄)가 (partner_id, id) 인덱스를 거꾸로 읽나? 인덱스가 없으면(PK 역순으로 읽으며 거르기) 얼마나 더 읽나?
- 설정: 클라우드 컨테이너, MySQL 8.4.13(docker), 테스트 DB `terminal_ops_test`를 비우고 마이그레이션 전부 up. 업체 5곳·키 10개, 호출 200,000줄(업체 1이 70% = 140,000, 업체 2·4가 각 10,000, 3·5가 각 20,000 — 업체 2는 10줄에 하나꼴로 고르게 섞여 있다). `analyze table` 뒤 `EXPLAIN ANALYZE`를 세 번.
- 재현(테스트 DB에서, root):
  ```sql
  insert into partner (code,name,created_by,created_at) select concat('X-',n),concat('업체',n),'exp',now() from (select 1 n union select 2 union select 3 union select 4 union select 5) t;
  insert into partner_api_key (partner_id,name,prefix,key_hash,scopes,created_by,created_at) select ((n-1) div 2)+1, concat('k',n), concat('pk_exp000', lpad(n,2,'0')), repeat('a',64), '[]','exp',now() from (with recursive s(n) as (select 1 union all select n+1 from s where n<10) select n from s) t;
  set session cte_max_recursion_depth=300000;
  insert into partner_api_call (partner_id,key_id,method,path,status,duration_ms,created_at) with recursive s(n) as (select 1 union all select n+1 from s where n<200000) select case when n%10<7 then 1 else ((n%4)+2) end, case when n%10<7 then 1+(n%2) else ((n%4)+1)*2+1 end, 'GET','/partner/v1/terminals/X',200,5,now(3) from s;
  analyze table partner_api_call;
  explain analyze select * from partner_api_call where partner_id=2 and id < 150000 order by id desc limit 51;
  explain analyze select * from partner_api_call ignore index (partner_api_call_partner_id_id_index) where partner_id=2 and id < 150000 order by id desc limit 51;
  ```

## 결과

| 쿼리 | 고른 인덱스 | 읽은 행 | Limit 실제 시간(ms, 3회) |
|---|---|---|---|
| 업체 2, beforeId 150000 | `partner_api_call_partner_id_id_index` 역순 range | 51 | 0.469 / 0.28 / 0.433 |
| 같은 쿼리, 그 인덱스 무시 | PRIMARY 역순 range + 거르기 | 1,012 | 0.794 / 0.542 / 0.671 |
| 키 7, beforeId 150000(EXPLAIN만) | `partner_api_call_key_id_id_index` 역순 range | (추정 7,500) | — |
| 거르기 없음, beforeId 150000(EXPLAIN만) | PRIMARY 역순 | (추정 99,592) | — |

첫 실행 한 번은 0.854ms까지 걸린 인덱스 range가 Limit에서 210ms로 나왔다(버퍼 풀이 비어 있던 첫 읽기로 본다 — 확인하지는 않았다). 표는 그 뒤 세 번.

## 결론

- 옵티마이저는 업체·키로 거를 때 복합 인덱스를 거꾸로 읽고, 딱 51줄만 읽는다. 외래키 열 하나짜리 인덱스는 두지 않았다(`@ManyToOne({ index: false })`) — 복합 인덱스의 앞부분이 외래키 검사도 맡는다(`show create table`에서 외래키가 복합 인덱스로 서 있다).
- 이 규모(20만 줄, 업체가 고르게 섞임)에서는 인덱스가 없어도 1ms 안이다(1,012줄). 차이가 커지는 경우는 드문 업체가 오래전에만 불렀을 때 — PK 역순으로 그 업체를 찾을 때까지 다른 업체 줄을 다 읽는다. 그래서 인덱스를 둔다(쓰기마다 보조 인덱스 둘).
- 쓰기 비용(insert 한 줄에 보조 인덱스 둘)은 재지 않았다.
