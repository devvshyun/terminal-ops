- B를 버린 이유: 업무 규칙(상태 전이·배포 중단)이 브라우저에 한 벌 더 생긴다. "상태 변경은 전이 서비스 한 곳"(CLAUDE.md)과 부딪히고, 보이는 반응이 실제 백엔드의 것이 아니게 된다
- C를 버린 이유: 계정·비용·운영 부담, 시연 계정이 공개 인터넷에 열린다
- A를 고른 이유: 녹화본도 실제 서버가 낸 응답이다 — "백엔드가 진짜로 반응한다"는 이 프로젝트의 요점이 지켜진다
- 저장소가 공개(public)인지 확인했다 — 비공개면 Pages에 유료 플랜이 필요했다

### 2-2. 재생 엔진 먼저(`src/replay/engine.ts`)
- 설계: "녹화 시계" 하나(결정 0094). 실행을 누르면 시계가 그 시각으로, 끝나면 다음 실행까지 8배속으로 흐르다 멈춘다
- **시행착오 1 — 실행 직후 읽기가 실행 전 값을 냈다.** 처음 엔진은 POST를 받으면 시계를 그 POST의 녹화 시각으로만 옮겼다. 테스트 결과 `Tests  1 failed | 6 passed (7)`: 출고 직후 단말기 상태가 `SHIPPED`가 아니라 `IN_STOCK`이었다. 녹화에서 결과 패널이 다시 읽은 응답은 POST보다 100~300ms 뒤에 찍히는데, 재생에서는 실행이 끝나자마자 다시 읽기 때문이다
  - "POST 뒤 2초 건너뛰기"도 생각했지만 버렸다. 실행 하나 안에서 POST 뒤 2초 안에 다음 POST가 있으면(재고 고르기 → 출고), 그 다음 일까지 이미 일어난 재고 목록을 읽게 된다
  - 해결: 녹화기가 실행마다 **끝난 때(end)**를 적는다(단추가 돌아오고 1.5초 뒤). 실행 안의 GET은 "다음 POST 바로 앞" 시각으로, 실행이 끝나면 시계를 end로. 테스트 7개 통과
- 테스트를 엔진보다 먼저 쓰지 못했다(엔진 모양을 정하며 같이 썼다). 첫 실행에서 위의 실패가 나와 테스트가 실제로 잡는다는 것은 확인됐다

### 2-3. 녹화기(`scripts/record.cjs`)
- 보강 10 리허설 스크립트(scratchpad의 `dh.cjs`)를 바탕으로, 응답 기록·실행 시각·다른 화면 사진을 더했다
- 리허설에서는 건너뛴 두 일도 실제로 한다: 4막 점주 고장 접수(매장 화면에서 DM-0004)와 교체품 도착 뒤 설치 확인
- **시행착오 2 — 같은 제목의 단계.** 단계 key를 제목으로 찾았는데 "되돌리기: 0%"가 5막과 6막에 같은 제목으로 있었다. 녹화 로그에 `실행 undefined "번개택배 429 확률 0%"`가 찍혔다. 녹화가 이미 돌고 있어 스크립트만 단추 글자로 먼저 찾게 고쳤다 — 그 녹화는 어차피 6막에서 멈춰(시행착오 3) 버렸고, 다음 녹화부터 key가 모두 채워졌다

- **시행착오 3 — 첫 녹화가 6막에서 멈췄다.** 녹화 191초에 "정상 배포"를 누른 뒤 "· 완료"가 나오지 않았다(리허설에서는 25초). DB를 보니 3단계 대상 5대 가운데 1대만 보고가 없었다 — 4막에서 점주가 설치를 확인한 교체품 DM-0014였다. 시뮬레이터는 시연 데이터의 13대만 돌아 DM-0014를 모른다. 리허설은 설치 확인을 건너뛰어 이 연결을 못 봤다
  - 녹화를 멈추고(PID로 종료), 시연 홈 배포 실행이 배포 전에 "운영 중인데 시뮬레이터가 모르는 단말기"를 시뮬레이터에 더하게 고쳤다(테스트 먼저 → 실패 1 → 통과)
  - web 이미지를 다시 빌드하고 `down -v`부터 다시 녹화(트러블슈팅 0040)
- **시행착오 4 — 다시 빌드한 web 이미지가 실패했다.** 재생 시작점이 녹화본을 `import`하고 있어서, 녹화본이 아직 없는 보통 빌드의 타입 검사가 `Cannot find module './recording.json'`으로 깨졌다. 녹화하려면 이미지가 필요하고, 이미지를 만들려면 녹화본이 필요한 닭과 달걀이다. 녹화본을 코드에 묶지 않고 재생본이 시작할 때 `recording.json`을 받아 오게 바꿨다 → 보통 빌드는 녹화본과 무관해졌다

### 2-6. 재생본 리허설
- 방법: 재생본을 `vite preview`로 띄우고 Playwright가 7막을 녹화 순서대로 누르며 기대 글 14개를 기다린다. 같은 실행 다시 누르기, 사진 링크, "처음 상태로" 뒤 다시, 390px 폭까지 본다(스크립트는 scratchpad — 저장소 밖)
- **시행착오 6 — 재생본에서 실행 단추가 모두 꺼져 있었다.** 녹화 2에 `/auth/me`를 임시로 붙여(검증용, 커밋 안 함) 돌려도 꺼져 있었다. 로그인 정보는 로그인 칸(`LoginBox`)이 `/auth/me`를 불러 채우는데, 재생본에서는 그 자리를 녹화 시계로 바꿔 아무도 부르지 않았다
  - 화면 테스트가 못 잡은 이유: 실행 단추가 꺼져 있어도, 설명 글 속의 "60%"를 결과로 잘못 찾고 통과했다
  - 테스트를 고쳐(단추가 켜졌는지, 결과 줄 "지금 펌웨어 실패율: 60%"를 정확히) 실패를 본 뒤(`Tests  1 failed | 8 passed (9)`), 녹화 시계가 `/auth/me` 확인을 하게 했다
- **시행착오 7 — 검사 두 개가 너무 쉽게 통과했다.** "자동 중단"은 단계 제목("다시 배포 → 자동 중단")에, "완료"는 설명 글에 이미 있었다. 결과 줄 모양(`자동 중단: N단계`, `A/S #n · 끝`)으로 바꿨다
- 최종(녹화 3): 기대 글 14개 모두, 녹화에 없는 요청 0, pageerror 0, 사진 링크 200, 390px `scrollWidth 390`
  - 기다리는 단계: 배송 완료 11.1초, 오프라인 판정 15.6초
  - 7막 전체 73.8초(녹화는 364초)
  - 8배속인데 50초가 11초인 것은 결과 패널이 5초마다 읽기 때문이다(실험 0020)
- 작업 실수 하나: 미리보기 서버를 끄려고 `pkill -f`를 썼다가 그 명령을 돌리던 셸 자체가 종료됐다. 다른 프로세스는 건드리지 않았지만 "프로세스는 PID로만 종료" 규칙을 어겼다. 그 뒤로는 PID로 껐다

### 2-8. 배포 뒤 사용자 피드백 — "영상인 줄 알았다"
- 배포(PR #7) 뒤 사용자: "이 페이지의 의미가 무슨 의미인지 잘 모르겠어." → "녹화본을 녹화해서 여기에 시연 영상을 순서대로 보여 준다는 거 아니었어?"
- **가장 큰 시행착오(8) — 요청을 다르게 이해했다.** 사용자는 "녹화"를 영상으로, 나는 서버 응답 데이터로 이해했다. 처음 선택지 표(A 녹화 재생, D 영상)에서 A를 권하면서 "A는 열면 저절로 재생되지 않는다"는 차이를 짚지 않았다. 리허설은 모두 "기능이 맞게 도는가"만 봤고 "처음 보는 사람이 이해하는가"는 보지 않았다
- 사용자가 정한 순서: 1) 소개 페이지 2) 녹화 재생본으로 소개(자동 진행) 3) 그 뒤 단편적으로 직접 실행. 사진을 하나하나 눌러야 보이는 것도 불편하다
- 처리(결정 0095):
  - 소개 페이지를 첫 화면으로 두었다
  - 자동 재생: 화면의 실행 단추를 자동 재생기가 대신 누르고, 22단계마다 비개발자용 자막을 띄운다
  - 직접 해 보기로 넘어갈 수 있게 했다
  - 사진은 단계 카드 안에 바로 보이게 했다
- 시행착오 9 — 화면 테스트가 낡은 요소를 붙잡았다. 녹화본의 `/auth/me`가 채워지면 가운데가 새로 그려지는데(로그인한 사람이 바뀌면 다시 그리는 장치), 그 전에 찾아 둔 단추를 눌러 아무 일도 없었다. 전체 실행에서는 우연히 통과하고 파일 하나만 돌리면 실패했다 — 매번 새로 찾게 고친 뒤 5번 연속 통과
- 시행착오 10 — "끝냄" 표시 검사가 엉뚱한 이유로 통과했다. 실행 단계는 실행 단추가 원래 끝냄 표시를 하므로, 자동 재생의 끝냄 표시를 지워도 테스트가 통과했다(일부러 지워 확인). 보기만 하는 단계로 검사를 옮겼다
- 시행착오 11 — 브라우저 리허설에서 진행률이 21/22로 끝났다. 로그를 찍어 보니 내 점검 스크립트가 마지막 자막의 "시연 끝"이라는 글자를 끝 안내로 읽고 "직접 해 보기"를 눌러 버린 것이었다(제품 잘못이 아님). 자막에서 그 말을 뺐다. 같은 로그에서 진짜 문제도 하나 나왔다: 막이 바뀔 때마다 진행 단계가 두 번 시작됐다(`navigate` 함수가 주소마다 새로 만들어져 효과가 다시 돎). 첫 번째가 바로 취소돼 해는 없었지만 고쳤다
- 최종 브라우저 리허설: 소개 → 시연 보기 → 22단계 자동 진행 2분 35초 → 진행률 22/22, 녹화에 없는 요청 0, pageerror 0 → 직접 해 보기 → 5막 429 켜기 직접 실행 "지금 번개택배 429 확률: 50%"

## 3. 남은 것
- 녹화본은 화면·API가 바뀌면 낡는다. 다시 찍기는 명령 하나(README)지만 자동이 아니다 — CI에서 시연 묶음을 띄워 찍는 것은 범위 밖
- 재생본은 녹화한 흐름만 낸다. 입력을 바꾸거나 녹화보다 많이 누르면 "녹화에 없음" 안내가 나온다
- 다른 앱(어드민·매장 화면 등)은 사진뿐이다
- 어드민에서 직접 만든 배포는 "시뮬레이터에 켜기" 보정을 거치지 않는다(troubleshooting/0040)

## 4. 돌아보며
- 잘 된 것
  - 녹화처럼 "전부 실제로" 돌리니 리허설이 건너뛴 연결이 드러났다: 설치 확인 → 6막 배포 멈춤
  - 재생 엔진은 실패하는 테스트로 설계가 한 번 바뀌었다(end 시각)
- 안 된 것
  - **요청을 확인하지 않았다.** "녹화"가 영상인지 데이터인지 묻지 않고 만들어 배포까지 한 뒤에야 어긋난 것을 알았다. 비슷한 단어가 두 뜻으로 읽힐 때는 "열면 어떻게 보이는가"를 한 줄로 그려 확인하고 시작한다
  - 화면 테스트가 엉뚱한 글자로 통과해 실제 리허설에서야 단추가 꺼진 것을 알았다
  - 녹화본의 경로 목록을 녹화 직후 바로 보지 않아 녹화를 한 번 더 했다
  - 다음에는 녹화 직후 경로 목록을 뽑아, 막마다 화면이 읽는 경로와 맞춰 본다
