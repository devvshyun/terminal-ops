- 등장하는 회사(세움전자, 번개택배, 느림보물류, 브릿지VAN, 톡톡메신저)와 가맹점은 모두 가상이다.

## 1. 무엇을 왜

Day 1~5는 API와 배치였다. 운영자는 지금까지 curl로만 시스템을 만졌다. Day 6은 **운영자가 쓰는 화면**을 만든다. 화면을 붙이면 API의 빈 곳이 드러난다 — "목록이 없다", "이 상태에서 무엇을 할 수 있는지 모른다", "오래 걸리는 요청을 브라우저가 기다릴 수 없다". 그래서 화면보다 API 보강을 먼저 한다.

1. **이월 정리(api)**: Outbox·리포트가 도메인 로직 파일을 import하는 방향을 바로잡고(Minor 5), 최악 약 10.6분 걸리는 `POST /reports/weekly`를 report 큐 job + 202로 바꾼다(Minor 6). 사전 검증에서 찾은 **날짜에 기대는 테스트**(이상 찾기 겹침 테스트가 2026-10-26 19:00 KST 이후 실패)를 고친다.
2. **화면용 API(api)**: 단말기 상세에 "지금 할 수 있는 전이·작업"을 서버가 계산해 주고(`allowedTransitions`, `actions`), 가맹점 필터·검수 기록·모델 목록을 더한다. 발주·A/S·펌웨어 배포·VAN 실행·주간 리포트·택배 수집 실행의 목록 API를 같은 모양("최근 것부터, beforeId 더 보기")으로 만든다.
3. **어드민(`apps/admin`, React + Vite)**: 공통 틀(작업자 이름, 오류 표시, KST 시각), 화면 9개(단말기 목록·상세, 박스 스캔, A/S 목록·상세, 펌웨어 배포, 이상 단말기, VAN 대조 목록·상세, 발주 입고 대조, 주간 리포트, 배치 실행 이력).
4. **실험 0013**: 단말기 10만 대에서 목록 API의 실행계획과 응답 시간. 모델·가맹점을 조인해 읽는 방식(MikroORM 기본 joined)과 따로 읽는 방식(select-in)을 비교한다.

## 3. 데이터 모델

테이블·열은 바꾸지 않는다(마이그레이션 없음). 응답 모양만 늘어난다.

- 단말기 목록 항목: `statusChangedAt` 추가.
- 단말기 상세: 목록 항목 + `modelName`, `merchantName`, `allowedTransitions: { to, blockedReason }[]`, `actions: { allocate, cancelAllocation, ship, inspect }`.
- 주간 리포트 보기: `queued`(수동 보내기 job이 대기·처리 중) 추가.
- 발주 보기: `id` 추가(키셋 커서).
- 이상 목록 항목 `ruleLabel`, VAN 결과 항목 `kindLabel`.
- 새 목록 응답: `{ items, nextBeforeId }`(주간 리포트만 `{ items, nextBefore }` — 주가 키).

## 4. 흐름

### 4.1 이월: 레이블 분리, 주간 리포트 비동기 (Minor 5·6)

- `ANOMALY_RULE_LABEL`·`KIND_LABEL`을 enum만 import하는 파일로 옮긴다. outbox·xlsx는 이 파일만 본다. 의존 방향 테스트(import 문을 읽는 단위 테스트)로 다시 거꾸로 가지 않게 한다.
- `POST /reports/weekly { weekStart? }`:
  1. 주 형식 검사(400 `INVALID_WEEK_START`), 끝나지 않은 주 거절(422 `WEEK_NOT_ENDED`) — job을 넣기 전에.
  2. 그 주 행을 만든다(없으면). 이미 `SENT`면 job 없이 200 `{ alreadySent: true, queued: false }`.
  3. report 큐에 `weekly-report-send { weekStart }`, jobId `weekly-report-send-<주>`(대기 중에 다시 눌러도 하나), 재시도 없음, 끝나면 job 삭제. 202 `{ queued: true }`.
  4. 처리기가 기존 `send(week)`를 부른다(잠금·파일·톡톡 재시도는 그대로). 실패하면 행의 `lastError`가 남고 job은 실패로 끝난다. 같은 주를 주기 job이 보내는 중(409)이면 건너뛴다.
  5. `GET /reports/weekly/:weekStart`가 `queued`(job 상태 waiting·active·delayed 등)를 준다. 화면은 `queued`인 동안 2초마다 다시 읽는다.
- `POST /anomaly-scans`는 동기 200 그대로 둔다: 실험 0011에서 단말기 10만 기준 찾기 전체가 첫 실행 약 1.2초, 두 번째 약 0.8초였다.

### 4.2 단말기 상세 — 할 수 있는 일은 서버가 (decisions/0040)

- `transition-rules.ts`에 `targetsFrom(from, source, policy)`: 전이 표(RULES)에서 `from`이 같고 `source`가 허용된 규칙의 `to` 목록, 모델 정책에 막히면 `blockedReason`. `checkTransition`과 같은 표를 읽고, 모든 상태·출처·정책 조합에서 둘이 같은 답을 하는지 단위 테스트로 확인한다.
- 상세의 `allowedTransitions`는 MANUAL(일반 전이 API) 목록, `actions`는 전용 API로만 하는 일(배정·배정 취소 = ALLOCATION, 출고 = SHIPMENT, 검수 = INSPECTION).
- 화면은 이 두 값만 보고 버튼을 그린다. 버튼을 눌러 보내는 요청에는 화면에서 본 `version`(expectedVersion)을 싣는다 — 그사이 다른 변경이 있으면 409 `VERSION_CONFLICT`이고 화면은 "다시 불러오기"를 보여 준다.

### 4.3 목록 API (decisions/0039, 실험 0013)

- 단말기 목록은 지금 모양(offset `page` + `size` + `total`)을 유지한다 — 화면이 "n / m쪽"을 보여 주고, 조건으로 좁혀 보는 목록이라 깊은 쪽을 거의 안 본다. 다만 모델·가맹점을 **select-in**으로 읽는다: joined면 MySQL이 terminal 전체를 해시 조인한 뒤 id로 정렬해 20행을 자른다(실험 0013에서 숫자로).
- 새 목록(발주, A/S 접수, 펌웨어 배포, VAN 실행, 택배 수집 실행)은 최근 것부터 `?beforeId=&limit=`(1~100, 기본 20) → `{ items, nextBeforeId }`. `id < beforeId order by id desc limit n+1` — PK 역순 범위라 몇 번째 쪽이든 비용이 같다. 연관은 select-in.
- 주간 리포트 목록은 주(`week_start`, unique)를 키로: `?before=YYYY-MM-DD`.
- 이상 단말기·VAN 결과는 Day 5 그대로(afterId, 오름차순).
- 배치 실행 이력: 실행마다 행을 남기는 배치는 택배 수집(SyncRun), VAN 대조, 주간 리포트 셋이다. 이상 찾기는 실행 기록 표가 없다(결과는 열린 이상과 알림) — 이번에 표를 만들지 않는다.

### 4.4 어드민 골격 (decisions/0041)

- **개발 서버 프록시**: 브라우저는 Vite(5173)의 `/api/...`만 부르고, Vite가 `http://localhost:3000/...`로 넘긴다. 같은 출처라 api에 CORS를 열지 않는다. api 주소는 `ADMIN_API_URL`로 바꾼다. 운영 배포(정적 파일 + 역프록시)는 범위 밖.
- **작업자 이름**: 화면 위쪽에서 입력 → localStorage `terminal-ops.operator` → 모든 요청에 `X-Operator: encodeURIComponent(이름)`. 규칙은 서버와 같다(1~50자, `system:` 금지). 이름이 없으면 쓰기 버튼(WriteButton)이 꺼진다. 인증이 아니다(decisions/0001).
- **서버 상태**: TanStack Query. 4xx는 재시도하지 않는다. 쓰기가 성공하면 관련 쿼리를 무효화해 다시 읽는다.
- **오류**: `api()`가 2xx가 아니면 `ApiError(status, code, message)`. `ErrorBox`가 코드별 안내(VERSION_CONFLICT, INVALID_TRANSITION, DUPLICATE, PARTNER_ERROR, 400·404)와 서버 메시지·코드를 보여 준다.
- **시각**: api는 UTC ISO를 준다. 화면은 `formatKst`(api의 `common/kst.ts`와 같은 규칙, 'YYYY-MM-DD HH:mm:ss KST')로만 보여 준다.
- **스타일**: 전역 CSS 한 장(`styles.css`), UI 라이브러리 없음.

## 5. 실패 처리

- 낙관적 락 충돌(409 `VERSION_CONFLICT`): 화면이 안내와 "다시 불러오기"(상세 다시 읽기)를 보여 준다. 자동으로 다시 보내지 않는다(운영자가 바뀐 상태를 보고 판단).
- 규칙 위반(422): 서버 메시지를 그대로 보여 준다. 화면이 미리 막은 버튼(blockedReason)도 서버가 다시 검사한다.
- 작업자 이름 없음: 버튼이 꺼진다. 우회해 보내도 서버가 400.
- 비동기 작업 실패: 주간 리포트는 행의 `lastError`, VAN 대조는 실행 행의 `error`(FAILED)로 화면에 보인다. 운영자가 다시 누른다(주간 리포트 job은 재시도 없음).
- api가 꺼져 있음: 프록시가 502를 주고 화면은 "서버에 연결하지 못했습니다"류 안내를 보여 준다.
