## 4. 흐름

### 4.1 QUEUED outbox 복구 (decisions/0042)

워커가 notify job을 처리하다 죽으면 BullMQ는 그 job의 잠금이 풀린 뒤(lockDuration 30초) stalled 검사(30초마다)로 job을 대기열로 되돌린다 — 한 번은 BullMQ가 살린다. 그런데 같은 job이 stalled 한도(maxStalledCount 1)를 넘으면 실패로 옮겨지고 `removeOnFail`로 지워진다. notify가 FAILED를 쓰지 못했으니 행은 **QUEUED로 남고 job은 없다**. Redis에서 job 키가 사라져도 같다. relay는 PENDING만 보므로 이 행은 영영 안 보내진다.

`requeueStale()`: `status = QUEUED and created_at < now − OUTBOX_REQUEUE_AFTER_MS(60초)`인 행을 id 순으로 100개 읽고, 행마다 `queue.getJobState('outbox-<id>')`가 `'unknown'`(없음)일 때만 같은 jobId로 notify job을 다시 넣는다. 행은 바꾸지 않는다. 주기 작업 `outbox-requeue`(outbox 큐, 60초).

### 4.2 데드락 응답 (decisions/0043)

`DeadlockException`(1213)을 필터의 `@Catch`에 넣어 409 `{ code: 'DEADLOCK', message: '…잠시 뒤 다시 시도하세요.' }`. 트랜잭션은 InnoDB가 통째로 롤백했으므로 같은 요청을 다시 보내면 된다. 어드민 ErrorBox에 같은 안내를 둔다. 서버 쪽 자동 재시도는 하지 않는다(일괄 등록의 `retryOnUnique`처럼 이미 재시도하는 경로는 그대로).

### 4.3 목록 이월 (Minor 10·11)

- 배포 목록: 쪽의 배포 id를 모아 `select rollout_id, stage, status, count(*) … where rollout_id in (…) group by rollout_id, stage, status` 한 번. 단건 `stageStats()`도 같은 함수를 쓴다.
- 단말기 목록: `page`는 `@Max(floor(MAX_SAFE_INTEGER / 100))`(size 최대 100이라 offset이 안전한 정수 안), `q`는 `@MaxLength(32)`(시리얼 최대 길이).

### 4.4 어드민 쿼리 키 (Minor 4)

`src/api/query-keys.ts`의 `keys`만 쓴다. 첫 칸이 무효화 단위: 목록 묶음은 복수(`terminals`, `purchase-orders`, `service-tickets`, `van-runs` …), 한 건 묶음은 단수(`terminal`, `purchase-order`, `service-ticket`, `van-run`). 글자는 지금과 같게 둔다(캐시 동작이 바뀌지 않게). 보완하는 무효화: 박스 스캔 성공 → `keys.terminal.all`·`keys.purchaseOrder.all`도, A/S 교체·설치 → `keys.terminal.all`도. 소스를 읽어 `queryKey: [` 글자가 화면에 없는지 검사하는 테스트를 둔다.

### 4.5 대시보드와 캐시 (decisions/0044)

```
GET /dashboard/summary[?refresh=true]
  → DashboardService.summary()
     ├─ refresh가 아니면 Redis GET <prefix>:dash:summary → 있으면 { ...값, fromCache: true }
     ├─ 없으면(또는 refresh) single-flight: 이 프로세스에서 도는 집계가 있으면 그 Promise를 함께 기다린다
     │    └─ DashboardQueries.collect(now): REPEATABLE READ 읽기 전용 트랜잭션에서 쿼리 일곱 개
     │         상태·모델별 수(terminal ⋈ terminal_model group by), 접속 상태(운영 중 ⟕ device_connectivity, 리포트와 같은 창),
     │         열린 이상 규칙별, 진행 중 배포 수, 열린 A/S 수, 최근 COMPLETED VAN, 이번 주(KST 월요일~지금) 전이 수
     └─ 결과 + cachedAt(집계 시각)을 SET … PX DASHBOARD_CACHE_TTL_MS(30초), { ...값, fromCache: false }
```

- 무효화: **TTL만.** 전이마다 지우지 않는다 — 전이는 이력·Outbox를 쓰는 가장 잦은 쓰기이고, 대시보드 숫자는 "운영 현황"이라 30초 늦어도 판단이 바뀌지 않는다. 대신 화면이 집계 시각을 보여 주고 새로고침(refresh=true)으로 바로 다시 집계할 수 있다.
- 동시 미스: 프로세스 안 single-flight(Promise 공유). Redis SET NX 잠금은 두지 않는다 — api 프로세스는 한두 개라 최악에도 프로세스 수만큼만 집계한다. 실험 0015가 "묶지 않으면 동시 50개 = 집계 50번"을 잰다.
- Redis 실패: 캐시 읽기·쓰기 실패는 경고만 남기고 캐시 없이 집계해 준다.
- 응답: `{ terminals: { total, byStatus[], byModel[] }, connectivity, anomalies: { open, byRule[{rule,label,open}] }, rollouts: { active }, serviceTickets: { open }, van: {runId, finishedAt, confirmed, counts} | null, week: { weekStart, transitions }, cachedAt, fromCache }`.

## 7. 기록할 결정

- 0042 QUEUED outbox 복구는 같은 jobId로 다시 넣기(행을 PENDING으로 돌리지 않음, queued_at 열 없음)
