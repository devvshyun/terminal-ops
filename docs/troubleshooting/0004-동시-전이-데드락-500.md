# 0004. 같은 단말기 동시 전이에서 데드락이 나고 500으로 응답

- 날짜 / 관련 기능: 2026-10-22 / F2 (Task 6 동시 수정 실험)
- 증상: 실험 테스트(`test/terminal-concurrency.e2e.spec.ts`)를 계획 그대로 3회 돌렸더니 3회 모두 2개 테스트가 실패했다. 기대는 A `{"200":1,"409":19}`, B 실패 사유는 OptimisticLock·InvalidTransition 두 가지뿐.
  ```
  [실험 A] N=20 결과={"200":1,"409":11,"500":8} 소요=62ms
  [실험 B] N=20 성공=1 실패={"DeadlockException: Deadlock found when trying to get lock; try restarting transaction":11,"OptimisticLock":1,"InvalidTransition":7}
  [실험 A] N=20 결과={"200":1,"409":11,"500":8} 소요=62ms
  [실험 B] N=20 성공=1 실패={"DeadlockException: Deadlock found when trying to get lock; try restarting transaction":11,"OptimisticLock":1,"InvalidTransition":7}
  [실험 A] N=20 결과={"200":1,"409":11,"500":8} 소요=64ms
  [실험 B] N=20 성공=1 실패={"DeadlockException: Deadlock found when trying to get lock; try restarting transaction":9,"InvalidTransition":10}
  ```
  Nest 로그(요약): `ERROR [ExceptionsHandler] DeadlockException ... at MySqlDriver.nativeUpdate ... at ChangeSetPersister.executeUpdates`, `code: 'ER_LOCK_DEADLOCK', errno: 1213`, `sql: "update terminal set status = 'ALLOCATED', ..., version = version + 1 where id = 1 and version = 2"`.
  `DomainExceptionFilter`는 데드락을 모르므로 500이 됐다. 성공 건수는 1건으로 맞았다(측정). 이력 건수는 재지 못했다. 응답 코드 단언이 먼저 실패해 `countHistory`까지 가지 않았다. 추정: 데드락 희생 트랜잭션은 통째로 롤백되므로 이력도 1건이었을 것이고, 데이터는 깨지지 않고 응답 코드만 틀렸을 것이다. (같은 순서 문제를 Task 7 검수에서 재현했을 때는 검수 기록·이력이 1건씩인 것을 실제로 쟀다 → experiments/0002)
- 가설:
  1. (Task 5 리뷰에서 소스를 읽고 예측한 것) MikroORM은 flush 한 번에 INSERT를 UPDATE보다 먼저 보낸다. 이력 INSERT가 FK 검사로 부모 `terminal` 행에 공유 락(S)을 잡고, 이어지는 `UPDATE terminal ... WHERE version=?`가 배타 락(X)을 기다린다. 두 트랜잭션이 둘 다 S를 쥔 채 X를 기다리면 서로 막혀 데드락이 된다.
  2. 테스트 쪽 문제(커넥션 풀 부족 등)로 타임아웃이 난다 → 에러가 1213 데드락이라 가능성 낮음.
- 확인:
  1. 에러 코드: 로그에 `ER_LOCK_DEADLOCK`(1213), 실패한 SQL은 UPDATE. 스택은 `executeUpdates`. → 락 대기 타임아웃(1205)이 아니라 데드락이다. 가설 2 기각.
  2. SQL 순서: 임시 테스트로 전이 1건을 실행하고 MikroORM 쿼리 로그를 받았다(Nest 로거를 거치면 테스트에서 log 레벨이 안 보여서 `MikroORM.init`에 `loggerFactory`를 직접 넣었다. 임시 파일은 지웠다).
     ```
     begin
     select t0.*, m1.... from terminal as t0 inner join terminal_model as m1 ... where t0.serial_no = 'TR-0001' limit 1
     insert into terminal_status_history (terminal_id, ...) values (1, 'IN_STOCK', 'ALLOCATED', ...)
     update terminal set status = 'ALLOCATED', ..., version = version + 1 where id = 1 and version = 5
     select t0.id, t0.version from terminal as t0 where t0.id in (1)
     commit
     ```
     → INSERT가 UPDATE보다 먼저다.
  3. `SHOW ENGINE INNODB STATUS`(docker exec, root)의 LATEST DETECTED DEADLOCK:
     ```
     *** (1) TRANSACTION: ... undo log entries 1
     update `terminal` set `status` = 'IN_STOCK', ... where `id` = 2 and `version` = 2
     *** (1) HOLDS THE LOCK(S):
     ... index PRIMARY of table `terminal_ops_test`.`terminal` ... lock mode S locks rec but not gap
     *** (1) WAITING FOR THIS LOCK TO BE GRANTED:
     ... index PRIMARY of table `terminal_ops_test`.`terminal` ... lock_mode X locks rec but not gap waiting
     *** (2) TRANSACTION: ... undo log entries 1
     update `terminal` set `status` = 'IN_STOCK', ... where `id` = 2 and `version` = 2
     *** (2) HOLDS THE LOCK(S): ... `terminal` ... lock mode S locks rec but not gap
     *** (2) WAITING FOR THIS LOCK TO BE GRANTED: ... `terminal` ... lock_mode X locks rec but not gap waiting
     *** WE ROLL BACK TRANSACTION (2)
     ```
     두 트랜잭션 모두 같은 `terminal` 행(id=2, CC-0002)에 S 락을 쥐고 X 락을 기다린다. `undo log entries 1`은 이미 INSERT 1건(이력)을 했다는 뜻이다. 이 트랜잭션들은 `terminal`을 SELECT로만 읽었으므로(잠금 읽기 아님) S 락의 출처는 이력 INSERT의 FK 검사뿐이다. → 가설 1 확인.
- 원인: 이력 INSERT(FK 검사로 부모 행 S 락) → 단말기 UPDATE(X 락 필요) 순서. 동시에 여러 트랜잭션이 S 락까지 잡고 나면 누구도 X로 올릴 수 없어 InnoDB가 하나를 데드락으로 롤백한다. 데드락 에러는 낙관적 락 에러가 아니라서 필터가 500으로 보냈다.
- 해결: `TransitionService`에서 `terminal.status = cmd.to;` 직후 `await tx.flush();`로 version 검사 UPDATE를 먼저 보내고, 그다음에 이력을 만든다. 첫 UPDATE가 X 락을 잡으므로 나머지는 X 락을 기다리다가, 앞 트랜잭션이 커밋되면 `version` 불일치(0행 갱신)로 `OptimisticLockError`가 난다. (결과는 아래 "해결 후")
- 해결 후:
  - SQL 순서(같은 임시 테스트): `begin` → `select terminal` → `update terminal ... where id = 1 and version = 6` → `select id, version` → `insert into terminal_status_history ...` → `commit`. UPDATE가 먼저 나간다.
  - 실험 3회 모두 2개 테스트 통과:
    ```
    [실험 A] N=20 결과={"200":1,"409":19} 소요=57ms
    [실험 B] N=20 성공=1 실패={"OptimisticLock":9,"InvalidTransition":10}
    [실험 A] N=20 결과={"200":1,"409":19} 소요=57ms
    [실험 B] N=20 성공=1 실패={"OptimisticLock":9,"InvalidTransition":10}
    [실험 A] N=20 결과={"200":1,"409":19} 소요=58ms
    [실험 B] N=20 성공=1 실패={"OptimisticLock":9,"InvalidTransition":10}
    ```
  - 실행 후 `SHOW ENGINE INNODB STATUS`의 LATEST DETECTED DEADLOCK 시각이 `2026-10-22 13:11:14`(수정 전 실행) 그대로였다. 수정 후에는 새 데드락이 없었다.
  - 전체 테스트 6개 파일 `43 passed`, `npm run typecheck` exit 0.
- 배운 것:
  - 자식 행 INSERT의 FK 검사는 부모 행에 S 락을 건다. 같은 트랜잭션에서 부모 행을 나중에 UPDATE하면 S→X 승격이 필요하고, 동시에 여러 개가 S를 쥐면 데드락이다. "부모 UPDATE 먼저, 자식 INSERT 나중"이 안전한 순서다.
  - MikroORM은 flush 한 번 안에서 INSERT를 UPDATE보다 먼저 보낸다. 순서가 중요하면 중간에 `flush()`를 직접 부른다.
  - 데드락(1213)은 필터에 매핑이 없어 500이 된다. 지금은 원인 순서를 고쳐서 없앴지만, 다른 경로에서 데드락이 나면 여전히 500이다. 재시도나 409 매핑은 실제로 다시 나올 때 결정한다.
  - 테스트 앱에서는 `MIKRO_ORM_DEBUG=1`이어도 쿼리 로그가 안 보였다(Nest 로거를 거침). SQL 순서를 볼 때는 `MikroORM.init`에 `loggerFactory`를 넣은 임시 테스트를 썼다.
  - 리뷰에서 소스를 읽고 한 예측이 실제로 재현됐다. 수정 전에 실험을 그대로 돌려 증거를 남긴 덕에 "고쳤다"를 숫자로 말할 수 있다.
