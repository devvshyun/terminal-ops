# 0011. 일괄 등록에서 시리얼 정렬을 빼면 반대 순서로 겹친 요청끼리 데드락

- 날짜 / 관련 기능: 2026-10-23 / F1, F6 (Task 4 리뷰 지적 확인)
- 증상: 리뷰에서 "INSERT를 시리얼 순서로 정렬하는 이유가 테스트로 증명되지 않았다"는 지적을 받았다. 정렬을 잠깐 빼고 겹친 요청 두 개를 반대 순서로 동시에 보내 봤다.
  - 40행끼리(A `RV-0001~0040` 오름차순, B `RV-0060~0021` 내림차순, 20행 겹침): 정렬을 빼도 3회 모두 통과, 데드락 없음.
  - 2000행끼리(임시 테스트, A `BG-00001~02000` 오름차순, B `BG-03000~01001` 내림차순, 1000행 겹침, 한 실행에 3번 × 3회 = 9번): 9번 모두 한쪽이 `DeadlockException: Deadlock found when trying to get lock; try restarting transaction`. 당시 재시도는 unique 위반만 잡아서 데드락은 그대로 실패했다.
    ```
    [재시도-임시] attempt=1 DeadlockException: Deadlock found when trying to get lock; try restarting transaction
    [큰 반대 순서 #1] ok 생성 2000 | FAIL DeadlockException: Deadlock found when trying to get lock; try restarting transaction
    ... (9번 모두 같은 모양, 어느 쪽이 지는지만 바뀜)
    Tests  3 failed (3)   ← 3회 모두
    ```
- 가설:
  1. 두 트랜잭션이 unique 인덱스(`terminal_serial_no_unique`)에 서로 반대 방향으로 키를 넣는다. A가 넣은(커밋 전) 키를 B가 넣으려 하면 B는 그 키에 S 락을 기다리고, 그 사이 A도 B가 넣은 키를 만나 S 락을 기다리면 서로 막힌다.
  2. 40행에서 안 나는 이유: INSERT 한 문장(40행)이 너무 빨리 끝나서 두 트랜잭션의 INSERT 구간이 거의 겹치지 않는다(추정).
- 확인:
  1. `SHOW ENGINE INNODB STATUS`(docker exec, root, 테스트 DB 서버. 읽기만 함)의 LATEST DETECTED DEADLOCK(2026-10-23 11:26:59, 행 값 덤프는 생략):
     ```
     *** (1) TRANSACTION: TRANSACTION 595798, ACTIVE 1 sec inserting
     LOCK WAIT 6 lock struct(s), heap size 1128, 3 row lock(s), undo log entries 3501
     insert into `terminal` (`serial_no`, ...) values ('BG3-01501', ...), ('BG3-01502', ...) ...
     *** (1) HOLDS THE LOCK(S):
     ... index terminal_serial_no_unique of table `terminal_ops_test`.`terminal` trx id 595798 lock_mode X locks rec but not gap
     *** (1) WAITING FOR THIS LOCK TO BE GRANTED:
     ... index terminal_serial_no_unique of table `terminal_ops_test`.`terminal` trx id 595798 lock mode S waiting
     *** (2) TRANSACTION: TRANSACTION 595799, ACTIVE 1 sec inserting
     LOCK WAIT 7 lock struct(s), heap size 1128, 4 row lock(s), undo log entries 3501
     insert into `terminal` (`serial_no`, ...) values ('BG3-01500', ...), ('BG3-01499', ...) ...
     *** (2) HOLDS THE LOCK(S):
     ... index terminal_serial_no_unique ... trx id 595799 lock_mode X locks rec but not gap
     *** (2) WAITING FOR THIS LOCK TO BE GRANTED:
     ... index terminal_serial_no_unique ... trx id 595799 lock mode S waiting
     *** WE ROLL BACK TRANSACTION (1)
     ```
     (1)은 오름차순 A의 여섯 번째 INSERT 문(01501부터), (2)는 내림차순 B의 여섯 번째 문(01500부터 내려감). 둘 다 unique 인덱스의 키 하나에 X를 쥐고 상대 키에 S를 기다린다. 두 레코드 heap no 28과 627이 서로 엇갈린다. → 가설 1 확인.
  2. 40행에서는 데드락 대신 한쪽이 처음 겹친 키에서 바로 unique 위반(`Duplicate entry 'RV-0040'`, 정렬 있으면 `'RV-0021'`)을 받았다. 실행 전후 LATEST DETECTED DEADLOCK 시각이 `2026-10-22 15:19:53` 그대로였다(40행 실행에서는 데드락이 없었다). 가설 2는 숫자로 확인하지 못했다(INSERT 구간 시간을 재지 않음). batchSize 300이라 2000행은 INSERT 문이 7개로 나뉘고 1초 가까이 걸려(`ACTIVE 1 sec`) 겹칠 시간이 생긴다는 추정이다.
  3. 정렬을 되돌리고 같은 2000행 임시 테스트를 3회: 9번 모두 통과, 데드락 없음(LATEST DETECTED DEADLOCK 시각 `11:26:59` 그대로). 진 쪽은 `Duplicate entry 'BG?-01001'` unique 위반 1번 → 재시도에서 ALREADY_EXISTS.
- 원인: 같은 unique 키 집합을 서로 다른 순서로 넣는 트랜잭션 두 개. 커밋 전 키를 넣으려는 쪽은 S 락을 기다리므로, 양쪽이 하나씩 쥐고 엇갈리면 데드락이다.
- 해결: 이미 있는 정렬(시리얼 오름차순으로 엔티티를 만든다)이 이걸 막는다. 이번 커밋에서 바꾼 것은
  - 재시도가 데드락(`DeadlockException`, 1213)도 다시 한다(3번까지, 20~80ms 무작위 대기). 정렬 덕에 일괄 등록끼리는 데드락이 안 나야 하지만, 다른 쓰기 경로와 엇갈릴 때를 위한 안전망이다.
  - 정렬을 뺀 채 새 재시도로 2000행 임시 테스트를 1회 돌리면 3번 모두 통과했다. 다만 3번 모두 `attempt=1 DeadlockException` → `attempt=2 UniqueConstraintViolationException` → 3번째에 성공이었다. 재시도가 있어도 정렬을 빼면 1초짜리 작업을 버리고 시도를 두 번 더 쓴다. 정렬은 그대로 둔다.
  - 40행 반대 순서 테스트(`bulk-registration.e2e.spec.ts`)는 남겼다. 이 크기에서는 정렬이 없어도 통과하므로 정렬의 회귀 테스트는 아니다. 2000행 테스트는 오래 걸려 남기지 않았다(지웠다).
- 배운 것:
  - unique 인덱스에 커밋 전 키가 있으면 INSERT는 바로 실패하지 않고 S 락을 기다렸다가, 상대가 커밋하면 duplicate, 롤백하면 성공이다. 그래서 순서가 엇갈리면 데드락이 될 수 있다.
  - 작은 입력으로 안 나는 데드락이 큰 입력에서 난다. "테스트가 통과한다"가 "순서가 상관없다"는 뜻은 아니다.
