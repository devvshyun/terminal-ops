# 0012. 공백 붙은 시리얼이 납품 명세 검사를 건너뛰고 등록됨

- 날짜 / 관련 기능: 2026-10-23 / F6 (Task 5 리뷰 지적)
- 증상(리뷰 지적, 아직 재현 전): 입고 스캔(RECEIVE)에서 `'SE0-9999 '`·`'SE0-9999\r'`처럼 끝에 공백이 붙은 시리얼은 명세에 없는데도 CREATED가 된다고 한다. decisions/0021(명세 밖 시리얼은 거절)을 어긴다. 회수 입고(RETURN_IN)에서는 같은 입력이 INVALID_FORMAT이 된다고 한다.
- 가설:
  1. 명세 검사(`scan.service.ts` receive)가 다듬지 않은 원래 값으로 `SERIAL_NO_PATTERN.test(serialNo) && !note.has(serialNo)`를 본다. `'SE0-9999 '`은 형식에서 걸려 이 조건이 거짓이 되고 "명세 검사를 통과한 행"으로 엔진에 넘어간다. 엔진 입구 `normalizeRows`가 다듬으면 형식이 맞는 `'SE0-9999'`가 되고, 명세를 다시 보지 않으니 CREATED.
  2. 회수 입고는 `precheckSerials(dto.serials)`를 다듬지 않은 값에 바로 써서 INVALID_FORMAT이 된다.
- 확인: 회귀 테스트를 먼저 넣고(`test/scan.e2e.spec.ts`) 고치기 전 코드로 돌렸다. `npx vitest run test/scan.e2e.spec.ts` → `Tests 4 failed | 7 passed (11)`. 공백 관련 두 개의 차이:
  ```
  입고: ['SE0-9998 ', 'SE0-9997\r', ' <명세 시리얼>\r']
  -     "NOT_IN_DELIVERY_NOTE",
  +     "CREATED",          ← SE0-9998
  -     "NOT_IN_DELIVERY_NOTE",
  +     "CREATED",          ← SE0-9997
        "<명세 시리얼>", "CREATED"

  회수 입고: ['RT-0011 ', 'RT-0011\r'] (RETURNING 상태)
  -     "RT-0011", "RETURNED"
  +     "RT-0011 ", "INVALID_FORMAT"
  -     "RT-0011", "DUPLICATE_IN_REQUEST"
  +     "RT-0011", "INVALID_FORMAT"
  ```
  명세에 없는 SE0-9998·SE0-9997이 실제로 단말기로 만들어졌다 → 가설 1, 2 확인. (나머지 두 실패는 같은 커밋의 다른 수정: RETURN_IN poNo 400, 잠금 해제 실패 시 `expected 500 to be 201`.)
- 원인: 다듬기가 엔진 입구(`registerMany`)에만 있고, 그보다 앞에서 값을 보는 스캔 서비스(명세 검사, 회수 입고, 요청 해시)는 원래 값을 썼다. 검사하는 값과 저장하는 값이 달랐다.
- 해결: `ScanService.scan` 입구에서 시리얼 목록을 한 번 다듬고(`normalizeValue` = `String(s ?? '').trim()`, `normalizeRows`도 같은 함수를 쓰게 바꿈) 요청 해시·명세 검사·입고·회수 입고가 모두 그 값을 쓴다. 엔진 안의 `normalizeRows`는 그대로 둔다(엑셀 경로도 쓰고, 두 번 다듬어도 같다). 고친 뒤 스캔 테스트 11 passed. 같은 커밋의 수정(fix(F6) 스캔 입력 정규화…)
- 영향: 요청 해시가 다듬은 값으로 바뀌어, 이미 저장된 ScanBatch 중 공백이 섞인 요청을 같은 scanId로 다시 보내면 SCAN_ID_REUSED가 될 수 있다. 개발 단계라 저장된 운영 데이터가 없어 그대로 둔다.
- 배운 것: 정규화는 "값이 처음 들어오는 곳"에서 한 번 해야 한다. 안쪽(엔진)에서만 하면 바깥에서 먼저 본 검사가 다른 값을 본다.
