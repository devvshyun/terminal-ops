# 0017. device-sim: stop이 주기를 못 끊고, 실패한 요청의 응답 시간이 통계에서 빠진다

- 날짜 / 관련 기능: 2026-10-23 / F8, F12 (실험 0008 신뢰성)
- 증상: 리뷰에서 device-sim 코드를 읽다 찾았다(실행 중 발견이 아니라 코드 읽기). 확인용 테스트를 먼저 쓰고 돌리니 아래처럼 나왔다.
  - `stop`: 묶음 20개·동시 2개·요청마다 200ms(한 주기 약 2초)에서 주기 도중에 stop을 부르니 `expected 1831.2 to be less than 400`(Fleet), 관리 API `POST /__admin/stop`은 `expected 1395.1 to be less than 350`. 거의 주기 하나가 끝날 때까지 기다렸다.
  - 시간 초과(요청 100ms 제한, 서버 400ms)를 내도 `errors`만 1 늘고, 응답 시간에는 아무것도 안 남았다(`latency`에는 성공한 요청만 들어갔다).
  - 2xx인데 `results`가 없는 응답을 `OK` 0건으로만 세고 오류로 세지 않았다.
  - 100만 개를 기록하면 앞 50만 개만 남아 뒤쪽 값이 통계에 반영되지 않는다(코드로 확인, MAX_SAMPLES).
  - `POST /__admin/config` 세 개를 동시에 보내면 서로 같은 옛 설정에 합쳐 마지막 것만 남는 경로가 있다(합치기가 `await fleet.stop()` 앞에 있었다). 테스트에서도 실패했다(`expected {…} to match object { count: 5, batchSize: 7, … }`).
- 가설과 확인:
  1. `stop()`이 `await this.inTick`만 한다 → `runPool`에 멈춤 조건이 없어 남은 묶음을 끝까지 보낸다. 테스트로 확인(위 시간).
  2. 실패 요청은 `catch`에서 `errors`만 올리고 시간은 버린다. 시간 초과는 가장 느린 요청인데 가장 먼저 빠진다 → p95가 실제보다 낮게 나오는 생존자 편향. 테스트로 확인.
  3. 표본 상한 50만 개는 "앞쪽 50만 개"를 대표로 삼아, 실험이 길어질수록 처음 몇 주기만 보게 된다. `/stats`는 호출마다 전체 배열을 복사·정렬해 O(n log n).
- 원인: 처음 골격(Task 2)에서 "단순하게"만 보고, 멈춤·실패·긴 실험의 경우를 따져 보지 않았다.
- 해결: 이 커밋. `runPool`에 `shouldStop`, `Fleet.stop`의 `stopping` 플래그, 응답 시간을 로그 구간 히스토그램(구간 1% 비율, 메모리·`/stats` 비용이 구간 수 고정)으로 바꾸고 성공·실패를 같이 기록, `timeouts`·`networkErrors`·`httpErrors`·`badResponses` 분리, 설정 검증·관리 요청 직렬화. decisions/0009 갱신 참고.
- 배운 것: 부하 도구의 숫자는 "실패한 요청을 어떻게 세는가"로 결과가 바뀐다. 통계 구조는 상한이 있어도 한쪽 끝을 버리면 안 된다 → study/backlog.md에 추가.
