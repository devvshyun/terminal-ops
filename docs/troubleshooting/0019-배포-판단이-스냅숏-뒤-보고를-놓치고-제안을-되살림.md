# 0019. 배포 판단이 스냅숏 뒤에 커밋된 보고를 놓치고, 보고한 단말기의 제안을 되살린다

- 날짜 / 관련 기능: 2026-10-23 / F8 (Day 4 Task 7 리뷰 지적)
- 증상: 리뷰에서 `RolloutService.control`을 읽다 나온 지적 두 가지(실행 중 발견이 아니라 코드 읽기). 테스트로 경합 시점을 만들어 둘 다 재현했다.
  1. **실패 보고가 실패율에서 빠진다.** 판단이 제한 시간이 지난 대상 c를 OFFERED로 읽은 뒤, TIMED_OUT으로 바꾸기 직전에 c의 FAILED 보고가 커밋되면 단계가 넘어간다.
     - 재현(`firmware-control.e2e.spec.ts` '스냅숏 뒤·TIMED_OUT 갱신 전에…'): 단계 [15, 100](3대), 기준 20%·minSamples 3, 제한 1초. a·b 성공 보고 → `em.nativeUpdate`를 spy해서 TIMED_OUT 갱신이 불릴 때 한 번만 먼저 c의 실패 보고(HTTP, 다른 연결·autocommit)를 끼운다 → `control(id, 지금+2초)`.
     - 고치기 전 결과: `"action": "ADVANCED"`, `"stage": 1`, `"timedOut": 1`(기대 WAITING, 0단계). 실제로는 c가 FAILED라 1/3 = 33.3% > 20%로 중단해야 했다. timedOut 1도 틀렸다(바뀐 행은 0).
  2. **보고한 단말기에 같은 버전이 다시 권해진다.** WAITING 판단이 커밋한 뒤 다시 걸기(publish)가 Redis에 닿기 전에 x의 실패 보고가 커밋하고 제안을 내리면, 다시 걸기가 x의 제안을 되살린다.
     - 재현('스냅숏 뒤에 보고가 커밋되고 제안을 내려도…'): `OfferStore.publish`를 한 번만 가로채, 원래 publish 전에 x의 실패 보고를 끼운다.
     - 고치기 전 결과: `expected '{"rolloutId":12,"version":"3.0.12"}' to be undefined` — FAILED 단말기가 다음 하트비트에 다시 업데이트 지시를 받는다.
  3. (같은 리뷰의 Minor) 보고의 UPDATE가 0행일 때 처음 읽은 상태를 돌려줘 `{ status: 'OFFERED', alreadyReported: true }`가 나올 수 있다. 재현: 보고의 FAILED 갱신 직전에 같은 단말기의 성공 보고를 끼움 → 고치기 전 `status: 'OFFERED'`, 기대 `'SUCCEEDED'`.
- 가설: 1은 RR의 두 가지 읽기가 섞여서다. `nativeUpdate`(UPDATE)는 지금 값(current read)을 보고 `status='OFFERED'` 조건에 걸리지 않는 c를 건너뛴다. `stageStats`의 일반 SELECT는 트랜잭션 첫 일반 SELECT(`offeredTargets`)에서 정해진 스냅숏을 본다 → c는 OFFERED. waiting(제한 시간 안의 OFFERED)에서도 빠져 있다 → 어디에도 세이지 않고 "남은 대상 0" → 단계 넘김. 2는 보고의 내리기가 판단의 걸기보다 먼저 Redis에 닿는 순서 문제(decisions/0031 "남는 것"에 적어 둔 경우).
- 확인: 재현 1의 결과에서 timedOut이 1인데 대상 행은 FAILED(테스트가 따로 읽음)였다 → UPDATE는 0행, 통계는 c를 OFFERED로 셌다는 뜻이다. 가설 1 확인. 재현 2는 끼운 보고가 200을 돌려준 뒤에도 Redis에 x의 제안이 남아 가설 2 확인.
- 원인:
  1. 고른 대상 수(`expired.length`)를 바뀐 행 수로 믿었다. 스냅숏과 current read가 다르다는 것을 생성(create의 count)에서는 따졌지만 control의 UPDATE 뒤 통계에서는 따지지 않았다.
  2. 커밋 뒤 Redis 작업 둘(판단의 걸기, 보고의 내리기)의 순서를 보장하지 않았다.
- 해결: 이 커밋.
  1. `changed = await tx.nativeUpdate(...)`. `changed < expired.length`면 이번 주기는 판단하지 않고 WAITING(`timedOut = changed`). 바뀐 TIMED_OUT은 그대로 커밋한다. 다음 주기는 새 스냅숏이라 그 보고를 센다(재현 1에서 두 번째 control이 ABORTED, `자동 중단: 1단계 실패율 33.3% (1/3) > 기준 20%`).
  2. `publishOffers`: 제안을 건 뒤 그 대상 행들을 PK `IN`으로 다시 읽어(트랜잭션 밖, 지금 값) OFFERED가 아닌 것의 제안을 배포 id 비교 Lua로 내린다. 보고는 커밋한 **뒤에** 내리므로 "걸기 → 다시 읽기" 순서면 둘 중 하나가 꼭 지운다(보고 커밋이 다시 읽기보다 앞 → 여기서 지움, 뒤 → 보고의 내리기가 걸기보다 뒤에 옴). 만들기·재개·판단의 걸기 모두 이 함수를 쓴다.
  3. 보고 0행이면 대상 상태를 다시 읽어 돌려준다.
