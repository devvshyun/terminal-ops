# 0023. 16KB가 넘는 SQL 문장은 왕복이 약 43ms 늘어난다(호스트 → Docker MySQL)

- 날짜 / 관련 기능: 2026-10-26 / F9 (실험 0012, decisions/0033)
- 증상: 실험 0012에서 VAN 대조 5만 건의 수집 단계가 약 6.2초였는데, 같은 100페이지를 HTTP로 받고 JSON을 푸는 것만은 113ms였다. 쿼리마다 DB 왕복 시간(MikroORM `logQuery`의 `context.took`)을 더해 보니 스테이징 INSERT(페이지마다 500행 한 문장, `insert … on duplicate key update`) 100번이 4,968ms — 한 번에 약 50ms였다. 500행 INSERT 한 문장에 50ms는 예상(수 ms)보다 10배쯤 크다.
  ```
  | label | … | collect | … | dbMs | snapInsertMs | snapSelectMs | heartbeatMs | …
  | A 기본 | … | 6201 | … | 5905 | 4968 | 219 | 373 | …
  [실험 0012] 참고: 목록 100페이지 HTTP·JSON만 113ms(DB 없음)
  ```
- 가설:
  1. MikroORM이 SQL을 만드는 JS 시간(자리표시자 3,000개).
  2. 자동 커밋마다의 redo·binlog flush(`innodb_flush_log_at_trx_commit=1`, `sync_binlog=1`).
  3. `on duplicate key update` 또는 PK(run_id, serial_no) 유지 비용.
  4. MySQL 안의 실행이 아니라 전송(호스트 Windows → Docker Desktop 포트 전달 → 컨테이너)에서 기다린다.
- 확인(테스트 DB, 앱 계정, mysql2로 직접. 스크립트는 세션 임시 폴더에 두었고 끝나면 넣은 행을 지움 — 남은 행 0 확인):
  - `took`는 드라이버 호출부터 응답까지라 1은 빠진다. mysql2로 직접 보내도 같다. 페이지 20번 평균:
    ```
    ① 자동 커밋, 자리표시자 3000개(query): 46.2ms/페이지
    ② ① + on duplicate key update: 48.5ms/페이지
    ③ 20페이지를 한 트랜잭션(커밋 1번): 45.2ms/페이지
    ⑥ 미리 만든 SQL 글자 보내기(만드는 시간 제외): 49.2ms/페이지
    ⑦ 같은 500행을 키 없는 임시 표에: 44.9ms/페이지
    ⑧ 자리표시자 3000개 select 한 문장(INSERT 없이 파싱·전송만): 68.3ms/페이지
    ④ 빈 커밋 왕복(select 1): 0.4ms/페이지
    ⑤ 1행 insert 자동 커밋: 3.5ms/페이지
    ```
    커밋을 한 번으로 묶어도(③), ON DUPLICATE를 빼도(①), 키가 없어도(⑦) 같다 → 2·3 기각. 쓰기가 없는 큰 SELECT(⑧)도 느리다.
  - 서버 안 시간(`set profiling = 1` → `show profiles`)과 클라이언트가 잰 왕복을 같은 문장 10개로 비교(SQL 39,608자):
    ```
    클라이언트 왕복(ms) 6.7 47.1 47.6 47.1 47.3 48.1 47.0 47.5 47.4 47.4
    서버 안(SHOW PROFILES, ms) 5.5 5.7 5.7 5.7 5.8 6.4 6.0 5.9 5.9 5.8
    마지막 INSERT 단계(ms): update 1.3, waiting for handler commit 3.9
    ```
    MySQL 안에서는 약 6ms이고, 약 41ms는 서버 밖이다. 첫 문장만 빠르다.
  - 문장 길이를 바꿔 가며(행 수 10~1,000, 각 6번, 중앙값):
    ```
    10행 (908자): 3.8ms / 50행 (4108자): 3.6ms / 100행 (8108자): 4.1ms / 150행 (12108자): 4.3ms / 200행 (16108자): 4.5ms
    300행 (24108자): 47.8ms / 400행 (32108자): 48.0ms / 500행 (40108자): 47.7ms
    1000행 (80108자): 중앙 50.7ms, 6번 8.3 7.7 50.4 55.6 54.4 50.7
    ```
    16KB와 24KB 사이에서 약 43ms 계단이 생긴다. 서버의 `net_buffer_length`가 16384다(`show variables`). 1000행도 새 연결의 처음 두 번은 빠르다.
  - 같은 500행 INSERT를 컨테이너 안에서 mysql 클라이언트로(유닉스 소켓, 포트 전달 없음, `-vvv`의 시간 표시는 10ms 단위): `Query OK, 300 rows affected, 1 warning (0.00 sec)`, 200행 `(0.01 sec)` — 40ms대가 없다.
- 원인(추정, 패킷 캡처로 확인하지 않음): 4. 호스트에서 Docker Desktop 포트 전달을 거쳐 보내는 큰 문장(한 번에 못 받는 크기, `net_buffer_length` 16KB 근처)에서 TCP 지연 ACK(Linux 최소 40ms)와 Nagle류의 기다림이 겹친다. 근거: ① 계단 크기 약 43ms가 지연 ACK 타이머와 맞다, ② 서버 안 시간은 그대로, ③ 새 연결의 처음 몇 문장은 빠르다(Linux는 연결 초기에 quick ACK를 쓴다), ④ 컨테이너 안에서는 없다. mysql2는 소켓에 `setNoDelay(true)`를 건다(`node_modules/mysql2/lib/base/connection.js` 113행) — 기다림은 우리 소켓이 아니라 포트 전달 구간에 있다고 본다.
- 해결: 코드는 바꾸지 않았다. 이 PC의 개발 환경(Windows + Docker Desktop) 문제일 가능성이 커서, 운영(같은 네트워크의 Linux)에서 같은 계단이 있는지 모르는 채 INSERT 묶음 크기를 이 숫자에 맞추지 않는다. 실험 0012 기록에 "수집 6.2초 중 약 4.2초는 이 전송 기다림(추정)"으로 적었다.
  - 다시 볼 조건: 운영과 같은 환경에서 페이지 INSERT가 수 ms가 아니면 → 스테이징 INSERT를 200행(16KB 미만) 묶음으로 나누거나 `LOAD DATA`·여러 문장 묶기를 잰다. 이 PC에서 큰 문장을 보내는 측정에는 이 계단이 섞인다는 것을 기억한다(실험 0011의 대량 INSERT는 `INSERT … SELECT`라 문장이 작아 해당하지 않는다고 본다 — 확인은 안 함).
